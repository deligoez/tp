# v1.29.0 measurements

v1.29.0 answers a field report from a coordinator that drove a spec's tasks by spawning subagents
by hand rather than through `tp run`. Three things went wrong there, and each depended on an agent
remembering:

- an agent started work without claiming its task;
- an agent finished without closing it;
- ready tasks sat idle while fewer agents ran than `run_max_parallel` allows, and a gate that was not
  a task lived only in the coordinator's head.

Two decision notes cover the answer: `agent-bound-claims` (claim at the spawn, refuse a stop that
leaves a claim unexplained) and `filled-pool` (a coordinator is asked to fill its free slots, and a
gate that is not a task is written down as a hold). Both are in `spec/backlog/ARCHIVE.md`.

## What the harness gives

Every fact below was measured in a scratch repository with `claude -p` sessions and a hook that
logged its stdin, never in the requesting project.

- A `PreToolUse` payload carries `agent_id` only when the caller is itself a subagent; the command
  environment of a hook carries only the session id. Neither identifies the agent a spawn creates.
- A `PreToolUse` hook on `Agent` sees `tool_input.prompt` and `tool_use_id`.
- Rewriting a command through `updatedInput` defeats the session's allow rules, so the claim is a
  separate `tp claim`, never a rewritten command.
- `SubagentStop` fires for a foreground agent, an agent in its own worktree (its `cwd` is the
  worktree) and a background agent, with `agent_transcript_path`. Beside that transcript,
  `agent-<id>.meta.json` holds the spawn's `toolUseId`; a running or killed agent has no `finished`
  key.
- `{"decision":"block","reason":...}` from `SubagentStop` or `Stop` makes the agent act on the
  reason; the next stop arrives with `stop_hook_active: true`.
- `TaskStop` fires no `SubagentStop`, so a killed agent leaves its claim behind.
- The main session's `Stop` input carries `background_tasks`, each running subagent as
  `{id: <agent id>, type: "subagent", status: "running"}`. An agent that ends its turn to wait on
  its own job drops out of the list; only its shell stays, with no owner. That is why a parked claim
  (`waiting` on a wip task) holds a slot.
- The meta file of a main session's agent is at `<transcript_path without .jsonl>/subagents/agent-<id>.meta.json`,
  read on this machine's own session directory.

## How the change was tested

Each behaviour was written test first. Where a test passed the first time it ran, it was shown able
to fail by a mutant made in a throwaway copy of the tree, one mutant per copy, each run against the
test named for it:

- the hold (`waiting` on an open task) across the ready pickers, `tp show`, `tp status`'s precedence,
  `tp export`, `tp resume`'s blocker, validate, and the clears on claim, batch claim, unclaim and
  `tp run`'s claim, release and solo reopen: 14 mutants, 14 killed;
- `tp pool`'s classes, session scope, unresolved agents, epic block, the reason's slice, the payload's
  subagent filter, and the hook's unit and second-stop exits: 13 mutants, 12 killed. The survivor
  removed the `coordinator` conjunct from `ask`; a session that never claimed has cap 0 and so no
  free slot, which makes the conjunct redundant, and it was removed.

A defect the hold introduced was caught before release: `tp claims` counted `waiting` on any copy as
a parked claim, so a worktree cut while a task was held kept passing the stop guard after the task
was claimed (red test first).

## The review rounds

The decision track ran two reviewer roles, correctness and agent experience, for two rounds, each
probing a build of the branch in throwaway repositories.

Round 1 found one regression the branch itself made. A coordinator's claim is an uncommitted edit on
its own tree, so an agent in its own worktree saw its task open: its close and its park went to its
own copy, the stop guard could not see the park, and merging its branch met the coordinator's
uncommitted claims. A probe reproduced the refused merge and, with the claims committed first, a
conflict in the task file. Before this branch the coordinator wrote nothing there, so the merge had
been clean. The repair has one root: `tp done` and `tp set waiting=` in a worktree write to the copy
that holds the claim, gating the worktree's own code first, so the agent's branch carries code only;
the same probe now merges cleanly and keeps the claim's start. Two rules followed from it: a copy
speaks for a claim only when it carries that claim's spawn, and a spawn carries one task.

Round 1 also found the hold leaking into `tp done`'s ready count, `tp commit`'s implicit claim and
`tp next`'s report; a stop guard that blocked every agent under a `tp` older than the plugin; a
pasted JSON brief whose marker the hook missed; a pool that offered tasks `tp run` would not start
beside the running ones; a Stop payload without `background_tasks` read as every agent gone; and
reasons whose commands did not run in a repository with two task files. Each was fixed test first, or,
where the test came after the code, shown red by a mutant.

Three findings were new surface, and the operator settled them:
- A per-session pause of the pool hook is not built. The operator sets `run_max_parallel` before a
  run, and lowers it to have fewer agents; the hook only holds the coordinator to that number.
- A resumed session keeps its id: a `claude -p --resume` run reported the first run's `session_id`,
  and its `Stop` input carried the same id, so its claims stay its own.
- A live agent spawned without a marker holds no slot, as decided: the marker is the way in.

The same probe settled a guard: a `Stop` input with no agent running carries `background_tasks` as
`[]`, so the pool hook's silence on an absent field never meets an empty pool.

## Left for later

- A coordinator that spawns without a brief's marker is not claimed for; the brief is the way in, and
  the stop guard only knows spawns it saw (`BUGS.md`).
- The pool reads only the coordinator's current tree for ready tasks. Other worktrees count for
  closes, parks, and a task closed there, not for readiness.
- Two task files whose `run_max_parallel` differ give the pool the smaller cap; no field case has
  two yet, and no test pins it.
