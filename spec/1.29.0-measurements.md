# v1.29.0 measurements

v1.29.0 answers a field report from a coordinator that drove a spec's tasks by spawning subagents
by hand rather than through `tp run`. Three things went wrong there, and each depended on an agent
remembering:

- an agent started work without claiming its task;
- an agent finished without closing it;
- ready tasks sat idle while fewer agents ran than `run_max_parallel` allows, and a gate that was not
  a task lived only in the coordinator's head.

Two decision notes cover the answer: `agent-bound-claims` (claim at the spawn, refuse a stop that
leaves a claim unexplained) and `filled-pool` (a coordinator is asked to fill its free slots, and a
gate that is not a task is written down as a hold). Both are in `spec/backlog/ARCHIVE.md`.

## What the harness gives

Every fact below was measured in a scratch repository with `claude -p` sessions and a hook that
logged its stdin, never in the requesting project.

- A `PreToolUse` payload carries `agent_id` only when the caller is itself a subagent; the command
  environment of a hook carries only the session id. Neither identifies the agent a spawn creates.
- A `PreToolUse` hook on `Agent` sees `tool_input.prompt` and `tool_use_id`.
- Rewriting a command through `updatedInput` defeats the session's allow rules, so the claim is a
  separate `tp claim`, never a rewritten command.
- `SubagentStop` fires for a foreground agent, an agent in its own worktree (its `cwd` is the
  worktree) and a background agent, with `agent_transcript_path`. Beside that transcript,
  `agent-<id>.meta.json` holds the spawn's `toolUseId`; a running or killed agent has no `finished`
  key.
- `{"decision":"block","reason":...}` from `SubagentStop` or `Stop` makes the agent act on the
  reason; the next stop arrives with `stop_hook_active: true`.
- `TaskStop` fires no `SubagentStop`, so a killed agent leaves its claim behind.
- The main session's `Stop` input carries `background_tasks`, each running subagent as
  `{id: <agent id>, type: "subagent", status: "running"}`. An agent that ends its turn to wait on
  its own job drops out of the list; only its shell stays, with no owner. That is why a parked claim
  (`waiting` on a wip task) holds a slot.
- The meta file of a main session's agent is at `<transcript_path without .jsonl>/subagents/agent-<id>.meta.json`,
  read on this machine's own session directory.

## How the change was tested

Each behaviour was written test first. Where a test passed the first time it ran, it was shown able
to fail by a mutant made in a throwaway copy of the tree, one mutant per copy, each run against the
test named for it:

- the hold (`waiting` on an open task) across the ready pickers, `tp show`, `tp status`'s precedence,
  `tp export`, `tp resume`'s blocker, validate, and the clears on claim, batch claim, unclaim and
  `tp run`'s claim, release and solo reopen: 14 mutants, 14 killed;
- `tp pool`'s classes, session scope, unresolved agents, epic block, the reason's slice, the payload's
  subagent filter, and the hook's unit and second-stop exits: 13 mutants, 12 killed. The survivor
  removed the `coordinator` conjunct from `ask`; a session that never claimed has cap 0 and so no
  free slot, which makes the conjunct redundant, and it was removed.

A defect the hold introduced was caught before release: `tp claims` counted `waiting` on any copy as
a parked claim, so a worktree cut while a task was held kept passing the stop guard after the task
was claimed (red test first).

## The review rounds

The decision track ran two reviewer roles, correctness and agent experience, for two rounds, each
probing a build of the branch in throwaway repositories.

Round 1 found one regression the branch itself made. A coordinator's claim is an uncommitted edit on
its own tree, so an agent in its own worktree saw its task open: its close and its park went to its
own copy, the stop guard could not see the park, and merging its branch met the coordinator's
uncommitted claims. A probe reproduced the refused merge and, with the claims committed first, a
conflict in the task file. Before this branch the coordinator wrote nothing there, so the merge had
been clean. The first repair wrote the agent's close beside the claim. Round 2 showed that a close is
more than a record: the gate then ran on the coordinator's tree as well, `--auto-commit` committed
the coordinator's files, `tp commit` bypassed it, and a dependent became ready before the agent's
code was merged. That repair was taken out; the close of a worktree agent got its own decision note
(below, *The worktree landing*). What stayed: a park is written beside the claim, a copy speaks for a claim only when it carries
that claim's spawn, and a spawn carries one task.

Round 1 also found the hold leaking into `tp done`'s ready count, `tp commit`'s implicit claim and
`tp next`'s report; a stop guard that blocked every agent under a `tp` older than the plugin; a
pasted JSON brief whose marker the hook missed; a pool that offered tasks `tp run` would not start
beside the running ones; a Stop payload without `background_tasks` read as every agent gone; and
reasons whose commands did not run in a repository with two task files. Each was fixed test first, or,
where the test came after the code, shown red by a mutant.

Three findings were new surface, and the operator settled them:
- A per-session pause of the pool hook is not built. The operator sets `run_max_parallel` before a
  run, and lowers it to have fewer agents; the hook only holds the coordinator to that number.
- A resumed session keeps its id: a `claude -p --resume` run reported the first run's `session_id`,
  and its `Stop` input carried the same id, so its claims stay its own. An interactive resume was
  not measured.
- A live agent spawned without a marker holds no slot, as decided: the marker is the way in.

A probe settled a guard: a headless run's `Stop` input carried `background_tasks` as `[]` with no
agent ever started, and again as `[]` once a background agent it had spawned had finished (the
earlier `Stop`, while the agent ran, listed it as `running`). The pool hook's silence on an absent
field did not meet an empty pool in either case. An agent stopped with `TaskStop` was not measured.

## The worktree landing

The close the review rounds took out came back through its own decision note
(`spec/backlog/worktree-land.md`, archived in `spec/backlog/ARCHIVE.md`). An agent in its own worktree
closes by writing a land request (`tp done <id> --commit <sha>`, gated in its worktree); the
coordinator's `tp pool` asks for `tp land` first, which picks the commits onto its branch and closes
the task there with its own gate. The coordinator's tree stays the only place a close is recorded.

It ran three review rounds, the third by the operator's decision over the track's cap of two. Each
finding was fixed with a test seen red first:
- round 1 (`00fcb2a6`..`37e2092f`): the coordinator's staged change swept into a landing, `tp land`
  run in an agent's worktree, a failed gate's cause not reported, an agent's copy closed again after
  its request landed, and a project below the repository root given a `tp land` call that did not run;
- round 2 (`bbf618a3`..`8ff79ad7`): a pick a crash left behind blocked every later `tp land`, a
  request not bound to the claim it was made under, and a coordinator able to close a spawn-claimed
  task with commits its branch lacks;
- round 3: the crash case recorded an empty commit instead of the one carrying the change, a merge
  commit blocked forever instead of reopening, a reopened task's brief named the task file from the
  project root rather than the repository root, the off-branch refusal named no worktree or command,
  and a sha that does not exist was reported as off-branch.

A pass over the round-3 fixes before tagging found that every pick git refused without a conflict
reopened the task, including a failure of the coordinator's own tree (a held index lock), which
would throw away finished work and respawn its agent. Only a merge commit reopens now; any other
refusal is `blocked` with the request kept. A change the branch carries inside a larger commit is
recorded as that commit, and an operation left in progress names the git command that aborts it.

The hand run on the release binary: an agent's `tp done --commit` in its worktree wrote the request,
the `Stop` hook's input (`session_id`, `cwd`, `background_tasks: []`) gave a block decision naming
`tp land --file spec.tasks.json`, `tp land` closed the task, its dependent became ready, and the
agent's repeated close exited 4 as already landed.

What the rounds found about the request's life after it leaves — a dropped request writes no
outcome, a second request written during a landing is deleted with the first, and the rest — was
first filed in `BUGS.md` as a change to the note's decision. Read against the archived note (item 4:
"the agent's worktree is told the outcome and closes nothing", "no hint suggests `--skip-gate`"),
it was conformance to that decision, and v1.29.1 fixed it; see *The request's life (v1.29.1)*.

## The request's life (v1.29.1)

Each fix below began as a `internal/cli` test (or, for the request removal, an `internal/engine`
one) seen red for the stated reason before the change:

| Test | What it saw red |
|---|---|
| `TestAFailedAgentsSecondCloseLeavesTheFreshAgentsRequest` | found while checking the list, not in it: after a failed landing a fresh agent's request cleared the first agent's outcome (one per task id), so the first agent's repeated `tp done` exited 0, overwrote the fresh request, and the landing conflicted again (`agent.txt` stayed `other`) |
| `TestLandTellsTheAgentWhenItsRequestIsDropped` | a request for a task closed by hand left `unlanded` empty and no outcome |
| `TestRemovingALandRequestKeepsOneWrittenSince` | `RemoveLandRequest` took an id, so it could only delete whatever was there |
| `TestASetInTheAgentsWorktreeAfterLandingIsRefused` | `tp set waiting=` and `title=` exited 0 on the landed task's copy and dirtied the task file |
| `TestPoolAsksForAFreshAgentAfterAFailedLanding` | after a reopen the session was no coordinator: `ready` empty, `ask` false, the Stop hook silent |
| `TestLandReportsWhyTheGateFailed` (extended) | the child close's log carried `--skip-gate` |
| `TestALandingTaskWhoseAgentRunsHoldsItsSlot` | `free` was 1 with the landing agent still live (cap 1) |
| `TestABatchCloseRefusesACommitItsBranchLacks` | the batch row closed the spawn's claim on a commit the branch lacked |

The outcome is now one file per task and worktree, the request is removed only when its `at` is
still the one read, and the off-branch check is one function the single-id and batch closes share.
The landing slot is option (a) of the two put to the operator: a `landing` claim holds a slot while
its spawn is live, the same evidence `running` uses.

## Left for later

- A coordinator that spawns without a brief's marker is not claimed for; the brief is the way in, and
  the stop guard only knows spawns it saw (`BUGS.md`).
- The pool reads only the coordinator's current tree for ready tasks. Other worktrees count for
  closes, parks, and a task closed there, not for readiness.
- Two task files whose `run_max_parallel` differ give the pool the smaller cap; no field case has
  two yet, and no test pins it.
- Engine-level tests for `LandPick` and the claim holders, so a mutation run can see the landing
  code without the cli's child process.
