# v0.34.0 candidates

Carried from the v0.33.0 cycle. `spec/0.34.0.md` already holds a different headline (unattended
run); these are the items that cycle's 13-round audit deliberately did not take, each with the
reason it was accepted rather than fixed. Items 1–2 are the two Non-Goals v0.33.0 declared; 3–6 are
audit findings accepted with recorded justification; 7 comes from the release check.

## 1. `scope` on audit rows — Non-Goal 1 of v0.33.0

Still the headline of the convergence problem, and still deferred for the same reason v0.33.0 gave:
`scope` is a judgement made by the very sub-agent that wrote the row, so wiring it into the release
gate means one row mislabelled `codebase` lets a genuine spec violation ship — strictly worse than
today's rule, which only over-counts and wastes rounds. v0.33.0 shipped the *signal*
(`spec_coverage_clean_rounds`, `role_streaks`, `divergence`) and left the gate alone precisely so
the operator gets the information without the tool getting the authority.

Whatever v0.34.0 does here has to answer: what makes a `scope` label trustworthy enough to gate a
release? A second role classifying independently, a mechanical rule derived from the checklist item
rather than the finding, or an explicit operator confirmation per label are the three shapes worth
costing.

## 2. `audit_converge_on` — Non-Goal 2 of v0.33.0

Depends entirely on item 1. Without a trustworthy `scope`, the knob has nothing to select on.

## 3. `tp import` writes the task file with no lock

`importcmd.go` reads the target twice and writes it through `WriteTaskFile` outside
`WithFileLock` — the last lock-free write path in the tool. v0.33.0 made that write *atomic*, which
removes torn reads but not lost updates: a concurrent `tp import` + `tp add` lost the add's task in
1 of 20 runs, with both processes exiting 0. Atomicity is not mutual exclusion.

Accepted because the window needs two writers on one task file, which the documented single-agent
loop does not produce; the fix is to wrap the read-modify-write in `WithFileLock`, which is
mechanical but wants its own test.

## 4. `tp add --bulk` and `tp set --bulk` drop rows past the 64KB line cap and report success

`{"added":["b1"]}`, exit 0, with the warning on stderr only — a 3-row file whose middle line is 70KB
adds one task and silently discards two. Every reader in the review/audit family was swept for this
class in v0.33.0 and now aborts exit 3 at a shared 1MB cap; the bulk readers were left out because
each pins its own warn-and-continue contract in its own tests and neither feeds a convergence gate.

The exemption is recorded at the call sites themselves (`line-cap:` markers in `add.go` and
`set.go`), so the guard that enforces the shared cap cannot quietly swallow a new reader.

## 5. The `ExitValidation` channel inherits task-file advice

`root.go` reports every validation error with the code-1 default hint, `run 'tp validate' to audit
the task file`. Two consequences:

- A malformed `--record` NDJSON (`tp audit|review <spec> --record bad.ndjson`) names an unrelated
  command and an unrelated file. The message itself names the file and the line, so an agent is not
  stuck — it just wastes a round trip.
- `tp <unknown-command>` exits **1** where the documented scheme says usage errors are **2**;
  `tp audit --bogus-flag` correctly exits 2, so tp is internally inconsistent here.

`TestFileErrorsCarryAHint` covers `ExitFile` sites only. Extending it to `ExitValidation` is the
natural follow-on and would enumerate these the way the exit-3 sweep enumerated its own class.

## 6. `lint.go` and `init.go` exit-3 sites want `specFileMissingHint`

Both commands take a **spec**, so the code-3 task-file default is the wrong object — the same
defect the v0.33.0 sweep fixed across the review/audit family. They are recorded in
`taskFileCommands` with that honest reason rather than as clean exemptions, so the list documents a
deferral instead of implying they are fine.

## 7. Documentation debt found by the release check

- `README.md`'s lint table lists 9 rules while the engine emits about 20 (`vague-language`,
  `long-spec`, `duplicate-heading`, `heading-hierarchy`, `section-size`, `orphan-reference`,
  `frontmatter`, `section-anchor` are absent). Possibly deliberate curation; worth deciding.
- Flags absent from all four docs: `--reason-file` (`done`/`close`), `--stdin` on `done`/`close`,
  `--docs-path`/`--test-path` (required with their perspectives), `--base` (`audit`),
  `--commit-strategy` (`init`).
- `spec/0.23.0.md` §8 still says "tp never silently rebuilds the index", which v0.33.0 made false
  for the snapshot-only case. It is a historical spec and was left alone deliberately; the living
  docs were corrected. Worth a one-line note in that file if historical specs are ever revised.

## Process note carried forward

Three guard tests written during the v0.33.0 audit looked like guards and were not: one failed 1 run
in 10 against the defect it targeted, one passed against a deliberately nonsense implementation
because a *different* mechanism satisfied its only assertion, and one was the sole data race in the
repo — invisible because the quality gate does not run `-race`. Each was caught by an independent
role re-deriving the claim by mutation.

Two cheap habits follow, and both belong in whatever runs the next cycle: **mutate the
implementation and watch the new test fail before trusting it**, and consider adding `go test -race`
to the gate, since the gate as written cannot see a data race at all.
