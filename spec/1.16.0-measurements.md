# tp 1.16.0 — a finding the next round is told not to re-report blocks convergence

1.16.0 builds `spec/backlog/carried-rows-block.md`, a Decision-track note, in one clone. The repro
below runs in a fresh `git init` repository outside this one; the shipped-spec measurement runs in a
`git clone` of this repository, read paths only. Both use a binary built from `227fad90` (v1.15.1,
before) and one built from the release's code commits (after).

## Conclusions

- **The hole is closed where it was found.** BUGS.md's sequence — a high recorded in round 1, then
  two empty rounds whose prompts carry it under "UNRESOLVED findings from previous rounds — DO NOT
  re-report" — now leaves `--status --check` at exit 1, `converged: false`, with the row named.
- **One set, read twice.** `engine.ReviewCarriedSet` is the only place the carried rows are computed:
  the rounds after the newest epoch, each finding (category, location, the first 80 bytes of its
  text) at its latest occurrence, classified unresolved, accepted or resolved. The emission's carry
  listing and every convergence read take it from there, and a test compares the prompt's blocking
  rows with the ones `--check` names over a history holding every disposition.
- **Latest occurrence, not first.** The old dedup kept the first copy of a finding, so a row re-raised
  and fixed in a later round was still listed as unresolved. With the set now also gating
  convergence that would have held loops open for nothing; the carry keeps the latest copy. The
  existing `TestResume_AReviewTheCapEndedMovesOn` depends on it: its three rounds repeat one row and
  only the third copy is accepted.
- **The cap does not end a loop past a carried row either.** At the cap the loop used to be done once
  the latest round's rows were dispositioned. A carried blocking row from an earlier round was never
  dispositioned, so the cap now leaves the loop open too, and the cap refusal's hint is that row's way
  out instead of the latest round's file.
- **A fix counts once a round verifies it** (decision 6, raised in review, approved by the operator).
  Marking a carried blocking row `fixed` used to clear it at once, unattended too, and at the cap end
  the loop. It now blocks until a review round emitted after the fix is recorded.
- **Shipped specs flip on `--status`, the export's `review.state` and the dashboard's table.** Four
  shipped specs read not converged after the upgrade. Nothing proposes review work on them: `tp
  resume`, the session-start hook and `tp export --list`'s `next_step` read the phase from the task
  file first, and all four are past review (three in `release`, 0.25.0 in `audit`, as before). The
  export's review `state` goes `done` → `cap_reached`, which the dashboard's spec table renders as
  "cap reached", and the drawer now says "N carried blocking findings unresolved" instead of
  "converged in round N".
- **Three shipped histories converge only through the no-order fallback** (below): 0.23.0, 0.30.0 and
  0.34.0, holding 86 fixed blocking rows between them. Counting those rows unverified would flip all
  three.

## Upgrade consequence, for the release notes

Review convergence now waits on the findings the next round is told not to re-report. A spec review
is not converged — and a round cap does not end it — while a critical or high finding from an
earlier round stands unresolved, or is marked `fixed` and no review round emitted after the fix has
been recorded. Histories that converged by empty rounds past such a finding read as not converged
after the upgrade; in tp's own repository that is 0.24.0, 0.25.0, 0.29.0 and 0.31.0, all past review,
so nothing asks for review work on them. A `fixed` written from 1.16.0 on records the round it
follows; one with no recorded order counts as verified if a later round is recorded. An epoch over a
text that still holds an unresolved blocking finding is the operator's decision
`rewrite-past-blocking`.

## Calls the note left open

- **How `rewrite-past-blocking` behaves by hand.** The two models in tp are `discard-emission`, which
  needs `--force` by hand because it overwrites files on disk, and `accept-finding`, which needs no
  flag by hand and is fenced only under `TP_UNATTENDED`. An epoch past a blocking row destroys
  nothing and has the effect of an acceptance, so it follows `accept-finding`: no flag, a stderr
  notice naming the decision, and `cut_blocking`/`cut_blocking_rows` in the payload. `--rewritten`
  keeps refusing `--force`, so `--force` keeps meaning a discard.
- **The resume blocker's class.** `review-carried-blocking` is `escalate`: another round cannot clear
  a row its roles are told not to re-report, so handing `tp run` a round unit would loop until the
  cap. It fires only for rows recorded before the latest round; the latest round's own rows are the
  `review-resolve` unit's.
- **The payload bound.** A count and the first five rows, the same five in `--status`, `--record`,
  the resume blocker and `--rewritten`. 0.25.0's 57 rows show why the list is cut.
- **`LoopDone` stays a value type.** Its new slice field pushed it over gocritic's `hugeParam`
  threshold; grouping its three flags brought it back under rather than turning seven signatures
  into pointers.

## After review

Both reviews of the first build were addressed in the same clone, each change test-first.

- **Decision 6, a fix counts once a round verifies it.** Repro, before: round 1 a high, rounds 2 and 3
  empty, then `--resolve 0 fixed` — `--status` read `done: true, done_by: cap`. After: `done: false`,
  `carried_fixed_unverified: 1`, the row's `state` is `fixed-unverified`, and `next_action` names the
  operator's `raise-review-cap` and no `--resolve`. Below the cap the next recorded round verifies the
  fix and the loop converges; a round already emitted when the fix was written does not.
- **A later low copy no longer downgrades a carried high**: a row is graded at the highest severity
  since its last resolving disposition, and the prompt tags it so.
- **`--status`/`--record` list only rows of rounds before the latest**; `carried_blocking` stays the
  whole predicate. The resume blocker leads the budget blocker, carries `commands` and `operator` as
  `spec-stale` does, and the cap refusal's hint is the carried clause instead of the latest-round
  hint. `tp export` carries `carried_blocking` and the drawer shows it.
- **Low items**: the review-resolve unit owes a resolve for a blank-evidence `wontfix`; next_action's
  latest-round branches count the earlier carried rows; the row's aside comes before its command; a
  cap ending past an epoch cut says so; `review_loop.convergence` names the carried rows.
- **Skipped: refusing `--resolve … fixed` over an unchanged spec.** Comparing the round's snapshot hash
  with the spec's takes a few lines, but 63 test call sites in 24 files resolve `fixed` without
  editing the spec, so the refusal is not a few lines in effect. Decision 6 already keeps such a fix
  from ending the loop until a round reads it.
- **An epoch past a fixed row is not past a blocking one**: the rewrite is the change, and the next
  round reads the new text whole, so `rewrite-past-blocking` counts unresolved rows only.

## Who decided

The operator chose the scope: the rule of the note, leaving the four shipped specs unconverged rather
than backfilling dispositions nobody checked, and the narrow `rewrite-past-blocking` — only an epoch
whose cut holds an unresolved blocking row is the operator's, any other epoch stays ordinary. Review
raised decision 6 and the operator approved it. Its fallback for a disposition with no recorded
order is put to the operator with the count above — three shipped specs, 86 rows — since that
approval has to cover a number. The tp-smart session gave a
second opinion on the rule. The agent took the calls listed above. No rule-9 decision came up while
building it: no gate was skipped, no cap raised, no finding accepted without a change and no emission
discarded.
