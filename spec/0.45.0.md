# tp v0.45.0 — When the spec moves between rounds

> Split from `spec/0.43.0.md`, whose own Non-Goal 9 named these two sections as the second half that
> should ship in a later number, on the grounds that they are the part touching v0.35.0's shipped
> surface. They share a subject that neither of the other halves has: what happens to a round's
> record when the spec it read has since changed. The content is unchanged.

## 1. Overview

Two things happen between counted rounds and tp records neither. The operator repairs the spec, and
the repair is reviewed only by the next full five-role panel — expensive out of proportion to a
one-section change. And the repair moves the spec's hash, which invalidates the round's staleness
check with no way to say *why* it moved.

Both are accounting rather than convergence. Nothing here changes what counts as a clean round, and
`spec/0.37.0.md` §4 owns the one rule that does — a changed spec resets the audit streak. This
release is the reader-facing side of the same event.

## 2. Recommending the scoped delta round

Today any `fixed` disposition voids a round: `--record` refuses it, correctly, because a fix means
the spec changed and the round's findings were read against older text. The cost is that a
one-section repair forces a full five-role panel.

**The pass already exists; only the recommendation is missing.** `tp review <spec> --perspective
regression` emits the regression role alone, derives its scope from the newest earlier snapshot via
`DiffSections`, and reports `Round: 0`, "This pass records no state" and `Convergence: "uncounted
delta pass — counted rounds stay full-panel"` — verbatim what a new `--delta` flag would have to
produce. An earlier draft of this section proposed that flag and justified it as "generalizing the
existing pass by deriving the scope instead of taking it"; the derivation is the shipped default, and
taking the scope (`--diff-from` + `--findings`) is the opt-in mode. Adding the flag would have shipped
a second spelling of a shipped feature, so no flag is added.

What this release adds is one thing: **`next_action` learns to recommend that pass.** Today an
operator finds it in `skills/tp/SKILL.md` or does not run it at all, which is why a one-section
repair still costs a five-role panel.

The recommendation fires in one situation: the last recorded round produced findings, the repairs
since touched **more than three sections**, and no section was added or removed. Outside that,
`next_action` still names a full counted round. The threshold direction is SKILL.md's, not this
file's — the manual has carried "when a fix batch touched more than 3 sections, run the standalone
regression delta pass" since v0.28.0, and an earlier draft of this section inverted it to "at most
three". A large repair is what needs the cheap look; a one-section repair is small enough that the
next counted round covers it. The rule now has one home, and SKILL.md's line is the one it agrees
with.

A delta pass is a cheap look at a large repair, never a substitute for a round, and it can never move
the loop toward convergence — only a counted full-panel round can.

**The branch is omitted while a run is driving.** `spec/0.35.0.md` §3.3 fixes eight unit kinds and
none of them runs a delta pass, and those kinds shipped — `unit-kinds`, `brief-commands` and
`next-units` are closed tasks against `internal/engine/unitkind.go`. So an unattended driver reaching
this recommendation would be told to run work it has no unit for, which is the failure
`spec/0.35.0.md` §8a already names for a different branch. The rule is therefore stated here rather
than deferred: when `TP_RUN_ID` is set, `next_action` names the counted round instead. The branch is
for an operator at a terminal, and a ninth unit kind is not on the table — it would reopen a
review-converged 44-task spec mid-implementation to buy a recommendation a human can already read.

Delta findings go where the invoking operator sends them (`-o`, defaulting to stdout as today) and
never into `$TP_ROUND_DIR`: an uncounted pass must not write the counted round's regression file,
which `spec/0.35.0.md` §6.3 reserves for a role unit the driver spawned.

## 3. Recording why the spec changed

A delta pass reviews the change. Nothing records the *intent* of it, and the gap is not cosmetic.

A tp user driving a Rust NLP project reported the shape: after nine commits, every one closing an
item the rounds themselves had opened, the only way to clear the resulting staleness was to overwrite
the hash the round had actually read. The correct action and the mechanical action pointed in
opposite directions, so the user hand-authored a `spec_hash_at_round` field with a note beside it
rather than corrupt the record.

`tp review <spec> --reconcile --note "<text>"` records a reconciliation entry: the hash the round
read is preserved, and the note stating why the spec moved is added as its own row rather than
overwriting anything. Like §2's delta pass it is uncounted and gates nothing — accounting, not
convergence.

The invariant this protects is the one tp relies on everywhere else: **a recorded round is a frozen
fact.** Any surface that makes overwriting one the path of least resistance is a defect in tp, not
in the operator.

**tp's own v0.35.0 cycle then hit it, which is the second instance and the one measured from inside.**
Mid-implementation, verifying the converged spec against shipped code found two real gaps — the oracle
emitted no record unit, and §6.3's retry promise was refused by the recorder — so the spec was
repaired, and the repair was put through the uncounted regression pass, which found eight defects in
it. The blocker then had no honest exit: `--reconcile` does not exist yet, and the only mechanical
clearance was overwriting the hash the rounds had read. The cycle proceeded to audit with the blocker
standing, because **after implementation is complete the audit subsumes what a re-review could ask** —
`spec-coverage` derives its checklist from the repaired text and tests the code against it, which is
strictly stronger than a reviewer reading prose about code that already exists. The cost avoided was
real: `review_clean_rounds` is 2 and every `fixed` forces another round, so a five-role panel over a
whole spec to settle a two-section repair is the shape v0.32.0 paid eleven rounds for. What was
missing was not a way to re-review; it was a way to **record why the spec moved** without lying about
what the rounds read.

**How this composes with `spec/0.37.0.md` §4.** That section resets the audit streak when the spec
hash changes; this one records why it changed, preserving the hash the round actually read. Reconcile
explains the movement for a reader, the reset makes the loop re-earn its streak. Neither substitutes
for the other and neither is a prerequisite for the other.

## 4. The delta pass must not become the loop

This gates the release rather than testing it afterwards.

The regression pass never changes `consecutive_clean`, never writes a round file, and never appears
in `next_action` while `TP_RUN_ID` is set. A cycle driven only by regression passes must remain
un-converged forever.

The gate needs no corpus — it is a behavioural assertion against a live tree — which is why it is
the one gate among the three specs split out of `spec/0.43.0.md` that survives that file's §6.1
input problem intact.

## 5. Non-Goals

1. **No new flag for the delta pass.** §2 explains why: the pass ships already, under
   `--perspective regression`.
2. **No convergence arithmetic change.** Both mechanisms are uncounted; `spec/0.43.0.md` Non-Goal 1
   states the general rule and this release is inside it.
3. **No new roles.** The delta pass reuses the existing regression role.
4. **No unit kind for the delta pass.** §2 carries the rule normatively — the branch is omitted when
   `TP_RUN_ID` is set — so this is a pointer, not a deferral. v0.35.0's eight kinds shipped first,
   which settles the question in this release's favour rather than leaving it open.
5. **No `hunt`/`fix` round kind.** Recorded against the same field report in `spec/0.43.0.md`
   Non-Goal 6.

## 6. Tests

1. `tp review <spec> --perspective regression` — the shipped pass this release recommends rather
   than reimplements — still emits the regression role alone, derives its scope from the newest
   earlier snapshot, and reports `Round: 0`. A recommendation is worthless if the pass it names
   drifts, so this is a regression guard on a shipped surface, not a test of new code.
2. That pass writes no round file, leaves `consecutive_clean` unchanged, and sends its findings to
   `-o`/stdout rather than to `$TP_ROUND_DIR`.
3. `next_action` recommends it when the last recorded round produced findings, the repairs since
   touched **more than three** sections, and no section was added or removed; it names the counted
   round in every other case, and whenever `TP_RUN_ID` is set.
4. `--reconcile --note` adds a row and leaves the round's recorded `spec_hash` byte-identical,
   proven by comparing the record before and after.
5. `--reconcile` without `--note` is a usage error, since a reconciliation whose reason is empty is
   the overwrite it exists to replace.
