# tp v0.40.0 — The gate sequence and the red gate

> Renumbered from `0.37.0.md`, then `0.39.0.md`, and split here. The release those files carried
> ported CLAUDE.md's rules outward and bundled six items; three needed a design pass and now ship as
> `spec/0.47.0.md`, and the binary advisory as `spec/0.42.0.md`. What remains is the half that was
> ready, plus the section that half was missing. `spec/0.34.0.md` is shipped and still says
> "v0.36.0" for the gate sequence; it means this file's §2.

## 1. Overview

tp's `CLAUDE.md` carries hard-won rules about how to run a cycle, every one paid for with a failed
cycle, and **none of them reaches anyone who is not this repository.** That is the same shape tp
solved once on the review side: a finding class that recurs becomes a registered mechanical check,
reviewers stop reporting it, and convergence gates on it. v0.33.0 proved the pattern works on
process rules too — "track `spec-coverage` separately" was a CLAUDE.md instruction for one release
and became `spec_coverage_clean_rounds` in the next, at which point nobody had to remember it.

This release takes the two rules about the quality gate. They belong together because the second
needs the first: a procedure for a red gate is worth much less when the gate cannot say which half
of it went red.

## 2. `quality_gate` as a sequence

**The rule being mechanized:** *verify the gate with separate exit codes, never a `&&` chain.*

A gate written as `go test ./... && golangci-lint run` reports one exit code for two questions. When
it fails, the output does not say which half failed, and a red linter behind a green test suite is
easy to misread. In v0.31.2 exactly that hid a failing `golangci-lint` for four audit rounds.

`quality_gate` accepts an array of `{name, cmd}` entries alongside today's string form. tp runs each
entry in order, records each entry's exit code and duration, and stops at the first failure. The
recorded evidence names the failing entry. The string form stays valid and unchanged, so no existing
task file moves.

This also makes the gate's composition visible: an operator adding a mutation-score or race check is
adding a named entry, not extending an opaque shell string. `spec/0.49.0.md` §8 is the worked
example of that composition and depends on this section shipping first.

## 3. What a unit does when the gate is red

**The rule being mechanized:** *a red gate is a bounded investigation with a named exit, never the
unit's own judgement call.*

`spec/0.30.0.md` §8.2 already has `tp brief` carry the resolved gate command verbatim together with
the rule that a red gate is never closed over and that `--skip-gate` is a human decision.
`spec/0.35.0.md` §4.2 adds the record: a gate failure under `TP_UNIT_KIND` writes `last_failure`, and
`tp brief` surfaces it so a fresh unit sees the wall the previous attempt hit.

So the unit is handed the wall and the prohibition with nothing between them. The failure that
produces is not a wrong fix — it is a **loop**: an agent with no bound and no exit re-runs the gate,
edits, re-runs, and burns the unit. Reset-native execution makes the loop expensive rather than
merely annoying, because the context that learned why the gate was red dies with the unit and the
next attempt restarts from `last_failure`'s one-line summary.

The brief gains an ordered procedure. Every step is a rule this repository already paid for; the
contribution is the sequence and the bound, not the steps.

1. **Isolate, then reproduce.** Run the failing entry alone rather than the gate — §2 is what makes
   the entry a name, and under the string form this step is the manual split §2 exists to remove. A
   failure that does not reproduce is a finding about the gate, not about the change.
2. **Observe the failure before editing it.** CLAUDE.md's rule — prove a fix by running it, not by
   reading it — read in the other direction: a fix accepted without watching the failure first
   proves nothing, and an assertion never seen failing may be a tautology.
3. **Re-run the entry, then the whole gate.** Both, in that order; §2's v0.31.2 case is a red half
   standing behind a green one.
4. **Exit by name when the investigation ends.** It ends when the next step would be a user-only
   decision, or when an attempt produces no new information about the failure — a condition rather
   than an attempt count, because a count is exactly the gameable proxy Non-Goal 2 rejects. The exit
   itself is context-dependent and the brief must resolve which one applies: under `tp run` the unit
   records `tp escalate --decision skip-gate` and the run stops with `stop_reason: escalation`, while
   outside a run `tp escalate` is a usage error by design (`internal/cli/escalate.go`) so the
   interactive fallback's exit is a hand-back — stop, leave the task `wip`, report the wall and let
   `last_failure` carry it forward. A procedure that names a command exiting 2 on the path the unit
   is on is worse than no procedure.

The procedure is short and always emitted, because it belongs where the prohibition already is: a
"never close over this" with no stated alternative is the shape that produces the loop. The
`last_failure` specifics — which entry failed, its exit code, the previous attempt's summary — are
emitted only when a record exists, which is already how `tp brief` carries that key.

**Why this one is not a check.** §2 turns a rule into something tp can measure. This one cannot be:
whether an investigation was systematic is not observable from its output, and every proxy
considered — attempt count, diff size — is the shape Non-Goal 2 rejects. What tp can do instead is
put the procedure and its exit in front of a unit that has lost the previous attempt's context,
every time. A rule living in a prompt or in a `CLAUDE.md` does not survive the reset; the brief does.

## 4. Non-Goals

1. **No enforcement of §3.** The procedure is text in a brief. The only hard behaviour this release
   adds is §2's stop-at-first-failure, which is the gate's own semantics rather than a fence on the
   unit.
2. **An audit-repair surface check.** "A repair that introduces a new abstraction belongs to the next
   version" is a real rule and among the most expensive ones tp has learned, but every mechanical
   proxy considered so far — diff size, new symbol count — is gameable and punishes legitimate
   repairs. It stays prose until someone finds a predicate that is not. §3 step 4 leans on this
   Non-Goal by name, and `spec/0.49.0.md` §9 records the same shape for execution evidence.
3. **A test-first gate.** "Write the test, watch it fail, then fix" is CLAUDE.md's rule and §3's
   step 2 states it, but it stays a procedure. Enforcing it means detecting test-before-code from a
   diff or a commit order, and a unit that must pass such a gate learns to pass that gate rather
   than to write the test — v0.34.0 §7.1 is this repository's own instance of a mechanism that
   suppressed for eight rounds what it was meant to measure. It is also the only item considered
   here that would change what a green close means. Not without a measurement showing the gate
   catches more than it teaches.
4. **The test-file fence, the example-table lint rule and the unexecutable-split warning.**
   `spec/0.47.0.md`. All three needed a design pass, which is why they are not here.
5. **The binary advisory.** `spec/0.42.0.md`.
6. **Mutation score as a gate entry.** `spec/0.49.0.md` §8 composes into §2's array form and ships
   after it.

## 5. Tests

1. A `quality_gate` array runs entries in order, stops at the first failure, and records per-entry
   exit codes; the string form behaves exactly as before.
2. Recorded evidence names the failing gate entry.
3. A gate whose second entry fails is distinguishable from one whose first does, in the recorded
   evidence and in `last_failure` — proven by mutating which entry fails and observing the record
   change, since a single "the gate failed" string would pass a weaker assertion either way.
4. `tp brief` carries §3's procedure with the exit resolved for the unit's context — `tp escalate`
   under a run, the hand-back outside one — and the `last_failure` specifics appear only when a
   record exists.
