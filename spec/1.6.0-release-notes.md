# tp v1.6.0 — what to start next, on a large plan

> The release notes for the `v1.6.0` tag. Publishing is a separate, human decision.

v1.5.0 connected the epic graph to the work. Piloted on a large graph, it answered what can start but
not what to start first, opened every milestone of a track one after another, and asked the operator
for conditions long before anything waited on them alone. The decision and the fixes are
`spec/1.6.0.md`, with the findings in `spec/backlog/epics-progress-field.md`; the cycle is recorded in
`spec/1.6.0-measurements.md`.

## New

- **Opening order.** The graph's `opens_after` maps a milestone to the milestones it opens after, of
  any track; `[]` keeps a family of siblings in one track, always open. A milestone without an entry
  opens after the previous one of its track, as before. `tp epic set opens_after=<json>` writes the
  map, and it and `set milestones=` report `ancestry_changed`, each milestone whose transitive openers
  the write moved. `tp epic status` reports each milestone's effective `opens_after` and `waiting_on`.
- **Lint for opening order.** `opens-after-cycle` (error) and `partial-parallel`, a milestone whose
  epics depend on an earlier milestone of its track it does not open after: a warning, or `info` when
  the milestone's own entry chose it. `info` is a new severity, counted in neither total.
- **What to start next.** Each `tp epic ready` item carries `downstream`: `longest_chain`,
  `dependents`, `dependents_open` and `dependents_by_milestone`, over the not-done work that waits on
  it. Ready items are ranked by it. `tp epic status` gains a top-level `critical_path` over the whole
  graph.
- **Actionable conditions.** A condition is listed under `operator` only when it is `actionable`: its
  dependencies done, its milestone open, and nothing depends on it or some dependent that can move
  waits on conditions alone. Each item carries `actionable`.
- **One gate at a time.** `tp epic set gates.<m>.threshold=<text>`, `gates.<m>.deferrable=<ids>` and
  `gates.<m>.members=<ids>` edit one gate and carry its `met`.
- **`tp epic status --open`** reports the open milestones only.
- **`--epic <id>` on `tp resume`, `tp next` and `tp ready`** works on the epic's bound task file: its
  only one, or the only one not at `release`; otherwise exit 4 naming them.
- **A richer export.** `tp epic export` `epics[]` items carry `title`, `milestone`, `condition`,
  `downstream`, `actionable` (conditions), `held_by` and `blocked_by`. A slice without `key.json`
  reports the key derived from its recorded rounds.
- **`estimate_total`** on each roll-up row, over every task of the epic's bound files.
- **A refused write names its rule's fix.** A write refused for a lint error carries one hint per
  broken rule.

## Changed

- `share_done` counts work epics only, and so do the status counts and `throughput`; done conditions
  are reported apart as `counts.conditions_done`. A milestone holding conditions reads a different
  share than under v1.5.0, with the export still at `version: 1`.
- `tp epic status` JSON is an object, `{critical_path, milestones}`, with `critical_path` at the top
  level; the export's `milestones` stays the list.
- `tp epic ready --all` lists every undone condition of a tracked milestone, each with `actionable`,
  rather than only those whose dependencies are done.
- Every milestone has a gate unit in an epic review, its block listing the effective members and
  `opens_after`. A milestone without a `gates` entry gains a review unit, and a gates entry without
  explicit members or an `opens_after` entry changes its block: each is asked once after the upgrade.
- `no-dependencies` does not fire on a condition.
- `gate-member-outside-milestone` reads `deferrable` too.
- A milestone two tracks name (a `duplicate-name` error) takes its first place for openness.
- `tp epic status --compact` leaves each milestone's `critical_path` out (the top-level one carries
  the chain), and `--compact` leaves `dependents_by_milestone` out of ready items on `tp epic ready`
  and `tp epic status`.
- `tp epic status --open --milestone <m>` on a closed milestone exits 4 naming what it waits on.
- A milestone no track holds is refused naming the milestones the tracks do hold.

## Fixed

Found by the release's own diff review.

- A task file's path, in `--epic`'s refusal and in every write payload's `file`, is relative to the
  cwd with symlinks resolved on both sides, so it works as `--file` from a symlinked cwd (macOS
  `/tmp`, `/var`) or a subdirectory; it climbed to `/` and back before.
- `--epic` with an id the graph does not hold says so, and the refusal of several candidates lists
  them as a `candidates` array too.
- An `opens_after` list of `null`, which read as "opens after nothing", is refused exit 2 by
  `tp epic set` and `tp epic import`.
- A write that shrinks an `opens_after` cycle passes, as one shrinking an epic cycle does; refusals
  print no empty `[]` for a finding that names no epic.
- A `gates` key naming no milestone and a `tag_checks` `provided_by` naming no epic get their own
  refusal hints instead of the edge's.
- An epic a gate lists both in `members` and in `deferrable` is the new lint error
  `gate-member-deferrable`, so the one-gate writers refuse it.
- `ancestry_changed` lists only milestones the graph held before the write (a first write prints
  `[]`), and `tp epic milestone add` and `tp epic import` report it too.
- Dependency cycle members get one shared, order-independent `downstream`.
- `tp epic export` carries the top-level `critical_path`, and `tp epic status` `blocked[]` items carry
  `held_by`, as export's epics do.
- `tp next` and `tp resume` blocked only by conditions name the operator's
  `tp epic done <c> --evidence` (`operator: {decision: "epic-done", commands}`).
- `partial-parallel` agrees in number with its dependents, and `tp epic status` / `tp epic ready`
  help name the new keys.
