# tp 1.24.0 — measurements

## The cycle

v1.24.0 answers one field report: a requesting project drove a long implement phase by hand, one
task at a time, while `run_max_parallel` already existed. The report was not taken at face value;
each item was checked against tp's own history and state first.

**Why the session did not know.** The plugin cache the session loaded held the 1.16.1 skill, whose
text has no mention of `run_max_parallel`; the 1.23.0 skill has eight. The plugin had been updated
the same day, but an update reaches only a new session. Two changes follow:

- SKILL.md says so where the update command is given.
- `tp resume` reports `plugin_stale` when the plugin root the hook passes is older than the binary.
  Verified end to end: a v1.23.0 build on `PATH`, run through the cached 1.16.1
  `hooks/session-start.sh` with `CLAUDE_PLUGIN_ROOT` set, prints the field; it is absent when the
  variable is unset or the versions match. `CLAUDE_PLUGIN_ROOT` is not set in an agent's own shell,
  so the field speaks at session start and after a compact or clear, not mid-session. It would not
  have rescued the reporting session; it names the cause at the next reset.

**What the report counted.** A read-only count of the requesting project's log since 2026-11-17
20:00 gave 494 commits, 89 of them `chore(tp)`, 53 of those closes. Under `builtin` a close is
already amended into its code commit (REFERENCE, "Close checkpoint"); the separate commits came
from closing by hand outside that path. So "fold the close into the code commit" was already there.

**What changed.**

- **Write-time parity.** `tp add`, `tp add --bulk` and `tp set` refuse any task `tp validate` would
  reject (one function, `TaskSchemaErrors`, behind both); the entry check refuses every per-task
  schema error rather than a subset.
- **Docs.** SKILL.md, README and `tp run --help` describe implement batches as they run.
- **`waiting`.** A wip task can say what it waits on; every close and `tp reopen` clear it, and
  `tp resume`'s guidance names it after a reset. The guidance also says when only a chain remains, so
  a cap above 1 will run one unit at a time.
- **`worktree_setup_cmd`.** A Decision, below: a fresh worktree lacks the main tree's ignored build
  output, and the fixture shows cold batches losing to cap 1.
- **Deferred.** The report's remaining items are in `spec/undecided.md`, "The parallel field
  report's deferred items", each with the condition that would reopen it.

**The Decision's review.** Two reviewer roles, two rounds. Round 1 returned 7 driver findings and 13
on contract and docs; all were applied, each code fix test first. Round 2 returned no high or medium driver
finding and one medium docs finding (the note's fence sentence), fixed in 3fdc83ad. Its low
findings stand as known limits:

- a pending signal during a failed setup reports `interrupted`, reversing the stop precedence;
- a signal in the short gap after the last setup's watch ends does not stop the batch from spawning;
- a successful setup's backgrounded children are not killed, and on Windows only the shell is.

## Worktree setup

This section measures the criterion in `spec/backlog/worktree-setup.md` §2. It was run on 2026-11-18
on macOS (APFS), in a temporary project outside the repository, with a binary built from the
branch after review round 1's code fixes. Every later commit on the branch changes docs, scripts,
or names a function's results without changing what it does.

**What this proves.** The fixture proves the mechanism, not the gain in a compiling project. Its
gate stands in for a build: the "cache" is synthetic, and so is the cost of rebuilding it. The real
figure belongs to the requesting project's own run.

### Reproducing it

The fixture and the driver are committed:

- `scripts/measure-worktree-setup.sh`, which builds the fixture and runs the measurement;
- `scripts/measure-worktree-setup-unit.sh`, the scripted unit it spawns.

The numbers below came from:

```bash
go build -o /tmp/tp-dev/tp ./cmd/tp
OBJS=200 TASKS=6 REPS=3 scripts/measure-worktree-setup.sh /tmp/tp-dev/tp "$(mktemp -d)"
```

The setup is `/bin/cp -cR`, a copy-on-write clone on APFS. Elsewhere, set `SETUP_CMD` to the
platform's equivalent.

### Fixture

- **The repository.** A git repository with one spec and six open tasks, each with its own
  `touches`. `commit_strategy` is `builtin`.
- **The cache.** `cache/` is git-ignored and holds 200 objects of 1 MB.
- **The gate.** `quality_gate` is a shell script:
  - with no cache, it rebuilds one: per object it hashes 4 MB from `/dev/urandom` and writes 1 MB;
  - with a cache, it only reads `cache/obj*` and hashes the result.
- **The setup.** `worktree_setup_cmd` is `/bin/cp -cR "$TP_MAIN_ROOT/cache" .`.
  `git status --porcelain --untracked-files=normal` stayed empty after every setup.
- **The units.** The fake runner's batched write records a pending close without running the gate,
  so it would not exercise the worktree gate this section is about. The units are therefore
  spawned through the same seam (`TP_RUNNER_SEAM`) by the scripted unit. It sleeps 1 s for the
  agent's time, commits one file, and closes through the real `tp done <id> --commit <sha>`. So the
  gate runs where the unit runs, and again on the main branch at integration unless the gated tree
  is reused.
- **Each run** starts from a fresh copy of the template, with `run_max_units` set to 6. Every run
  stopped with `cap-units`, and all 6 tasks were done in every run.

### Gate time, 3 runs each (seconds)

| Where | Runs | Median |
|---|---|---|
| main tree, warm | 2.08, 0.87, 0.48 | **0.87** |
| fresh worktree, no setup (cold) | 9.09, 8.21, 7.42 | **8.21** |
| fresh worktree after the setup: the gate | 2.05, 0.61, 0.67 | **0.67** |
| fresh worktree: the setup itself (`cp -cR`) | 0.06, 0.04, 0.03 | 0.04 |

The first run of each row was slower; the machine was still warming its file cache.

With the setup, the worktree gate takes **0.77×** the main tree's warm gate, or **0.82×** counting
the setup itself. The criterion allows at most 1.5×. The clone is 12.3× faster than the cold path,
so the note's failure condition ("no faster than the cold path") did not occur.

### Wall time for the six tasks, 3 runs each (seconds)

| `run_max_parallel` | Setup | Runs | Median | Setups recorded: count, range of per-run totals (s) |
|---|---|---|---|---|
| 1 | none (no worktree is made) | 13.28, 12.39, 13.52 | **13.28** | 0 |
| 2 | `cp -cR` | 9.58, 9.74, 12.35 | **9.74** | 6, 0.18–0.25 |
| 3 | `cp -cR` | 8.46, 8.47, 9.62 | **8.47** | 6, 0.18–0.31 |
| 2 | unset (cold worktrees) | 33.19, 33.13, 36.63 | 33.19 | 0 |
| 3 | unset (cold worktrees) | 30.10, 29.67, 28.92 | 29.67 | 0 |

The count and the totals come from the run state's `setups`. The wall time is the wall clock
around `tp run`, setup time included.

With the setup, cap 2 and cap 3 each finish in less wall time than cap 1, which is the criterion's
second half. Without the setup, the same batches take 2.5× (cap 2) and 2.2× (cap 3) as long as
running alone. That is what the v1.23.0 Limits paragraph's advice ("keep `run_max_parallel` at 1")
was protecting against.

Cap 1 gets no setup by design: a unit that runs alone runs in the main tree, which already holds
the ignored files. Cap 3 over six tasks is two batches of three, so every task still got a setup.

The wall-time gain over cap 1 is modest: 27% at cap 2 and 36% at cap 3. The fixture's units are 1 s
of sleep plus a gate under a second, and the integration gates on the main branch run one at a
time. A project whose units take minutes would see the parallel share dominate. That is the
requesting project's figure to measure.

**The earlier run.** Before review round 1, the same fixture was measured with the pre-fix binary.
That run differed in two ways: the setup ran in the worktree root rather than in the project
directory, which is the same place in this fixture, and there was no `HEAD` check. It gave the
same verdict:

- gates: 0.48 s warm, 6.82 s cold, 0.54 s after the setup;
- wall time: 9.94 s at cap 1, 8.05 s at cap 2 and 7.49 s at cap 3 with the setup;
- without the setup: 31.42 s at cap 2 and 27.97 s at cap 3.
