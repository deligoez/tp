# tp 1.24.0 — measurements

## Worktree setup

The criterion of `spec/backlog/worktree-setup.md` §2, measured on 2026-11-18 with the branch's own
binary (`go build ./cmd/tp`) on macOS (APFS), in a temporary project outside the repository.

**What this proves.** The fixture proves the mechanism, not the gain in a compiling project. Its
gate stands in for a build: the "cache" is synthetic, and so is the cost of rebuilding it. The real
figure belongs to the requesting project's own run.

### Fixture

- **The repository.** A git repository with one spec and six open tasks, each with its own
  `touches`. `commit_strategy` is `builtin`.
- **The cache.** `cache/` is git-ignored and holds 200 objects of 1 MB.
- **The gate.** `quality_gate` is a shell script:
  - with no cache, it rebuilds one. Per object it hashes 4 MB from `/dev/urandom` and writes 1 MB;
  - with a cache, it only reads `cache/obj*` and hashes the result.
- **The setup.** `worktree_setup_cmd` is `/bin/cp -cR "$TP_MAIN_ROOT/cache" .`, a copy-on-write
  clone. `git status --porcelain --untracked-files=normal` stayed empty after every setup.
- **The units.** The fake runner's batched write records a pending close without running the gate,
  so it would not exercise the worktree gate this note is about. The units are therefore spawned
  through the same seam (`TP_RUNNER_SEAM`) by a scripted unit. It sleeps 1 s for the agent's time,
  commits one file, and closes through the real `tp done <id> --commit <sha>`. The gate therefore
  runs where the unit runs, and again on the main branch at integration unless the gated tree is
  reused.
- **Each run** starts from a fresh clone of the template, with `run_max_units` set to 6, so every
  run stops with `cap-units` once the six tasks are done. All 6 were done in every run.

### Gate time, 3 runs each (seconds)

| Where | Runs | Median |
|---|---|---|
| main tree, warm | 0.60, 0.47, 0.48 | **0.48** |
| fresh worktree, no setup (cold) | 6.82, 6.98, 6.45 | **6.82** |
| fresh worktree after the setup: the gate | 0.54, 0.54, 0.57 | **0.54** |
| fresh worktree: the setup itself (`cp -cR`) | 0.04, 0.04, 0.05 | 0.04 |

The gate in a set-up worktree takes **1.13×** the main tree's warm gate, or **1.21×** with the setup
counted. The criterion is at most 1.5×. The clone is 12.6× faster than the cold path, so the
note's falsifier ("no faster than the cold path") did not trip.

### Wall time for the six tasks, 3 runs each (seconds)

| `run_max_parallel` | Setup | Runs | Median | Setups recorded (count, total s) |
|---|---|---|---|---|
| 1 | none (no worktree is made) | 9.94, 9.85, 11.31 | **9.94** | 0 |
| 2 | `cp -cR` | 7.74, 8.70, 8.05 | **8.05** | 6, 0.16–0.20 |
| 3 | `cp -cR` | 7.64, 7.49, 7.13 | **7.49** | 6, 0.14–0.15 |
| 2 | unset (cold worktrees) | 31.42, 30.95, 32.69 | 31.42 | 0 |
| 3 | unset (cold worktrees) | 27.73, 27.97, 29.22 | 27.97 | 0 |

The rows come from the run state's `setups` and the wall clock around `tp run`. With the setup, cap 2
and cap 3 each finish in less wall time than cap 1, setup time included. That is the criterion's
second half.

Without the setup, the same batches take three times as long as running alone. That is what the
v1.23.0 Limits paragraph's advice ("keep `run_max_parallel` at 1") was protecting against.

Cap 1 gets no setup by design. A unit that runs alone runs in the main tree, which already holds the
ignored files.

The wall-time gain over cap 1 is modest, at 19% and 25%. The fixture's units are 1 s of sleep plus a
0.5 s gate, and the integration gates on the main branch run one at a time. A project whose units
take minutes would see the parallel share dominate. That is the requesting project's figure to
measure.
