# tp v0.42.0 — The binary check

> Split from the release that ported CLAUDE.md's rules outward, where it was one of six items. It
> depends on nothing else in that release and needs no design pass, which is why it ships on its
> own. The content is unchanged.

## 1. Overview

**The rule being mechanized:** *dogfood the in-progress binary, never the lagging release.*

During self-development the tp on `PATH` lags the repository and hides the behaviour under
development. The rule has been in `CLAUDE.md` since v0.28.0 and is violated by anyone who forgets to
rebuild. It generalizes beyond this repository: any project developing a tool with tp hits the same
trap.

## 2. The advisory

When tp runs inside a repository that is tp itself — detected by the presence of a task file whose
spec version is newer than the running binary's version — it emits one advisory naming the mismatch
and the rebuild command. One advisory per invocation, silenced by `--quiet`, never an error.

## 2a. A second advisory of the same shape: the task file is not tracked

**The rule being mechanized:** *a converged cycle's task file is the record of its closure evidence,
and tp knows whether git can recover it.*

A field cycle lost one. That project's convention names a task file `spec/upcoming-<name>.tasks.json`
until release and renames it to `spec/<version>-<name>.tasks.json` at the tag, and its `.gitignore`
carries `spec/upcoming-*.tasks.json` — so before the rename the file exists only on disk. It was
deleted mid-session on a wrong scope note, had never been tracked, and is therefore not in git
history: fourteen tasks' closure evidence and commit SHAs are unrecoverable.

**The naming convention is not tp's and this section does not adopt it.** tp ships no `upcoming-`
prefix and no such `.gitignore` line; that is one project's local practice, and a check keyed on the
prefix would help only projects that share it. What generalizes is the loss: tp resolves the active
task file's path on every invocation, and whether git tracks that path is one `git ls-files` away.
`internal/cli/report.go` already counts untracked files and `config_extract.go` already shells to
`git status --porcelain`, so no new capability is being proposed — only that the answer reach the
operator before the file is gone rather than after.

**The advisory names the loss, not the state, and this distinction is the whole section.** A first
draft specified it as §2's twin — "the task file is untracked", one per invocation. The operator who
lost the file read that draft and refuted it, and the refutation is not a wording preference:

> I did not lose the file because I was confused about whether git had it. I executed my own wrong
> scope note saying to delete it. "Task file is untracked" does not contradict "this file should be
> deleted" — if anything it *supports* it. An untracked file reads as disposable.

The two propositions are orthogonal, so a state advisory can fire correctly and change nothing. And
§2's per-invocation cadence actively works against this one: that session ran tp dozens of times, so
habituation would have been complete long before the moment it mattered. The form that contradicts
the deletion is a count:

```
task file spec/upcoming-x.tasks.json is untracked — 14 closed tasks and 27 commit SHAs exist only on disk
```

**Fired once, where the convention applies.** Not every invocation: when the audit converges, or when
`tp resume` reports `phase: release` — which is the step that operator was at when the file went. tp
already has everything the sentence needs at that moment: `engine.PhaseRelease` exists and `resume`
reaches it, and the resolved task file carries the closed-task count and `commit_shas` (measured on
this repository at v0.36.0's release: 24 closed tasks, 47 SHAs). Still silenced by `--quiet`, still
never an error, still never a refusal.

**So §2 and §2a share a subject and not a cadence, and merging them would be wrong.** §2's advisory
is about a condition that is true for a whole session and cheap to ignore correctly. §2a's is about a
single irreversible moment. A per-invocation warning is right for the first and is the failure mode
of the second.

**What is deliberately not proposed here.** The same report asked for a tp command that performs the
release-time rename. That is a workflow verb, and it would bake one project's naming convention into
the tool. The operator agreed on re-reading and did not ask for it back; their own ranking put it
"clearly below the reframed advisory". If it is ever wanted, the shape that avoids the objection is
one that takes the destination from the caller rather than deriving it — `tp mv <spec> <path>` doing
a `git mv` plus a post-check that the file is now tracked, so tp supplies the guarantee and no
convention.

**One caveat carried forward rather than dropped**, because it is the reporter's own: this is
retrospective self-report about a decision that cannot be rerun. The orthogonality argument does not
depend on that — it is a claim about two propositions, checkable by reading them — but the assertion
that the reframed sentence *would* have stopped the deletion is unfalsifiable and is recorded as
testimony, not measurement.

## 3. Not the same check as `spec/0.35.0.md` §6.1, and the two must not be merged

That one asks whether `tp` is present on `PATH` and new enough for the *plugin*, compares against
`plugin.json`'s version, runs in the `SessionStart` hook and **fails**. This one asks whether the
running binary is older than the *spec being developed*, runs inside tp on any invocation, and
**advises**. A freshly installed release developing the next version's spec passes the first and
trips the second, which is exactly the case worth catching.

## 4. Non-Goals

1. **Never an error.** The advisory changes no exit code, in any command, under any condition.
2. **No merge with the plugin's version check.** §3 states why; merging them would make one of the
   two wrong for its own case.
3. **No rebuild.** tp names the command; it does not run it.
4. **No detection beyond the version comparison.** A repository that is not developing tp, or a
   binary at or ahead of the spec version, sees nothing.

## 5. Tests

1. The advisory fires once on a version mismatch, is silenced by `--quiet`, and never changes an
   exit code.
2. A binary at or ahead of the newest task file's spec version emits nothing.
3. The advisory and `spec/0.35.0.md` §6.1's hook check disagree on the case §3 names — a freshly
   installed release developing the next version's spec — with the hook passing and this advisory
   firing. That case is the reason both exist, so it is the one a test must contain.
