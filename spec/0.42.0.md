# tp v0.42.0 — `unresolved_findings` reports what is open

> **This file is decisions.** §1.1 is a first-person reproduction: this field misled the orchestrator
> of this repository during v0.37.0's release, who reported its number to the operator and had to
> retract it. The defect is not that the number is wrong. It is that the number is **inverted**.

## 1. Overview

`tp resume` and `tp run` carry `next_action.payload.unresolved_findings`, the count a driver reads to
decide whether a phase has work left. `roundPayload` (`internal/engine/resumepayload.go:95-110`)
computes it as:

```go
for _, r := range rows {
    if findingResolvedStatus(r) != "wontfix" {
        unresolved++
    }
}
```

Every row in the last round counts unless it was explicitly dispositioned `wontfix`. **On the audit
phase every row is a checklist item, and a PASS row is a row.** So a clean audit round of 106 items
reports 106 unresolved findings, and recording a disposition is the only thing that ever decrements
it.

### 1.1 The measurement

v0.37.0's audit round 7 — the round the release shipped on, `spec-coverage` 74/74, two clean rounds
running:

| | |
|---|---|
| rows recorded | 106 |
| rows with `resolved.status: "wontfix"` | 3 |
| **`unresolved_findings` reports** | **103** |
| rows that are actually non-`PASS` | **3** |

```
python3 -c "import json; rows=[json.loads(l) for l in
open('spec/.tp-review/0.37.0/audit-round-7.ndjson') if l.strip()];
print(len(rows), sum(1 for r in rows if (r.get('resolved') or {}).get('status')=='wontfix'),
      sum(1 for r in rows if r.get('status')!='PASS'))"
```

**The 103 is exactly the set of PASS rows.** All three genuinely open findings had been dispositioned,
so the field excluded every row that was a finding and included every row that was not. It did not
approximate the answer; it returned its complement.

**This is a driver-facing field.** `tp run` branches on it, and the number it reads on a converged
round is two orders of magnitude off in the direction that says *keep working*.

## 2. `unresolved_findings` counts open findings

A row counts as unresolved when **it is a finding** and **it is not closed**:

- **It is a finding.** On the audit phase, `status` is not `PASS`. On the review phase every recorded
  row is a finding, so this clause is vacuously true there and the count is unchanged — which is why
  the field looked correct for as long as review was the only phase reading it.
- **It is not closed.** `resolved.status` is absent, or is a value other than `wontfix` **or**
  `fixed`.

**`fixed` joins `wontfix`, and its omission is the second half of the defect.** The corpus carries
1,406 rows with a `resolved` object: **1,308 `fixed` and 98 `wontfix`**. Today thirteen closed
findings out of fourteen still count as open, so the one disposition an operator is most likely to
record is the one that changes nothing.

**An unrecognised `resolved.status` counts as open.** A row saying `status: "maybe"` is not evidence
of closure, and the direction that keeps a driver working is the safe one — the same fail-closed rule
`AuditRowsClean` already applies to a severity it cannot grade.

**The row's own `status` decides whether it is a finding; `resolved` decides whether it is closed.**
Keeping the two independent is what makes a dispositioned FAIL and an undispositioned PASS both
representable, and collapsing them is how the current field came to mean neither.

## 3. The payload says what it counted

`unresolved_findings` gains two siblings in the same payload: **`rows_recorded`** and
**`findings_closed`**, the round's total row count and the number of finding rows carrying a
recognised disposition.

**A bare count cannot be sanity-checked, and this one went unchecked for five releases.** `103` looks
plausible beside a round of unknown size and impossible beside `rows_recorded: 106`,
`findings_closed: 3`. The two extra integers are already in hand at the moment the loop above runs.

**They are reported, not gated.** Nothing branches on them; they exist so a reader — human or driver —
can tell a large round from a broken count.

## 4. Non-Goals

1. **No change to what `resolved` means or who writes it.** `{evidence, resolved_at, status}` stays
   as recorded; this release only stops ignoring the `status` it already carries.
2. **No repair of past payloads.** `unresolved_findings` is computed on read, so every recorded round
   reports correctly the moment this ships. Nothing stored is rewritten.
3. **No convergence effect.** `clean`, `consecutive_clean` and `--check` do not read this field and
   are untouched. This release changes what a driver is told, not what a round is.
4. **No new workflow field, no new disposition vocabulary.** `fixed` and `wontfix` are the two values
   the corpus contains; inventing a third here would be inventing a case with no data behind it.
5. **The review phase's count does not change.** Every review row is a finding, so §2's first clause
   admits all of them, and the second clause only ever removes rows an operator explicitly closed.

## 5. Tests

Every row derives from a numbered decision, names the artifact it depends on, and names a mutant that
must fail it.

| # | from | assertion | the mutant that must fail it |
|---|---|---|---|
| 1 | §1.1 | v0.37.0's round 7 as a fixture — 106 rows, 3 non-PASS, all 3 dispositioned — reports **0**, not 103 | the shipped `!= "wontfix"` loop, which returns 103; this test must be watched failing against `HEAD` first |
| 2 | §2 *finding* | an audit round of N PASS rows and zero findings reports 0 for every N | count rows rather than findings, which makes the number a function of checklist size |
| 3 | §2 *fixed* | a non-PASS row with `resolved.status: "fixed"` does not count | keep `wontfix` as the only closing value, leaving 1,308 of the corpus's 1,406 dispositions inert |
| 4 | §2 *unknown* | a non-PASS row with `resolved.status: "maybe"` **does** count | treat any present `resolved` object as closure, so a malformed disposition silently retires a real finding |
| 5 | §2 *independence* | a PASS row with no `resolved` and a FAIL row with `resolved.status: "fixed"` both report 0, and a FAIL row with neither reports 1 | derive one from the other, which cannot represent both cases at once |
| 6 | §2 *review* | a review round's count is byte-identical before and after this release | apply the PASS filter to review rows, which have no `status` field and would all be dropped |
| 7 | §3 | the payload carries `rows_recorded` and `findings_closed` alongside, and they are consistent with the round file | emit them from a second read of the round, which can disagree with the count they are meant to explain |

**Row 1 is the acceptance and is the round this project shipped on.** Using the real recorded round
rather than a constructed one is deliberate: the fixture that would have caught this defect is the one
the author of the defect did not build, and the corpus already contains it.
