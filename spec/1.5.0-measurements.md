# 1.5.0 — measurements and interview record

The sidecar of `spec/1.5.0.md`: the interview, the evidence behind its decisions, and the cycle as it
runs. Grounding does not grade this file.

## Interview (operator)

- **Scope:** everything in `spec/backlog/epics.md` §4–§8, the view's critical path, throughput and
  estimate-versus-actual included.
- **Round caps:** `review_max_rounds` 4, `audit_max_rounds` 5.
- **Binding:** one epic per task file; an epic may have several files.
- **Conditions:** the operator asked why triggers and metric gates should stay outside tp when the
  work they gate is tracked in tp. The requesting project answered that its file of them existed only
  because tp could not hold them; it holds no time series, no measurements and no history, and most
  thresholds are unwritten placeholders. tp still runs no command at read time.
- **The how is ours.** The requesting project proposed modelling every trigger and every threshold
  as a condition epic, marked and done with evidence, refused while a configured placeholder remained.
  Reviewed against its own goal — a ready list that answers "what is next", and gates it reads as
  milestone transitions — three changes were chosen by the operator:
  - **Gates open milestones.** A gate that only reports leaves the ready list showing every unblocked
    epic of every milestone; the project answers "what is next" from milestone order and the gate, so
    a milestone is open only when every earlier milestone of its track has a green gate.
  - **Exit thresholds live on the gate.** A threshold that closes a milestone is decidable only once
    the milestone's work is done; as a condition epic it would wait on the operator from the
    milestone's first day. On the gate it is recorded as met after the members are done. Conditions
    stay for what opens work.
  - **A structural rule replaces the placeholder token.** An empty threshold or condition cannot be
    met, and a met record keeps the threshold it was judged against, so a later edit shows. A project
    leaves an unwritten threshold empty instead of configuring its own placeholder text.

- **After ground round 1** (operator and the requesting project, before the first review round):
  every milestone has a gate, an implicit one being its work epics; a gate without `members` takes
  them by default and conditions are never default members; optional trigger-waiting work is listed
  `deferrable`. The operator added the export as the contract a later `tp dashboard` reads
  (`spec/backlog/dashboard.md`): versioned, with bound files' phases and loop states and every epic
  review slice with its key.
- **A consequence the ground round measured:** most of this repository's own shipped task files are
  not at `release` (several sit in `audit` with an exhausted budget). An epic bound to one of them is
  never `done`; that is the definition chosen, one oracle of finished, not a defect.

## Field evidence (the requesting project, in shape only)

- The plan is a graph of several hundred epics with no spec written yet; epics were cut to one
  deliverable each, so one spec per epic is expected, and a tightly coupled family may share a
  design note.
- About a quarter of the epics are taskless (formations, filings, agreements, field work); their
  completion is recorded nowhere today.
- The requesting project's triggers open both single epics and whole milestones of a track; its
  metric thresholds close milestones and are met once, a later dip belonging to a business
  dashboard. Every one of them fits a condition epic: a root the waiting epic depends on, the first
  member of a milestone, or a gate member of the milestone it closes.
- Its priorities for the view, in order: the ready and blocked lists, counts and share done per
  milestone with the gate's state, the remaining critical chain, plan versus actual, throughput.
- Parallel agents already run review rounds; two agents claiming one epic is a foreseen risk, and a
  lost update between two writes in one session was observed in the v1.4 pilot.

## The review loop's end

The loop ran its cap of four rounds; the findings went 21, 11, 10, 9, with no high or critical left in
round 4. Round 4's nine were decided at the cap in `spec/1.5.0-corrections.md` and dispositioned
`wontfix` naming their decision. The registered `spec-growth` check failed at the end: repairs in rounds
2 and 3 added thirty body lines past round 1. Each added line closes a finding where two correct
implementations would have diverged (a `wip` task under a block, `tp done` bypassing it, the direct
dependency rule, the estimate chain, the fence's removals); none adds a requirement. The operator
accepted the growth and approved `tp import --force` over the failing check, and the audit is the
verification round that follows, on code.

## Implementation and audit

The 29 imported tasks were implemented one fresh subagent per task (pairs of small dependent tasks
shared one), test-first, each closed with `tp done --commit`. The audit ran over every file the
release changed, named explicitly: the default picks the first fifty, and `--affected-from-tasks`
sees only each task's closing commit. `spec-coverage` was clean in all seven rounds and no round had
a FAIL. The other roles found one defect per round in the code the previous round's repair had
written: the batch `tp done` refusal shape, the block judged before the lock, an all-done file
reported as blocked, an unparsable task file skipped as if absent, `tp claim` judging the file before
the id, `tp commit`'s implicit claim bypassing the block, and a failed closure stage losing the
commit it had made. The operator raised the cap from five to seven, one round at a time, so a round
re-read each repair made at the cap; round seven was clean in every role.
