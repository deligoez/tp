# tp v1.1.0 — The spec follows tested behaviour

> The release notes for the `v1.1.0` tag. Publishing is a separate, human decision.

## What changed

**A review finding carries its evidence into the record.** `evidence` is a required, non-empty,
free-text key on every review finding, beside `severity`, `finding` and `location`: what was run or
read to reach the finding — the command and its output, the query, the probe that was built, or the
artifact and line that was read. tp does not look at what the text says. It records that a reviewer
named what it did; whether that text bears on the claim beside it is the open *evidence contract* in
`spec/undecided.md`.

Those four keys are one required set, and **both gates enforce it through one predicate**:

- `tp review --merge` **skips** a row missing one, naming the key in the stderr warning it already
  wrote for the other three, and counts the row as skipped.
- `tp review <spec> --record` **refuses the whole file**, and names **every** offending line in one
  exit rather than stopping at the first.

Both decide *missing or empty* after `strings.TrimSpace`, so a whitespace-only value is a missing key
at either gate — for `severity`, `finding` and `location` as much as for `evidence`.
`skills/tp/REFERENCE.md` names exactly which characters that set contains, and which do not count.

A five-row file, one row per missing required key plus one whose `evidence` is three spaces:

```
$ tp review spec.md --record bad.ndjson
{"error":"line 1: missing required field severity; line 2: missing required field finding; line 3: missing required field location; line 4: missing required field evidence; line 5: missing required field evidence","code":1,"hint":"every row in the --record NDJSON carries a non-empty severity, finding, location and evidence: fix or drop each line the message names"}
```

Exit 1, and no round file is written. The refusal is raised after the spec is hashed and before any
round state is touched, so an unreadable spec still exits 3, and `--record`'s existing rules for a
pre-resolved row — `fixed` aborts, `wontfix` needs its own evidence — keep their own messages. The
parity is over the required-field set only and does not reach those rules.

## A refused `--merge` no longer touches its `-o` path

`tp review --merge` now **creates no file at `-o`, and modifies no file already there, when it exits
non-zero**. It writes through a temporary file in the destination's own directory and renames on
success, so a failed write leaves neither a truncated `-o` nor the temporary beside it.

Three runs against one `-o` path, the merge refusing each time because one input parsed no row:

| run | before | after |
|---|---|---|
| `-o` absent | no file | still no file, exit 1 |
| `-o` holds a seed line | `sha256 33b32dce…` | `sha256 33b32dce…`, exit 1 |
| an input file is missing | seed present | seed byte-identical, exit 3 |

This closes a real hazard rather than tidying an output path — see *Upgrading* below.

## The emitted prompts name the key

Every command that emits a finding contract now names `evidence` on the JSON object line a reviewer
copies: `tp review <spec>`, `tp review <spec> --role <r>`, `tp review <spec> --perspective code-audit`,
`tp review <spec> --perspective regression`, and `tp review <spec> --verify`. Beneath the line each
format states that the four keys are required and non-empty, and says what happens at each gate to a
row that omits one.

Two of those changed by more than a key:

- **The code-audit format also gained `location`.** Its eleven keys named `file` and `line` but no
  spec anchor, so adding `evidence` alone would still have produced rows `--merge` skips and
  `--record` refuses.
- **`tp review <spec> --verify` gained an output contract it did not have.** Its prompt previously
  ended in prose — *respond with one JSON finding per line* — and carried no object line at all, so a
  verifier had nothing to copy. It now ends in the same four-key object line as the panel roles.

## Rounds recorded before this release still load

The requirement is enforced when a round is **recorded**, never when one is **loaded**.
`tp review --status`, `--report`, `--regression`, `tp resume` and `tp audit` all read recorded rounds
through `engine.LoadRoundRows`, which validates nothing, and the clean/converged computation reads the
same way. A pre-`v1.1.0` round file whose one undispositioned `high` row carries no `evidence` reports
`consecutive_clean: 0` at exit 0, and exits 1 under `--check`, exactly as it did before.

That matters here more than it usually would. Of the recorded review rows in this repository's own two
round corpora, **90 of 4,059 carry an `evidence`** — all ninety from this release's own three review
rounds. Every earlier round would be refused at record; none is refused at load.

```bash
python3 -c 'import json,glob,os,re
tot=ev=0
for p in ("spec/.tp-review/*/*.ndjson","spec/backlog/.tp-review/*/*.ndjson"):
    for f in glob.glob(p):
        if not re.search(r"review-round-\d+\.ndjson$", os.path.basename(f)): continue
        for l in open(f):
            if not l.strip(): continue
            r=json.loads(l); tot+=1
            e=r.get("evidence")
            if isinstance(e,str) and e.strip(): ev+=1
print(tot, ev)'
```

Both globs are required: the unreleased specs' round directories live under `spec/backlog/`.

## Upgrading: one danger this release creates, and its remedy

**A findings file written before `v1.1.0` fails the merge gate on every row.** Merging one round file
copied out of this repository's own `v1.0.0` corpus:

```
$ tp review --merge role-old.ndjson -o out.ndjson
warning: skipping incomplete line (missing evidence) in role-old.ndjson      (×46)
… "inputs":[{"path":"role-old.ndjson","parsed":0,"skipped":46}], "merged_count":0
{"error":"no line parsed in role-old.ndjson: every content line was skipped, so that input contributed nothing to the merge","code":1,…}
```

Exit 1, 46 of 46 rows skipped, and no `out.ndjson`. That refusal is correct. **The danger is what a
shell does with it.** A merge chained into `--record` with `;` runs the record step whatever the merge
did, and a `>` redirect creates the target file *before* the merge starts — so the record step reads a
**zero-byte** file, which is exactly how a converged round reports itself. Run end to end on a spec
nobody had reviewed:

```
$ sh -c 'tp review --merge role-old.ndjson > merged.ndjson; tp review spec.md --record merged.ndjson'
… record exit 0
$ # again
$ tp review spec.md --status --check ; echo $?
0
```

Two zero-byte records declare convergence on a review that never happened.

**The remedy is to re-emit the round's findings with `evidence`**, not to work around the gate. Ask
the roles again — the prompts now name the key — or add the field to the rows by hand. Do not reach
for `--force`, and do not delete the gate's inputs.

**Two things in this release reduce the blast radius, and neither removes it.** `--merge` refusing to
touch `-o` means the `-o` form of that chain now walks into `--record` with the file *absent*, which
exits 3 rather than recording a clean round; and `skills/tp/SKILL.md` and `skills/tp/REFERENCE.md` now
tell you to write the chain with `&&` and `-o` rather than `;` and `>`. The `>` redirect above defeats
both, because the shell, not tp, creates that file.

## Also in this release

- **`skills/tp/SKILL.md` gains four rules on what a spec is about**, under *What a spec is about
  (v1.1.0)*. They came from a survey of how other tools and communities write and review
  specifications, checked against what the `v1.0.1` cycle measured, and they are the reason this
  release is named as it is:
  - a sentence that would have to change if the implementation changed is not spec;
  - the reviewed document is a decision record, and behaviour is verified by executing rather than by
    reading;
  - a repair subtracts before it adds;
  - a review round ends at its cap by design, not only by failure.

  They landed in the tree at commit `4914215f`, before this spec's first grading round. What the
  release does with them is **distribute** them: they reach a user at the tag, not at that commit.
  The same commit bumped `.claude-plugin/plugin.json` to `1.1.0`, so **the manifest bump precedes the
  tag** and no bump is outstanding at release time.
- **`skills/tp/SKILL.md` gains a pre-review build rule** at the head of Step 2: a spec that changes a
  validation rule, a gate or a record schema has its minimal change built and the full suite run
  outside the repository before the first counted round, with packages printing `FAIL … [build failed]`
  counted separately from `--- FAIL:` lines, because they emit no such line. That total is the
  release's real size, and decomposition gives the fixture migration a task of its own that the
  gate-changing task depends on.
- **`skills/tp/REFERENCE.md` no longer contradicts the release.** Its *Measuring whether a second model
  earns its cost* recipe and its *Finding `class` and Report* contract both stated the superseded
  required-field set as present fact; the contract now separates the four keys both gates require from
  `role` and `class`, which no gate requires.
- **The `review-record` unit command chains with `&&`.** `[ -f X ] || tp review --merge … -o X && tp
  review <spec> --record X` — the `(A || B) && C` precedence keeps the retry path that protects the
  dispositions `review-resolve` accumulates in `merged.ndjson`, while a refused merge now ends the
  unit at its own diagnosis.
- **The suite's finding fixtures were migrated first.** Every review-finding fixture fed to either
  gate carries all four non-empty keys; that migration was its own task, and the task that changed
  either gate depended on it.

Derived at `a2a2a953`: the release's sixteen tasks closed across 23 commits touching 48 files, 46 of
them under `internal/` and two the skill documents.

```bash
python3 -c 'import json,subprocess
d=json.load(open("spec/1.1.0.tasks.json"))
shas=[s for t in d["tasks"] for s in (t.get("commit_shas") or [])]
files={l for s in shas for l in subprocess.run(["git","show","--name-only","--format=","--no-ext-diff",s],capture_output=True,text=True).stdout.split() }
print(len(shas), len(files))'
```

## What this release deliberately did not change

`spec/1.1.0.md` §4 fences the audit phase out of this release; the audit side of the acceptance
channel is `spec/backlog/a-finding-can-leave-an-audit-round.md`. Three consequences are known
limits, not oversights, and each was re-checked at the tag:

- **`tp audit --merge` still writes `-o` before it refuses.** A refused audit merge over a single
  unparseable input exits 1 and leaves a zero-byte file at that path — the review-side hazard above,
  still live on the audit side.
- **The audit output contract names no `evidence`.** `outputContractInstruction`, shared by all four
  auditor prompts, stamps `role`, `location`, `class`, `severity` and `status`. Audit rows carry
  `evidence_file` and `evidence_lines` already and are unaffected by §2's required set.
- **`tp run`'s emitted record brief still chains with `;`**, for both phases. On the review side that
  is now harmless — the refused merge leaves no file and the record step exits 3 — but the emitted
  string and the documented one differ, and on the audit side the leftover is still there to be
  walked into.

Nothing in ground changed. There is no `kind` label on findings and no `evidence_kind`: the field is
free text, for the reasons under *Alternatives considered* in `spec/1.1.0.md`. tp does not verify the
evidence, and `tp import --force` at a cap stop is unchanged and still the operator's decision.
