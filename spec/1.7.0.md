# tp v1.7.0 — reviewing and editing a large epic graph

> Decision track. Source: `spec/backlog/epic-review-at-scale.md` (a field sweep of `tp epic review`,
> in shape only). All eight items are taken, by the operator's decision.

The epic layer gains an any-of dependency, an atomic multi-row graph write, batch review across
slices, a cross-slice report, a direct tag check, a bounded context for the phase-economist role,
stdout for merge output, and an operator grant for one verification round on a stale slice past its
cap. Two changes are not additive: an epic review role's output path (§1) and the export's version
(§7).

## 1. Role output path

A role's output path in `tp epic review` is an absolute path in the slice's inbox,
`<state dir>/inbox/<role>-r<N>.ndjson`, the same in the prompt and in `output_path`; inside a
`tp run` unit it stays the round directory's. Emitting a round removes any inbox file of that round,
so a file left by a discarded emission is never recorded as the new one. `.tp/.gitignore` ignores the
inboxes. The plugin's write-deny hook lets exactly that name through, for any writer, when the
physical path is that name too, and still refuses every other path under the state directory. Spec
review and audit keep the relative form. Rejected: a `--findings-dir` flag (every call must carry
it); a path in system temp (gone after a reboot); letting the hook pass any `.ndjson` under the state
directory (round files would become hand-editable).

## 2. Merge to stdout

`tp review --merge … -o -` and `tp audit --merge … -o -` write the merged NDJSON to stdout and, for
`-o -` only, the summary to stderr, whatever the terminal; a merge that exits non-zero writes nothing
to stdout. It is for a pipe: a redirect into a file still loses the guard that `-o <file>` keeps,
so SKILL.md's "always `-o`, never `>`" stands. Rejected: a hint naming the temporary-file cause (it
explains the failure and offers no route).

## 3. Classes across slices, and direct tag checks

`tp epic review --report`, a new mode, takes `--all` or `--milestones` and lists each class with the
slices, rounds and distinct epics it was raised on. It suggests no mechanisation: epic review has no
registered checks to retire a candidate, and its routes to one — a lint rule, a `direct` tag check —
are the operator's. A tag check may say `"direct": true`: every carrier then needs a plain direct
dependency on the provider, never one reached through other epics or through a group, even a group
holding the provider. Rejected: `tp review`'s `mechanize_candidates` rule (nothing in epic review
retires it, and overlapping slices count one observation twice).

## 4. The phase-economist's context

A graph role's `context` may be `neighbours-brief`: each dependency as its full block, each dependent
as its id, title, milestone and its edge into the asked unit with that edge's why. The shipped
phase-economist uses it; a project with an ejected corpus keeps its own copy until it edits it.
Rejected: a size cap (what a role sees would depend on graph order); a summary of every block (the
other two roles' findings rest on dependency acceptance text).

## 5. Batch review

`--milestones <csv>` and `--all` emit each slice's round in one payload, `{"slices": [<emission>…]}`,
with `--role` applying to each; for emission `--all` means every tracked milestone. The graph is read
once and every slice prepared before any slice writes state; a slice that cannot emit — done, at or
past its cap, or failing — is listed under `skipped` with its reason, and the rest still emit.
`--status` with either flag, where `--all` means every slice directory, reports one row per slice
with its key, round, state, open counts, `grantable` and `next_action`; `--check` exits 0 only when
every slice's own `--status --check` would. Rejected: a shell loop documented in SKILL.md.

## 6. One atomic graph write

`tp epic apply <ndjson>` applies rows in order to one graph, lints the after-state once against the
before-state, and writes all or nothing; a refusal names each error's payload lines. Rows:

    {"op":"add", "epic":{…}}                                  replace by id, as --bulk
    {"op":"link", "from":…, "to":… | "any_of":[…], "why":…}
    {"op":"unlink", "from":…, "to":… | "any_of":[…]}
    {"op":"set", "id":…, "field":…, "value":…}              an epic field, as tp epic set <id>
    {"op":"set", "field":…, "value":…}                      a graph key (milestones, opens_after,
                                                             gates.<m>.<field>, tag_checks)
    {"op":"remove", "id":…, "force":bool}

Rows apply in file order, so of an unlink and a link of the same edge the last one stands. The only
failure at a row is a subject absent at that row — the `from` of a link or unlink, the `id` of a set
or remove; every reference inside a row, and every other check, waits for the one lint of the
after-state. A remove and a later add of one id keep its records, as an add that replaces does. It
prints the writers' payload, `ancestry_changed` included; `--dry-run` prints it and each row's action
and writes nothing; `--if-revision` refuses a graph that moved; under `tp run` it escalates as
`other`, like every graph writer. Records (done, claim, gate --met) and import are not rows.
Rejected: linting only the final state of `--bulk` (it cannot carry links, unlinks or sets).

## 7. Any-of dependency

A `depends_on` entry may name a group instead of an epic:

    "depends_on": [{"any_of": ["A", "B"], "why": "either decision opens the API"}]

A group is satisfied when one member is done; until then it holds its epic as one dependency.

- A group has two or more distinct members and one why; a member may be a condition or work. A
  one-member group, a group beside a plain edge to one of its members, and two groups with one
  member set are `any-of-shape` errors, so a writer refuses them rather than storing them.
- Milestone order: a group is a `later-milestone-dependency` only when every member is in a later
  milestone of its epic's track; `partial-parallel` counts it only when every member is in that
  milestone. Any member closes a dependency cycle.
- Waiting: a group makes a gate wait only when every member waits on an opening that waits on that
  gate — each member through its own opening if need be — so it closes a wait cycle only when no
  member can be done first. `gate-held-by-condition` names a group, "one of {A, B}", only when every
  member is an undone condition outside the gate's milestone.
- Actionability: where a rule asks whether an epic waits on conditions alone, an unsatisfied group
  counts as a condition when any member is one.
- A member is moot when it is undone, every group naming it is satisfied, no plain edge names it,
  and no gate holds it. A moot epic leaves the critical path, actionability and the downstream of
  everything; the export marks it `moot: true`. A moot epic a gate still holds stays the operator's
  to defer or remove.
- A tag check's provider counts as a dependency through a group only when every member is the
  provider or depends on it, by the same rule at every level.
- Downstream: while a group is unsatisfied its epic, and what depends on it, count in each member's
  downstream; once one member is done it leaves the others'. Counts over several epics count each
  dependent once.
- Critical paths go through the member with the shortest remaining chain.
- The export moves to `version: 2`, since a `depends_on` entry may now carry no `id`. Its `epics[]`
  keep `blocked_by` and `held_by` as epic ids and add `blocked_by_any_of` and `held_by_any_of`, one
  list of member ids per unsatisfied group, and `blocked` and `held` booleans, so no consumer has to
  combine lists to know; status adds the same two lists. A blocked task file adds
  `blocked_by_any_of` beside `blocked_by_epics`, and its operator action lists each group's records
  as alternatives.
- `tp epic link <from> --any-of <csv> <why>` and `tp epic unlink <from> --any-of <csv>` write a
  group; linking a member set the epic already has replaces that group's why, as a plain link does,
  and a different set is a new group. `tp epic remove --force` on a member drops its group when the
  member is done, since the group was satisfied, and otherwise drops the member; a group left with
  one member becomes a plain edge, and a group that then repeats a plain edge or another group is
  dropped as implied.

Rejected: a third condition whose acceptance says "A or B" (tp cannot read it); a separate
`depends_on_any` key (a reader that misses it starts the epic early); treating sibling milestones as
unordered (it would change `later-milestone-dependency` for every plain edge).

## 8. One verification round past the cap

`tp epic review <slice> --grant-round` lets a slice that is at or past `review_max_rounds` and stale
emit and record one more round; it is refused unless both hold, a recorded round spends it, and it
is given one slice at a time. Under `tp run` it exits 2 and the unit records
`tp escalate --decision grant-round`. `next_action` on such a slice names the grant before the
project cap, and `--status` marks it `grantable: true`. Rejected: a cap keyed per slice (a standing
setting where the need is one round).

## Non-goals

- k-of-n groups, nested groups, any-of on gates, `opens_after` or tag providers; a lint for a group
  that only widens another.
- Changing spec review's or audit's output path.
- Truncating any prompt by size.
- Records or import inside `tp epic apply`.
- Batch `--record` or `--grant-round` across slices.
- `neighbours-brief` in regression rounds, where only changed units are asked.

## Decided with the operator

1. The export moves to `version: 2` (after review: a `depends_on` element without an `id` retypes a
   documented key, and the version rule bumps for that).
2. The shape rule is `any-of-shape`, an error: fewer than two members, both or neither of `id` and
   `any_of`, a member repeating a plain edge, two groups with one member set.
3. A group's operator action is `choices: [[cmdA, cmdB]]` beside `commands`.
4. `tp epic apply` takes `remove` rows.
5. The granted round follows the ordinary carry rules, with no special prompt.
