# tp v1.7.0 — reviewing and editing a large epic graph

> Decision track. Source: `spec/backlog/epic-review-at-scale.md` (a field sweep of `tp epic review`,
> in shape only). All eight items are taken, by the operator's decision.

The epic layer gains an any-of dependency, an atomic multi-row graph write, batch review across
slices, a cross-slice report, a direct tag check, a bounded context for the phase-economist role,
stdout for merge output, and an operator grant for one verification round on a stale slice at its
cap. Every change is additive except one default: an epic review role's output path (§1).

## 1. Role output path (the one non-additive change)

A role's output path in `tp epic review` is an absolute path in the slice's inbox,
`<state dir>/inbox/<role>-r<N>.ndjson`, the same in the prompt and in `output_path`; inside a
`tp run` unit it stays the round directory's. The plugin's write-deny hook lets exactly that name
through, for any writer, and still refuses every other path under the state directory. Spec review
and audit keep the relative form. Rejected: a `--findings-dir` flag (every call must carry it, and
the default still writes into the working directory); a path in system temp (a later `--record`
cannot find it after a reboot); letting the hook pass any `.ndjson` under the state directory (round
files would become hand-editable).

## 2. Merge to stdout

`tp review --merge … -o -` and `tp audit --merge … -o -` write the merged NDJSON to stdout and the
summary to stderr, whatever the terminal; a merge that exits non-zero writes nothing to stdout.
Rejected: a hint naming the temporary-file cause (it explains the failure and still offers no route).

## 3. Classes across slices, and direct tag checks

`tp epic review --report` with `--all` or `--milestones` reports each class across every slice's
recorded rounds, and `mechanize_candidates` by `tp review`'s rule, a round of any slice counting as a
distinct round. A tag check may say `"direct": true`: every carrier then needs a direct dependency on
the provider, not one reached through other epics or through a member of an any-of group. Rejected:
a new threshold for cross-slice candidates (the review rule already reads "two rounds").

## 4. The phase-economist's context

A graph role's `context` may be `neighbours-brief`: each dependency as its full block, each dependent
as its id, title, milestone and its edge into the asked unit with that edge's why. The shipped
phase-economist uses it; a project with an ejected corpus keeps its own copy until it edits it.
Rejected: a size cap (what a role sees would depend on graph order); a summary of every block (the
other two roles' findings rest on dependency acceptance text).

## 5. Batch review

`--milestones <csv>` and `--all` (every tracked milestone) emit each slice's round in one payload,
`{"slices": [<emission>…]}`, with `--role` applying to each; a slice that cannot emit (done, at its
cap) is listed under `skipped` with its reason. `--status` with either flag reports every slice: one
row per slice with its key, round, state, open counts and `next_action`; `--check` exits 0 only when
every slice is done. Rejected: a shell loop documented in SKILL.md (the round trips the field paid).

## 6. One atomic graph write

`tp epic apply <ndjson>` applies rows in order to one graph, lints the after-state once against the
before-state, and writes all or nothing; a refusal names each error's payload lines. Rows:

    {"op":"add", "epic":{…}}                                  replace by id, as --bulk
    {"op":"link", "from":…, "to":… | "any_of":[…], "why":…}
    {"op":"unlink", "from":…, "to":… | "any_of":[…]}
    {"op":"set", "id":…, "field":…, "value":…}              an epic field, as tp epic set <id>
    {"op":"set", "field":…, "value":…}                      a graph key (milestones, opens_after,
                                                             gates.<m>.<field>, tag_checks)
    {"op":"remove", "id":…, "force":bool}

Rows apply in file order, so an unlink and a link of the same edge leave the last one's effect; a
row naming an epic that a later row adds fails; lint errors in an intermediate state do not.
`--dry-run` prints each row's action, the lint delta and `ancestry_changed` and writes nothing;
`--if-revision` refuses a graph that moved, as the other writers do; under `tp run` it escalates as
`other`, like every graph writer. Operator records (done, claim, gate --met, import) are not rows.
Rejected: linting only the final state of `--bulk` (it cannot carry links, unlinks or sets).

## 7. Any-of dependency

A `depends_on` entry may name a group instead of an epic:

    "depends_on": [{"any_of": ["A", "B"], "why": "either decision opens the API"}]

A group is satisfied when one member is done; until then it holds its epic as one dependency.

- A group has two or more distinct members and one why, and repeats no plain edge or other group of
  its epic; a member may be a condition or work. A one-member group, a group beside a plain edge to
  one of its members, and two groups with one member set are `any-of-shape` errors, so a writer
  refuses them rather than storing them.
- Milestone order: a group is a `later-milestone-dependency` only when every member is in a later
  milestone of its epic's track; `partial-parallel` counts it only when every member is in that
  milestone. Any member closes a dependency cycle.
- Waiting: a group makes a gate wait on a milestone's opening only when every member does, so it
  closes a wait cycle only if every member is in it. `gate-held-by-condition` names a group, "one of
  {A, B}", only when every member is an undone condition outside the gate's milestone.
- A tag check's provider counts as a dependency through a group only when every member is the
  provider or depends on it.
- Downstream: while a group is unsatisfied its epic, and what depends on it, count in each member's
  downstream; once one member is done it leaves the others' downstream and actionability. Counts over
  several epics count each dependent once.
- Critical paths go through the member with the shortest remaining chain.
- `tp epic export` and status keep `blocked_by` and `held_by` as epic ids and add `blocked_by_any_of`
  and `held_by_any_of`, one list of member ids per unsatisfied group, and a `blocked` and a `held`
  boolean on every epic, so no consumer has to combine lists to know; a blocked task file adds
  `blocked_by_any_of` beside `blocked_by_epics`, and its operator action lists each group's records
  as alternatives.
- `tp epic link <from> --any-of <csv> <why>` and `tp epic unlink <from> --any-of <csv>` write a
  group; linking a member set the epic already has replaces that group's why, as a plain link
  does, and a different set is a new group. `tp epic remove --force` on a member drops it from the
  group, and a group left with one member becomes a plain edge.

Rejected: a third condition whose acceptance says "A or B" (today's workaround: tp cannot read it); a
separate `depends_on_any` key (a reader that misses it starts the epic early, where an unknown entry
inside `depends_on` keeps it blocked); treating sibling milestones as unordered (it would change
`later-milestone-dependency` for every plain edge).

## 8. One verification round past the cap

`tp epic review <slice> --grant-round` lets a slice that is at `review_max_rounds` and stale emit
and record one more round; it is refused unless both hold, and a recorded round spends it. Under
`tp run` it exits 2 and the unit records `tp escalate --decision grant-epic-round`. `next_action` on
such a slice names the grant before the project cap, and `--status` marks it `grantable: true`.
Rejected: a cap keyed per slice (a standing setting where the need is one round).

## Non-goals

- k-of-n groups, nested groups, any-of on gates, `opens_after` or tag providers.
- Changing spec review's or audit's output path.
- Truncating any prompt by size.
- Operator records inside `tp epic apply`.
- Batch `--record` across slices: record is where a bad file should stop that slice alone.
- `neighbours-brief` in regression rounds, where only changed units are asked.

## Decided with the operator

1. The export keeps `version: 1`: no existing graph changes shape, the fields are additive, and the
   `blocked`/`held` booleans answer the question a consumer of `blocked_by` alone would get wrong.
2. The shape rule is `any-of-shape`, an error: fewer than two members, both or neither of `id` and
   `any_of`, a member repeating a plain edge, two groups with one member set.
3. A group's operator action is `choices: [[cmdA, cmdB]]` beside `commands`.
4. `tp epic apply` takes `remove` rows.
5. The granted round follows the ordinary carry rules, with no special prompt.
