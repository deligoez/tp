## The corpus carries no evidence key

Every recorded review row in this repository, under both `.tp-review` roots, counted at the tag of
`v1.0.1`:

```bash
bash -c 'python3 -c "
import json,glob
files=sorted(glob.glob(\"spec/.tp-review/*/review-round-*.ndjson\")+glob.glob(\"spec/backlog/.tp-review/*/review-round-*.ndjson\"))
rows=[json.loads(l) for f in files for l in open(f) if l.strip()]
print(\"files\",len(files),\"rows\",len(rows),\"with_evidence_key\",sum(1 for r in rows if \"evidence\" in r))
"'
```

Run at `4602f081` (the `v1.0.1` tag): 174 files, 3,969 rows, 0 with an `evidence` key. That zero is
why §6 row 10 exists: the record-time rule must not be applied on load, or every recorded cycle
becomes unreadable.

The ground phase already records a tier per row; its vocabulary at the same commit, over both roots:

```bash
bash -c 'python3 -c "
import json,glob,collections
files=sorted(glob.glob(\"spec/.tp-review/*/ground-round-*.ndjson\")+glob.glob(\"spec/backlog/.tp-review/*/ground-round-*.ndjson\"))
rows=[json.loads(l) for f in files for l in open(f) if l.strip()]
print(collections.Counter(r.get(\"tier\") for r in rows).most_common())
"'
```

Five named tiers plus rows with none. `read` and `run` are the two most common by a wide margin and
the two the `v1.0.1` cycle's refutations actually turned on; the review-side field keeps those two.

## What the `v1.0.1` cycle measured

All of it is in `spec/1.0.1-measurements.md`; the sections this release rests on, by title:

- *What implementation did that five review rounds could not* — the table of corrections made by
  implementing tasks, each from a run, against five grading rounds that rewrote one section four
  times. This is the measurement behind decision 4 (the spec follows tested behaviour).
- *The cap stop, and why the release goes to implementation unconverged* — review findings rose from

- *The audit arc, and the round that subtracted* — three audit repairs replaced a claim with a claim

  prose alone survived the next round. Behind decision 1 (evidence at record).

## The survey

Run on 2026-09-07 with a fixed budget of searches; each source is listed with the concrete rule taken
from it. Nothing below is quoted in the spec.

**Spec-driven development tools.**

- GitHub spec-kit, `spec-driven.md` and the spec template — the reviewed spec must "avoid HOW to
  implement (no tech stack, APIs, code structure)"; code-level decisions live in a separate
  `implementation-details/` artifact that is not the reviewed document; ambiguities are marked inline
  and the gate is that none remain, not a round count.
  https://github.com/github/spec-kit/blob/main/spec-driven.md
- AWS Kiro feature specs and best practices — three files (`requirements.md` in EARS, `design.md`,
  `tasks.md`), one human approval after each, and a task-level *Sync Files* step after
  implementation; the design file does describe structure before code exists, which the field report
  below names as the over-specification that made specs rigid.
  https://kiro.dev/docs/specs/feature-specs/ · https://kiro.dev/docs/specs/best-practices/ ·
  https://dev.to/aws-builders/what-i-learned-using-specification-driven-development-with-kiro-pdj
- Tessl — one spec per code file, an API section in code, a `[@test]` link per requirement; the only
  surveyed tool that keeps spec and code in sync, and it does so by linking tests, not by prose.
  https://docs.tessl.io/use/spec-driven-development-with-tessl
- Martin Fowler's team on the three tools — observed over-specification, duplication with existing
  code, and authors "frequently confused when to stay on the functional level".
  https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html

**Executable specifications.**

- Cucumber, *Writing better Gherkin* — "describe the intended behaviour of the system, not the
  implementation"; the per-sentence test *will this wording need to change if the implementation
  does?* https://cucumber.io/docs/bdd/better-gherkin/
- Adzic, *Specification by Example* (InfoQ excerpt) — "automating validation without changing
  specifications"; "watch out for descriptions of how the system should work".
  https://www.infoq.com/articles/specification-by-example-book
- Python doctest and rustdoc documentation tests — a document's examples are executed to keep it
  "up to date", not reviewed. https://docs.python.org/3/library/doctest.html ·
  https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html

**Design-document and RFC cultures.**

- Rust RFC template and the libs-changes guide — unresolved questions are split into those resolved
  before merge and those "expected to resolve through the implementation"; "nor must an
  implementation PR perfectly match the RFC text"; RFCs favour immutability.
  https://rust-lang.github.io/rfcs/libs_changes.html
- PEP 1 — an accepted PEP "is considered a historical document rather than a living specification";
  expected behaviour is maintained elsewhere. https://peps.python.org/pep-0001/
- Oxide RFD 1 — states from prediscussion to committed; a days-long discussion window, author decides
  when to merge. https://rfd.shared.oxide.computer/rfd/0001
- Google design docs (Ubl) — context and scope, goals and non-goals, the design with trade-offs,
  alternatives; not "an implementation manual".
  https://www.industrialempathy.com/posts/design-docs-at-google/

**Requirements engineering.**

- INCOSE Guide to Writing Requirements v4 (rules summarised at reqi.io) — R31 *solution free*; every
  requirement verifiable, with a stated method. https://reqi.io/articles/incose-requirements-quality-42-rule-guide
- ISO/IEC/IEEE 29148:2018 — the individual-requirement characteristics include *appropriate*
  ("avoids implementation details") and *verifiable*; the standard's own definition of *requirements
  verification* is a check of form, distinct from verifying the system.
  https://www.reqview.com/doc/iso-iec-ieee-29148-templates/

**Review loops of language-model agents.**

- *Adversarial Review* (arXiv 2608.18167) — a reviewer–critic loop underperformed a single reviewer
  until each finding had to cite code that confirms or refutes it; "agents can optimize for agreement
  rather than correctness". https://arxiv.org/html/2608.18167
- *Refute-or-Promote* (arXiv 2604.19049) and *Benchmarking Agentic Review Systems* (arXiv
  2606.19749) — refute-first staging for precision; more peer agents can yield diminishing or
  negative returns. https://arxiv.org/html/2604.19049 · https://arxiv.org/html/2606.19749v1

Nothing was found on multi-round review of *prose* specifications by agents converging or not; the
direct evidence for that is this repository's own recorded rounds.

## What the survey did not change

The backlog's order. Each surveyed practice that maps to a tp mechanism already has a backlog file —
the panel record, the checklist cap, the emit-time hash, the forced brief — and the survey supports
their subjects without changing their priority. The one practice with no file is the subject of this
release.
