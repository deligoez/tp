# 1.3.0 — measurements and provenance

Supplemental material for `spec/1.3.0.md`. The spec stands without this file. Nothing here is graded
by `tp ground`.

## Provenance

The release is the first half of `spec/backlog/epics.md`; the account it rests on is in
`spec/backlog/epics-measurements.md`. The requesting project is not named anywhere in this
repository, by its owner's decision, and none of its data is here.

## The interview, 2026-11-08

The operator confirmed the Full track and the split into two releases, and delegated the remaining
design choices. Taken on that delegation, each with the recommendation it followed:

| choice | decision | why |
|---|---|---|
| a spec's "finished" for the second release | bound to `tp resume`'s `release` phase | one oracle; `audit_clean_rounds` has no zero, so a spec without an audit is a workflow question, parked in the backlog sidecar |
| driver integration | none in this release; the loop is agent-driven like `tp ground` | a loop is bound to the driver after it has run once on a real graph, not before |
| `milestone` on every epic | required | a discovered epic still says where it belongs; the order rule needs it |
| finding location | `epic:<id>` or `gate:<m>`; an edge finding sits on its source epic | ids may hold spaces and arrows, so an `edge:a→b` form has no safe parse |
| round budgets | review 3, audit 3 | the repository's Full-track default |

## Pre-registered stop rules

Written before the first round, so a later decision to stop is read against them.

- The ground loop runs before the first counted review round and ends when `--status --check` exits
  0 and the latest round's breakdown holds no unrepaired `FAIL` or `PARTIAL`.
- Review converges at two clean rounds under `review_converge_on: blocking`, or stops at the cap of
  three. At the cap, open findings about behaviour this release creates become task acceptance and
  decomposition proceeds; a critical or high finding about a *decision* stops the cycle for the
  operator.
- When the same section fails three rounds, the problem is the design, not the text: the section is
  cut or the decision changed, never reworded a fourth time.
- The spec and this file do not grow after round 1 (`spec-growth` is registered); a repair deletes
  or narrows.

The decisions taken at the review cap are in `spec/1.3.0-corrections.md` (D1–D13).

## The audit cap raise

Audit round 3 recorded spec-coverage clean for the second round running and no `FAIL` in any round,
with one `info` finding open from two code-lens roles (a wrong refusal hint), repaired at `106ad532`.
The cap of 3 was then exhausted unconverged. Under the operator's delegation the cap was raised to 5,
so that tp's own rule, two consecutive fully clean rounds, decides the release rather than
`CLAUDE.md` rule 13's spec-conformance exception. Round 4 found a second instance of the same hint
class; after a class sweep over every `tp epic` error path the cap was raised once more, to 6.

## The ship decision

Audit round 6, the raised cap, recorded spec-coverage clean for the fifth round running and no `FAIL`
in any of the six rounds. Its one finding, from a code-lens role, was a conflicting-input case in
`tp epic add` outside the spec's surface; it was repaired at `138a7e16` and resolved `fixed`. Each of
rounds 3, 4 and 6 found one new code-lens item in turn, the pattern `CLAUDE.md` rule 13 exists for,
so the cap was not raised again: the release ships on spec conformance under rule 13, and the last
repair is covered by its test and the gate rather than by a seventh round.

## Field pilot before the tag

After the ship decision and before the tag, the operator had the requesting project run the release
candidate (a `v1.3.0-pilot.<sha>` build on its `PATH`, the plugin read from this checkout) on its own
graph, and fix what it found here before tagging. The report came back in shape only; its sizes and
ids stay where the graph lives.

- **Import and lint.** The graph imported with nothing needed dropped. `thin-why` found restating
  whys the project's own checker did not look for, all true positives; one near miss on part of a
  word led to P1. A gate keyed by the milestone it opens produced one error per member, which led to
  P2. Writers echoing every id led to P3.
- **Three review rounds over one milestone**, the third on the fixed build confirming P5–P7. The roles found missing direct edges the structural
  checker cannot see, and `regression` caught a fix that handed a requirement to epics whose
  acceptance never took it. One fresh reader wrote rows without `severity` because the contract sat
  after the context (P5); a carried gate hid its `deferrable` list (P6); per-role data on which
  findings used a dependent's block decided P7. A question about rounds that resolve every finding
  counting as clean was answered by stating the rule (P8).
- **Deferred to the second release:** an edge-level writer (`link`/`unlink`) and a multi-index
  `--resolve`; silencing `no-dependencies` per epic. Not exercised by the pilot: building a graph
  from zero through Workflow E's first steps.

## Mutation run and the tag

The release rule's mutation run (`gremlins unleash ./internal/engine --workers 4`, fresh `rsync`
copy of `6091915e`, the last commit touching code) was started before the tag and the tag did not
wait for it: the operator chose not to hold the release an hour or more for a result that cannot
block an additive feature, and the run shared the machine with a gate run, which `docs/lessons.md`
says makes it load-sensitive. Its survivors in the new epic files are input to 1.3.1.
