# tp v0.49.0 — The evidence contract

> **Pre-design.** This file states a verified problem and records the objections any mechanism must
> answer. It is not ready to decompose: §4-§7 name no field, no writer and no arithmetic, and that is
> deliberate — a first draft specified them, and an adversarial pass found each mechanism either
> impossible against the shipped code or answering an objection the draft had itself raised. What
> survived is the problem and the objections. The mechanisms are open.
>
> Renumbered twice: from `0.38.0.md` when the release order was set from measured value rather than
> authoring order, and to `0.49.0.md` when the seven pending specs were split into independently
> releasable pieces. The content did not change either time.
>
> §8 arrives from the release that ported CLAUDE.md's rules outward, where it sat alone; that
> release is now `spec/0.40.0.md` and `spec/0.47.0.md`.

## 1. The rule

**Evidence that asserts is accepted where evidence that executes was meant.** tp cannot tell the two
apart at the point it reads them, which is why none of the three sinks below has ever caught it.

| Sink | What tp means to establish | What it accepts |
|---|---|---|
| an audit checklist item | the code does what the spec says | that matching text was found near it |
| a `tp done` closure line | the criterion was met | a sentence asserting it was |
| the quality gate | the suite would catch a regression | that the suite is green |

The rule is stated here and nowhere else in this file. §3-§8 are instances of it.

## 2. Why audit is the sink that matters

Review's subject is a specification. Prose has no execution semantics, so reading is not tp's choice
of instrument there — it is the only one. Audit's subject is code, which can be run, and tp has the
auditor read it anyway.

The consequence is that **the auditor has no instrument of its own**: it reads code the implementer
wrote and reports on it. (An earlier draft added that the auditor also leans on the implementer's
green gate. That is false and was removed — `quality_gate`, `gate_passed` and `closed_reason` appear
nowhere in `audit.go`, `audit_roles.go` or `audit_schema.go`. The narrower claim is sufficient.)

**The field instance.** A tp user driving a Rust NLP project reported auditor prompts carrying

```
expected_evidence: 'search code under section "1. Amaç ve vizyon" for keywords from item text'
```

Round 1's `spec-coverage` returned 75 PASS. The same day, three of that project's critical gates
were found printing `PASS` while discarding the exit status they were meant to report. A keyword
search sees the `PASS` line; it cannot see the gate throwing the result away.

Scope this precisely, because the first draft did not: that string is **one of four**
`expected_evidence` branches (`audit_roles.go`), the fallback taken by `table_row` and `list_item`
items and by `task_acceptance` items mapping to zero files. The `files changed by task commit:
<paths>` branch is not a keyword search. The defect is in the fallback, not in every item.

What the instance does establish generally: for a class of defects, executing is **cheaper than
reading and strictly more conclusive**. Finding this by reading means noticing an absence — a missing
`set -e`, a discarded `$?`. Finding it by running means injecting one failure. The usual objection to
execution, that it costs more, is inverted exactly where it matters.

## 3. The informative experiment is the one that could have failed

An auditor that runs the happy path learns nothing the suite does not already contain — the
implementer ran that. The value is in perturbation: the boundary value, the broken precondition, the
injected failure the code claims to catch. This is mutation testing's principle (§8) applied per
audit item rather than per mutant.

This paragraph is the release's thesis and it is **not yet a mechanism**. §4-§7 are why.

## 4. Open: the generator cannot author an experiment

`expected_evidence` is produced by deterministic string templates over the section title, the item
text and a task→file map. It has no model, no knowledge of the project's test harness, and no way to
name a command. "The default becomes a command to run" is not implementable by that generator for
any spec-derived item.

The two honest branches, neither chosen:

1. **The generator gains an input** — a model call, which would be this release's largest commitment
   and one no other tp surface makes.
2. **The role prompt asks the auditor to design the experiment**, in which case this is a role-text
   change and must say so, and the checklist item stops being the unit of evidence.

Whichever is taken, it must be decidable by a task's acceptance. The first draft's escape hatch —
"where the item's shape does not yield an experiment, `expected_evidence` says so" — was not an
exception but the only reachable branch, which made the section a no-op that still cost tokens.

## 5. Open: `UNVERIFIED` has no legal place in the loop

"I could not run anything here" currently lands in `PARTIAL`, where it is indistinguishable from
"the code partly matches". A fourth verdict is the precondition for §3: demanding an experiment
without an honest way to report the absence of an instrument leaves asserting as the only way to
produce a verdict.

Four objections, all verified against shipped code, none answered:

1. **It cannot avoid counting.** `engine.AuditRowIsPass` makes every non-`PASS` row a finding and
   convergence is zero findings across two rounds. "Counts but is reported separately" does not
   remove it from the count — a codebase with un-runnable surface would never converge.
2. **It becomes an `audit-fix` unit with no honest exit.** `spec/0.35.0.md` §4.1 hands the oracle's
   fix unit every non-PASS, undisposed row, and the dispositions are `fixed|wontfix|duplicate`. All
   three are lies about an unverified row, and "still unverified" is not among them, so the row stays
   undisposed and the oracle re-returns the same unit until a cap.
3. **It is a downgrade path out of FAIL.** The draft reasoned only about UNVERIFIED absorbing
   PARTIAL. The dangerous direction is a real defect reported as "could not verify" — a verdict with
   no severity, in a separately-reported bucket, that reads as more honest than the finding it
   replaced. That is v0.34.0 §7.1's shape. Any design must make UNVERIFIED unavailable once a defect
   is observed.
4. **The row has nowhere to put it.** `audit_schema.go` requires `evidence_file` and `evidence_lines`
   for PASS and PARTIAL — both pointers into source text — and `RenderAuditCategoryText` keys
   `category` off PASS vs PARTIAL/FAIL with no cell for a fourth status.

## 6. Open: a declared evidence mode measures nothing

The first draft had each row declare `ran` or `read` and the round report the mix, claiming kinship
with §8's borrowed rule. The kinship is false and the objection is decisive: a mutation score is
computed by a third party from artifacts, while `ran` is asserted by the same agent whose assertions
this release exists to distrust. Nothing can contradict it, and a round reported 60% `ran` may be 0%.

A design that survives this has to bind the declaration to something tp can see — the row carrying a
command and its exit code, with the mode **derived** rather than declared. That is a different and
larger change than a field, and it interacts with every objection in §5.4.

**And a derived mode is only as good as the command's author.** Binding the mode to an exit code
removes the unfalsifiable declaration; it does not remove the choice of what to run. `quality_gate`
sits in `readOnlyWorkflowFields` (`internal/cli/set.go`), so a task-level gate is authored at
`tp init` and the project default only through the explicit `--project` route into `.tp/config.json`
— one committed file, reviewed like any other. A command a unit writes into its own closure evidence
has the opposite provenance: authored per close, in free text, by the agent whose assertions this
release exists to distrust. Executing it establishes that a command exited zero, which is strictly
more than a sentence and strictly less than the criterion. This is not §9's execution theatre — that
hazard is volume, one command's output pasted under every item; this one is provenance, and it
survives a command run exactly once against the criterion it is offered for.

The constraint it yields, stated as a narrowing rather than a design: **a carrier whose command
comes from a name space the unit does not author is worth more than one whose command it does.**
`spec/0.40.0.md` §2's named `{name, cmd}` gate entries are the only such name space currently
planned, so an evidence line naming an entry rather than a command is one shape this objection does
not defeat. Whether entry granularity is expressive enough for a per-criterion claim is unanswered,
and §7 is untouched either way — naming an entry still needs somewhere to put the name. (The
proposal that raised this arrived from a comparison of tp against two agent frameworks rather than
from a measurement, which is why it is recorded here as an objection and a constraint rather than as
a mechanism.)

## 7. Open: closure evidence has no per-line carrier

`engine.CountEvidenceLines` counts lines beginning `- ` and compares the count to the criterion
count. There is no line↔criterion binding to attach a kind to, `VerifyClosure` applies the rule only
at N ≥ 2 criteria so single-criterion tasks have no line at all, and `closed_reason` is one free-text
string rather than a structured row. Recording an evidence kind here means choosing a carrier — a new
task-file field, or in-band markers `CountEvidenceLines` must tolerate — and the draft chose neither.

## 8. Mutation score as a documented gate entry

*Moved from the release that became `spec/0.40.0.md`.*

A tautological or decorative test is invisible: coverage is high, the gate is green, and nothing
measures whether the suite would catch a regression. Mutation score is the available instrument. tp
ships no mutation tooling and no threshold; it documents the composition and stops there.

**It is a release gate entry, not a per-close one.** `spec/0.40.0.md` §2's `quality_gate` sequence
runs on every `tp done`, and CLAUDE.md's rule — the source of this section — says to run mutation
testing at decision points, "never while task gates are running", at roughly five minutes per
thousand mutants. On v0.35.0's own 44 tasks a per-close entry is about three and a half hours of
load-sensitive, timeout-prone gate time. Either §2 gains a per-entry trigger (`on: close | release`),
which is scope 0.40.0 does not currently carry, or this composes only at the release decision point.

**The discrimination claim needs its source named.** The moved text asserted that mutation scores
"did not discriminate between the runs it compared". That experiment is named nowhere, and in this
file a reader binds it to §2's field report, which is not it. It also reads against CLAUDE.md's own
measurement on this codebase — swept files at 96-100% efficacy, unswept at 25-78%, which is
discrimination. Either the borrowed claim is about comparing test-generation runs, in which case the
sentence must say so, or it does not hold here.

## 9. Two hazards, not one

**Execution theatre.** A requirement to attach command output is satisfied by attaching any command's
output; `go test ./...` pasted under fifty-five checklist items is keyword search with a worse token
bill. `spec/0.40.0.md` Non-Goal 2 already records the general form — every mechanical proxy
considered for "did this repair say more than it must" was gameable — and this release has not found
the predicate that is not.

**Perturbation has nowhere to happen.** §3 asks auditors to inject failures, and `spec/0.35.0.md`
§6.3 gives the audit unit a `tp-auditor` agent that "may write exactly one path" and is "denied every
other write" (test 55). §3.3 further justifies running role units *concurrently* on their being
read-only with respect to shared state. So under `tp run` no auditor can perturb anything, every row
is `read` by construction, and N auditors each building a scratch copy would dissolve the concurrency
argument. Any design owes an execution surface — a per-unit workspace in the child environment and an
amended agent definition — or must say plainly that perturbation is interactive-only.

## 10. Open: what would gate this

The first draft borrowed the replay clause now in `spec/0.43.0.md` §6. It does not transfer. That
gate works because every v0.43.0 mechanism is deterministic post-processing over rows that exist —
replay re-runs code over frozen data. §4 changes what a prompt asks a model and §6 adds a field no
recorded row contains, so no stored row can say what a differently-prompted auditor would have found.

One further fact, and it is the load-bearing one. When this section was written
`spec/.tp-review/0.35.0/` held zero audit rounds. It now holds nine — 1800 rows, recorded as that
cycle converged — so the premise that the cycle contributes nothing to its own gate is no longer
true and must be re-derived rather than repeated. What survives the correction is the clause that
actually blocks: those rows carry `role`, `item_id`, `location`, `status`, `severity`, `category`,
`evidence_file`, `evidence_lines` and `notes` — and **no `disposition`**. Audit dispositions arrive
with v0.35.0's `tp audit --resolve` but were never written during that cycle, so the manifest rule
in `spec/0.43.0.md` §6.1, which read from recorded dispositions, had no audit-side input. That
section has since been corrected against a full count of the corpus — 0 of 12,958 recorded rows
carry a disposition, review side included — and the correction is the reference to follow rather
than this paragraph's narrower audit-only finding. The corpus exists; the field the gate needed
does not.

A gate that cannot fail is worse than no gate. Naming a real one is part of this release's design
pass.

## 11. Non-Goals

1. **No verdict for the review phase.** Whatever §5 becomes is an audit-row status. Prose has no
   experiment to run.
2. **No threshold anywhere.** Neither a mutation score nor an evidence mix gates an exit code.
3. **No change to `role`, `location`, `class` or `severity`.** `status`, `evidence_file`,
   `evidence_lines` and `category` are all in scope — they are the fields the problem lives in.

Written at decomposition, and not before §4-§7 and §10 are decided. This file currently states no
