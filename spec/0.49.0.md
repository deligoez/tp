# tp v0.49.0 — The evidence contract

> **Pre-design.** This file states a verified problem and records the objections any mechanism must
> answer. It is not ready to decompose: §4-§7 name no field, no writer and no arithmetic, and that is
> deliberate — a first draft specified them, and an adversarial pass found each mechanism either
> impossible against the shipped code or answering an objection the draft had itself raised. What
> survived is the problem and the objections. The mechanisms are open.
>
> Renumbered twice: from `0.38.0.md` when the release order was set from measured value rather than
> authoring order, and to `0.49.0.md` when the seven pending specs were split into independently
> releasable pieces. The content did not change either time.
>
> §8 arrives from the release that ported CLAUDE.md's rules outward, where it sat alone; that
> release is now `spec/0.40.0.md` and `spec/0.47.0.md`.

## 1. The rule

**Evidence that asserts is accepted where evidence that executes was meant.** tp cannot tell the two
apart at the point it reads them, which is why none of the three sinks below has ever caught it.

| Sink | What tp means to establish | What it accepts |
|---|---|---|
| an audit checklist item | the code does what the spec says | that matching text was found near it |
| a `tp done` closure line | the criterion was met | a sentence asserting it was |
| the quality gate | the suite would catch a regression | that the suite is green |

The rule is stated here and nowhere else in this file. §3-§8 are instances of it.

### 1a. The same rule at the source: ask while writing

§1 is the rule at the **sink** — what tp accepts when it reads evidence. The same rule has a source
half that costs nothing and is where every instance below could have been prevented:

> **Does this claim have a specification it could be wrong about, and can I ask now?**

A value object with four named readonly fields cannot disagree with reality. A YAML reader can
disagree with YAML. A sentence asserting which function performed a load can disagree with the call
order. The first needs no probe; the other two have one available at the moment the claim is written,
and it is the *same* probe an auditor will run a round later.

**The binary in that question is not clean, and this section's own table is where it broke.**
`wrapperArgv` was first classified as modelling nothing, which is what made the axis look tidy.
Measured afterwards: its stub records `"$*"`, which joins arguments on IFS, so `go test -run "a b"`
and `go test -run a b` are recorded identically. It *does* have a specification it could be wrong
about — shell argument joining — and it survives only because this use never passes an argument
containing a space.

**The size that reading suggests is the wrong axis, and the counterexample came from the other
repository within the hour.** A first correction read this as graded — `ciRunLines` models a large
specification and touches its edges constantly, `wrapperArgv` a tiny one it never approaches — and
concluded that size is what to measure. Item 6 of the set of seven, *"cost ordering flips
`wasTruncated()`"*, rests on the push/pop accounting of a single loop, a **smaller** specification
than shell word-splitting. It was written wrong, and an auditor got it right by reading the same
fifteen lines.

That item is **verified here rather than taken as reported**, because its author supplied coordinates
instead of asking for it to be weighted on the grounds that it cost them: `tarfin-labs/event-machine`
at tag `9.20.0`, `src/Analysis/ScenarioPathResolver.php`, `bestFirst()`. The load-bearing line is that
`visited` is copied per successor and is therefore **path-local**, so the set of reachable
`(path, state)` entries is fixed by the graph and no extraction order can add or remove one; the loop
leaves a non-empty frontier exactly when that set exceeds `maxIterations`, which cost ordering cannot
change. The claim holds.

**And the tool that fetched the file got it wrong, in a way that was worth four more calls to
characterise.** Asked the four sub-claims as a checklist, a summarising model confirmed three and
answered the fourth — *does the insertion count depend on extraction order* — with "confirmed, it
depends", which is false. A first reading of that was that it had not noticed the per-successor copy.
Measured, that reading is wrong, and the real shape has a cheap mitigation:

| how the same question was asked, same file, same tool | answer |
|---|---|
| checklist of four claims, item 4 phrased *"depends on extraction order"* | **CONFIRMED** |
| checklist of four claims, item 4 phrased *"does NOT vary with extraction order"* | **CONFIRMED** |
| standalone, forced leading YES/NO, *"is it independent?"* | **YES** — correct |
| standalone, forced leading YES/NO, *"does it depend?"* | **NO** — correct, and it cites the per-successor copy |

**Both directions confirmed in the checklist format, and no file state makes both true**, which is a
proof the reading was not performed. The same model asked one question at a time, with the verdict
forced before the reasoning, answers correctly in both directions and names the exact line. So the
failure is not comprehension and not a property of the model — **it is induced by the batch-verification
format**, which invites a tick per row and supplies the direction to tick. The same run also flipped
claim 2 between CONFIRMED and REFUTED on identical wording, so instability accompanies it.

The mitigation is therefore not "do not delegate a reading". It is: **one claim per call, force the
verdict before the reasoning, and ask it in both directions — a reader that confirms both did not
read.** That test is decidable without knowing the answer yourself, which is the property that matters
when the reason for delegating is that you have not read the file. It was proposed by the reporter as
a hypothesis about sycophancy; run here, it holds as a detector while the sycophancy reading itself
turns out to be format-conditional rather than directional.

So `wrapperArgv` surviving is luck about the *use*, not safety about the *size*:

> **Size predicts whether you will bother to check, not whether you will be right.**

Small specifications are exactly as falsifiable as large ones and merely less conspicuous. The hazard
is not that they are forgiving — it is that **they do not look like specifications**, which is the
same direction as §1b's B arriving from the other side.

**What survives is not a size but a name.** Ask what the claim *rests on*, and write that down:

| the claim rests on | example |
|---|---|
| a library's documented semantics | `is_subclass_of`'s `$allow_string` |
| the caller's own code | which value reaches this parameter |
| an ordering | whether `validate()` ran before `validatePaths()` |
| a language rule | readonly classes rejecting dynamic properties; property-type invariance |
| local accounting | the push/pop balance of one loop |
| a literal at a tag | what the option text said at 9.19.0 |
| nothing | — |

**All seven prose errors of that set were classified against this and the "nothing" row came back
empty.** Every one had a nameable dependency and several are one line to write. If that generalizes —
seven is not enough to say it does — the field does more work than the answerable/not-answerable
judgement it was meant to supplement, and may replace it: **a claim that can name its dependency is
checkable by construction**, and one that genuinely cannot is the rare case worth a second look.
That recovers §1b's "no" pile without ever asking the fallible binary, which matters because a binary
judgement over a property that is *not* binary is noisy exactly where B lives.

**It sorts three phenomena, across two repositories, and the third set is what promotes it from a
rule about code to a rule about claims.**

| set | what was classified | result |
|---|---|---|
| this repository, v0.36.0's audit | 3 abstractions introduced during repair | 3/3 — the two modelling a large specification were falsified; the one modelling a tiny one survived |
| this repository, v0.36.0's audit | 8 prose findings | 8/8 — every one answerable by an open, a grep, a two-minute fixture, or one `echo` |
| a Laravel package, 6-round audit | 7 prose errors that drove the audit past its convergence rule | 7/7 — each later run by an auditor, each the same command the author could have run at write time |

The third set is disjoint from the first two and was classified by its own author against a criterion
derived from the others, which is the only reason the sorting is worth anything: the abstraction
version and the prose version were not the same evidence re-cut.

**What this changes about where the rule lives.** Stated as advice about audit repairs it reads as a
constraint on refactoring, and the prose case only arrives if a reader notices the analogy. Stated
here it is one rule with three instances, and `spec/0.46.0.md` §7's abstraction table becomes an
example rather than the statement.

**What it does not do.** It is a question, not a mechanism, and this release's §4-§7 are the reasons a
mechanism is hard. It sorts retrospectively on 18 points and has never been used prospectively by
anyone.

**The one piece of evidence that is not those 18 points**, and the reason to take it seriously at all:
CLAUDE.md already carries its narrowest instance — *never assert a quantifier you did not count; tie
the claim to a named artifact, or let a guard enforce it* — arrived at independently, from five
rounds of falsifying the same shape of sentence, and by a worse route. A special case reached without
the general rule is better evidence that the general rule is right than any amount of retrospective
sorting.

### 1b. What would count as a negative

The experiment §1a is owed has been pre-registered by the reporter whose seven prose errors promoted
it, before running it, and is recorded here rather than left as "someone should try". Two failure
modes, and the second is the one that matters:

**A — the criterion is ritual.** Probes run because the question said "checkable", where the probe
confirmed what the author would have written anyway. Reported as three raw counts: probes run, claims
a probe *changed*, claims a probe *confirmed*. If the third dominates and the second is near zero, the
question is cost with no yield.

**B — the criterion waves something through.** A claim judged *not* answerable at write time that a
later round falsifies anyway. An unnecessary probe costs a minute; a false negative is the criterion
actively certifying a claim it should have caught. **One occurrence demotes it from a rule to a
heuristic with a stated blind spot**, and the blind spot becomes the thing worth writing down.

**The protocol that keeps it falsifiable, and it is not optional.** Record what the claim **rests on**
(§1a) before running any probe, and judge from that rather than from a bare answerable/not-answerable
call. Write it down first. Otherwise "was it checkable" is decided by whether the probe found
something, and the criterion is unfalsifiable by construction — the exact shape this release exists
to reject.

**This repository already holds one near-instance of B, in the harmless direction.** v0.36.0's audit
recorded two byte-stamp claims as admitting no falsifying input at HEAD — the "can I ask now?" answer
was judged **no**. The round after, the same role built the reconstruction and withdrew its own
judgement: the claims *were* checkable, by truncating recorded state and emitting against an earlier
snapshot. They held, so nothing was certified wrongly and this is not a B. What it establishes is
narrower and still worth having: **the judgement itself is fallible in B's direction**, and it was
corrected only because a later round was asked to revisit what an earlier one had reached by reading.
A criterion whose input is a judgement inherits that judgement's error rate.

## 1c. Asking a role to argue against its own prior reasoning

**This is the largest thing this file's development produced and it is not about evidence grading at
all.** It is one sentence in a brief, it costs a round nothing, and it is the only mechanism either
of two independent cycles demonstrated that reliably moves a stuck loop.

**What was observed.** A five-message exchange between two agents developing §1a moved four times,
and every time it moved it was because one side brought a data point **against the position it had
just argued for**: a hypothesis's own supporting cost withdrawn as a misdiagnosis, a confound named
in the speaker's own sample, a survivor reclassified as luck rather than safety, a criterion's
"3/3" conceded to be a restatement rather than evidence. Neither cycle's audit rounds contain a
single instance of it. That is not a defect in the roles — **nothing in any brief asked for it.**

**It is inducible, and that was tested rather than assumed.** In the sixth round of a Laravel
package's audit, two roles were asked explicitly whether they still held two earlier judgement calls,
with either answer stated as acceptable. One returned **the same two verdicts with the reasoning
under both replaced**, in its own words:

> "'pre-existing and out of the file set' is a scoping excuse, and scoping excuses are exactly how a
> clean streak gets manufactured."

> "'filing it now would be ratcheting' is a statement about my own behaviour, not about the code, and
> it isn't a valid ground for a PASS."

Same conclusions, both grounds rebuilt, because it was asked. A round earlier, unasked, it had
carried both grounds forward unexamined.

**So it is not a property of correspondence between two agents who happen to disagree.** It is
available to one role in one round for the cost of one sentence — the same shape as the provenance
line that made an audit round build a new instrument instead of re-reading (*the inputs behind this
repair were chosen by the person who wrote it, which is the condition under which this cycle has been
wrong nine times; construct one that set does not reach*), pointed at **the role's own prior
reasoning** rather than at the evidence behind someone else's repair.

**Why it belongs to this release rather than to a prompt-wording change.** §1's failure is evidence
that asserts standing in for evidence that executes. A verdict carried forward on a ground the role
would not now defend is the same substitution one level up: the row asserts a conclusion whose
justification was never re-executed. `spec/0.37.0.md` §2.0a records two cycles whose audits could not
converge because later rounds re-read rather than re-examined; this is the cheapest known thing that
changes which of those a round does, and it is what makes an additional round worth its cost when the
severity gate says stop.

**What is not established.** Two instances, one per repository, both with the asking party invested in
its working. It has never been tried and found useless, which is the only result that would tell us
anything, and the same pre-registration §1b demands of the write-time question applies here: a round
that asks and gets every prior ground reaffirmed verbatim is the negative, and it must be reported.

## 2. Why audit is the sink that matters

Review's subject is a specification. Prose has no execution semantics, so reading is not tp's choice
of instrument there — it is the only one. Audit's subject is code, which can be run, and tp has the
auditor read it anyway.

The consequence is that **the auditor has no instrument of its own**: it reads code the implementer
wrote and reports on it. (An earlier draft added that the auditor also leans on the implementer's
green gate. That is false and was removed — `quality_gate`, `gate_passed` and `closed_reason` appear
nowhere in `audit.go`, `audit_roles.go` or `audit_schema.go`. The narrower claim is sufficient.)

**The field instance.** A tp user driving a Rust NLP project reported auditor prompts carrying

```
expected_evidence: 'search code under section "1. Amaç ve vizyon" for keywords from item text'
```

Round 1's `spec-coverage` returned 75 PASS. The same day, three of that project's critical gates
were found printing `PASS` while discarding the exit status they were meant to report. A keyword
search sees the `PASS` line; it cannot see the gate throwing the result away.

Scope this precisely, because the first draft did not: that string is **one of four**
`expected_evidence` branches (`audit_roles.go`), the fallback taken by `table_row` and `list_item`
items and by `task_acceptance` items mapping to zero files. The `files changed by task commit:
<paths>` branch is not a keyword search. The defect is in the fallback, not in every item.

What the instance does establish generally: for a class of defects, executing is **cheaper than
reading and strictly more conclusive**. Finding this by reading means noticing an absence — a missing
`set -e`, a discarded `$?`. Finding it by running means injecting one failure. The usual objection to
execution, that it costs more, is inverted exactly where it matters.

## 3. The informative experiment is the one that could have failed

An auditor that runs the happy path learns nothing the suite does not already contain — the
implementer ran that. The value is in perturbation: the boundary value, the broken precondition, the
injected failure the code claims to catch. This is mutation testing's principle (§8) applied per
audit item rather than per mutant.

This paragraph is the release's thesis and it is **not yet a mechanism**. §4-§7 are why.

## 4. Open: the generator cannot author an experiment

`expected_evidence` is produced by deterministic string templates over the section title, the item
text and a task→file map. It has no model, no knowledge of the project's test harness, and no way to
name a command. "The default becomes a command to run" is not implementable by that generator for
any spec-derived item.

The two honest branches, neither chosen:

1. **The generator gains an input** — a model call, which would be this release's largest commitment
   and one no other tp surface makes.
2. **The role prompt asks the auditor to design the experiment**, in which case this is a role-text
   change and must say so, and the checklist item stops being the unit of evidence.

Whichever is taken, it must be decidable by a task's acceptance. The first draft's escape hatch —
"where the item's shape does not yield an experiment, `expected_evidence` says so" — was not an
exception but the only reachable branch, which made the section a no-op that still cost tokens.

## 5. Open: `UNVERIFIED` has no legal place in the loop

"I could not run anything here" currently lands in `PARTIAL`, where it is indistinguishable from
"the code partly matches". A fourth verdict is the precondition for §3: demanding an experiment
without an honest way to report the absence of an instrument leaves asserting as the only way to
produce a verdict.

Four objections, all verified against shipped code, none answered:

1. **It cannot avoid counting.** `engine.AuditRowIsPass` makes every non-`PASS` row a finding and
   convergence is zero findings across two rounds. "Counts but is reported separately" does not
   remove it from the count — a codebase with un-runnable surface would never converge.
2. **It becomes an `audit-fix` unit with no honest exit.** `spec/0.35.0.md` §4.1 hands the oracle's
   fix unit every non-PASS, undisposed row, and the dispositions are `fixed|wontfix|duplicate`. All
   three are lies about an unverified row, and "still unverified" is not among them, so the row stays
   undisposed and the oracle re-returns the same unit until a cap.
3. **It is a downgrade path out of FAIL.** The draft reasoned only about UNVERIFIED absorbing
   PARTIAL. The dangerous direction is a real defect reported as "could not verify" — a verdict with
   no severity, in a separately-reported bucket, that reads as more honest than the finding it
   replaced. That is v0.34.0 §7.1's shape. Any design must make UNVERIFIED unavailable once a defect
   is observed.
4. **The row has nowhere to put it.** `audit_schema.go` requires `evidence_file` and `evidence_lines`
   for PASS and PARTIAL — both pointers into source text — and `RenderAuditCategoryText` keys
   `category` off PASS vs PARTIAL/FAIL with no cell for a fourth status.

## 6. Open: a declared evidence mode measures nothing

The first draft had each row declare `ran` or `read` and the round report the mix, claiming kinship
with §8's borrowed rule. The kinship is false and the objection is decisive: a mutation score is
computed by a third party from artifacts, while `ran` is asserted by the same agent whose assertions
this release exists to distrust. Nothing can contradict it, and a round reported 60% `ran` may be 0%.

A design that survives this has to bind the declaration to something tp can see — the row carrying a
command and its exit code, with the mode **derived** rather than declared. That is a different and
larger change than a field, and it interacts with every objection in §5.4.

**And a derived mode is only as good as the command's author.** Binding the mode to an exit code
removes the unfalsifiable declaration; it does not remove the choice of what to run. `quality_gate`
sits in `readOnlyWorkflowFields` (`internal/cli/set.go`), so a task-level gate is authored at
`tp init` and the project default only through the explicit `--project` route into `.tp/config.json`
— one committed file, reviewed like any other. A command a unit writes into its own closure evidence
has the opposite provenance: authored per close, in free text, by the agent whose assertions this
release exists to distrust. Executing it establishes that a command exited zero, which is strictly
more than a sentence and strictly less than the criterion. This is not §9's execution theatre — that
hazard is volume, one command's output pasted under every item; this one is provenance, and it
survives a command run exactly once against the criterion it is offered for.

The constraint it yields, stated as a narrowing rather than a design: **a carrier whose command
comes from a name space the unit does not author is worth more than one whose command it does.**
`spec/0.40.0.md` §2's named `{name, cmd}` gate entries are the only such name space currently
planned, so an evidence line naming an entry rather than a command is one shape this objection does
not defeat. Whether entry granularity is expressive enough for a per-criterion claim is unanswered,
and §7 is untouched either way — naming an entry still needs somewhere to put the name. (The
proposal that raised this arrived from a comparison of tp against two agent frameworks rather than
from a measurement, which is why it is recorded here as an objection and a constraint rather than as
a mechanism.)

## 7. Open: closure evidence has no per-line carrier

`engine.CountEvidenceLines` counts lines beginning `- ` and compares the count to the criterion
count. There is no line↔criterion binding to attach a kind to, `VerifyClosure` applies the rule only
at N ≥ 2 criteria so single-criterion tasks have no line at all, and `closed_reason` is one free-text
string rather than a structured row. Recording an evidence kind here means choosing a carrier — a new
task-file field, or in-band markers `CountEvidenceLines` must tolerate — and the draft chose neither.

## 8. Mutation score as a documented gate entry

*Moved from the release that became `spec/0.40.0.md`.*

A tautological or decorative test is invisible: coverage is high, the gate is green, and nothing
measures whether the suite would catch a regression. Mutation score is the available instrument. tp
ships no mutation tooling and no threshold; it documents the composition and stops there.

**It is a release gate entry, not a per-close one.** `spec/0.40.0.md` §2's `quality_gate` sequence
runs on every `tp done`, and CLAUDE.md's rule — the source of this section — says to run mutation
testing at decision points, "never while task gates are running", at roughly five minutes per
thousand mutants. On v0.35.0's own 44 tasks a per-close entry is about three and a half hours of
load-sensitive, timeout-prone gate time. Either §2 gains a per-entry trigger (`on: close | release`),
which is scope 0.40.0 does not currently carry, or this composes only at the release decision point.

**The instrument can stop early and say nothing about it, so a threshold read from a run is not
safe on its own.** Measured at v0.36.0's release: `gremlins unleash --workers 4 ./internal/engine`
exited after **702 mutants of roughly 1540** with a nil-pointer panic inside gremlins itself
(`engine.go:127`, `runOnFile`), whose source discards the errors from both `fs.Open` and
`parser.ParseFile` and then calls `ast.Inspect` on the nil result. The files it reached run
`auditfiles.go` through `overrides.go` — alphabetical — and the panic carries an 11-character
filename, which is `parallel.go`, the next file in that order.

Two consequences for any gate phrased on a score. The run is **silently partial**: everything
alphabetically after the crash is unmeasured, and `internal/engine/validate.go` — the standing
25%-efficacy backlog CLAUDE.md names — was never reached at all, so that run could not have spoken
to the very file it was run for. And the counts it does print are computed over what it managed,
so a score derived from them is a score over an unknown denominator. `TIMED OUT` was 5 of 702, which
rules out load as the cause and leaves the tool.

So a gate entry here cannot be "the score is at least N". It has to establish that the run
**completed** and over **which** mutants, before any threshold is read — a total against an expected
total, or the tool's exit status treated as a result rather than the summary line. This is the third
v0.6.0 defect this repository has had to work around, after `--test-cpu` silently corrupting every
verdict and `-D/--diff` failing to restrict at all; the pattern is that the failures are quiet and
produce numbers a reader would be pleased by.

**The discrimination claim needs its source named.** The moved text asserted that mutation scores
"did not discriminate between the runs it compared". That experiment is named nowhere, and in this
file a reader binds it to §2's field report, which is not it. It also reads against CLAUDE.md's own
measurement on this codebase — swept files at 96-100% efficacy, unswept at 25-78%, which is
discrimination. Either the borrowed claim is about comparing test-generation runs, in which case the
sentence must say so, or it does not hold here.

## 9. Two hazards, not one

**Execution theatre.** A requirement to attach command output is satisfied by attaching any command's
output; `go test ./...` pasted under fifty-five checklist items is keyword search with a worse token
bill. `spec/0.40.0.md` Non-Goal 2 already records the general form — every mechanical proxy
considered for "did this repair say more than it must" was gameable — and this release has not found
the predicate that is not.

**Perturbation has nowhere to happen.** §3 asks auditors to inject failures, and `spec/0.35.0.md`
§6.3 gives the audit unit a `tp-auditor` agent that "may write exactly one path" and is "denied every
other write" (test 55). §3.3 further justifies running role units *concurrently* on their being
read-only with respect to shared state. So under `tp run` no auditor can perturb anything, every row
is `read` by construction, and N auditors each building a scratch copy would dissolve the concurrency
argument. Any design owes an execution surface — a per-unit workspace in the child environment and an
amended agent definition — or must say plainly that perturbation is interactive-only.

## 10. Open: what would gate this

The first draft borrowed the replay clause now in `spec/0.43.0.md` §6. It does not transfer. That
gate works because every v0.43.0 mechanism is deterministic post-processing over rows that exist —
replay re-runs code over frozen data. §4 changes what a prompt asks a model and §6 adds a field no
recorded row contains, so no stored row can say what a differently-prompted auditor would have found.

One further fact, and it is the load-bearing one. When this section was written
`spec/.tp-review/0.35.0/` held zero audit rounds. It now holds nine — 1800 rows, recorded as that
cycle converged — so the premise that the cycle contributes nothing to its own gate is no longer
true and must be re-derived rather than repeated. What survives the correction is the clause that
actually blocks: those rows carry `role`, `item_id`, `location`, `status`, `severity`, `category`,
`evidence_file`, `evidence_lines` and `notes` — and **no `disposition`**. Audit dispositions arrive
with v0.35.0's `tp audit --resolve` but were never written during that cycle, so the manifest rule
in `spec/0.43.0.md` §6.1, which read from recorded dispositions, had no audit-side input. That
section has since been corrected against a full count of the corpus — 0 of 12,958 recorded rows
carry a disposition, review side included — and the correction is the reference to follow rather
than this paragraph's narrower audit-only finding. The corpus exists; the field the gate needed
does not.

A gate that cannot fail is worse than no gate. Naming a real one is part of this release's design
pass.

## 11. Non-Goals

1. **No verdict for the review phase.** Whatever §5 becomes is an audit-row status. Prose has no
   experiment to run.
2. **No threshold anywhere.** Neither a mutation score nor an evidence mix gates an exit code.
3. **No change to `role`, `location`, `class` or `severity`.** `status`, `evidence_file`,
   `evidence_lines` and `category` are all in scope — they are the fields the problem lives in.

mechanism a test could pin, which is the honest position rather than a gap to paper over.
