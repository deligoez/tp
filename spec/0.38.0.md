# tp v0.38.0 — The evidence contract

> §7 arrives from `spec/0.37.0.md`, where it sat alone in a release about porting CLAUDE.md's rules
> outward. It is the same rule as §3 and §6 at a third sink, and a rule stated three times in three
> files drifts three ways. It is stated once here.

## 1. Overview

tp asks three components for evidence, and all three accept an assertion where only an experiment
settles the question.

| Sink | What tp asks for | What it accepts today |
|---|---|---|
| `tp audit` checklist item | that the code matches the spec item | a keyword search that found matching text |
| `tp done` closure | one `- ` evidence line per acceptance criterion | "I looked, it appears correct" |
| the quality gate | that the suite would catch a regression | that the suite is green |

The three failures are one failure. Evidence that **asserts** — a reading, a search hit, a green
run of tests the same unit wrote — is accepted where evidence that **executes** was meant. The
asserting form is indistinguishable from the executing form at the point tp reads it, which is why
none of the three has ever been caught by tp itself.

This release makes the distinction visible. It does not mandate execution, for a reason §8 gives.

## 2. The asymmetry review and audit do not share

Review's subject is a specification. Prose has no execution semantics, so reading is not tp's choice
of instrument there — it is the only instrument. A review finding is a claim about consistency,
completeness or decidability, and it is settled by reasoning over text.

Audit's subject is code, which can be run. **tp currently has the auditor use the weaker instrument
anyway**, and the consequence is sharper than it first appears: the auditor has no instrument of its
own. It reads code the implementer wrote, and the "green" signal it leans on comes from tests the
implementer wrote, run by a gate the implementer's own close triggered. A verifier whose entire
evidence base is the implementer's exhibits is not independent of the implementer.

**The field instance this release is written from.** A tp user driving a Rust NLP project reported
that the generated auditor prompts carried

```
expected_evidence: 'search code under section "1. Amaç ve vizyon" for keywords from item text'
```

Round 1's `spec-coverage` returned 75 PASS. The same day, three of that project's critical gates
were found printing `PASS` while discarding the exit status they were meant to report. A keyword
search sees the `PASS` line and ticks the box; it cannot see that the gate throws the result away.
Reading finds this only by noticing an absence — a missing `set -e`, a discarded `$?`. Running finds
it by injecting one failure and observing the gate still print `PASS`.

That inverts the usual objection. For a whole class of defects, executing is **cheaper than reading
and strictly more conclusive**, so the cost argument against execution does not apply where it
matters most.

## 3. `expected_evidence` names an experiment

The default `expected_evidence` becomes a command to run and the outcome that would settle the item,
rather than a corpus to search. For an item asserting that a gate blocks a close on failure, the
experiment is: make it fail, run the close, observe the exit code — not: find the word "gate".

The generator cannot author a good experiment for every item, and must not pretend to. Where the
item's shape does not yield one, `expected_evidence` says so and the item is verified by reading,
which §5 makes visible rather than hiding.

**The informative experiment is the one that could have failed.** An auditor that runs the happy
path learns nothing the suite does not already contain — the implementer ran that. The value is in
perturbation: the boundary value, the broken precondition, the injected failure the code claims to
catch. This is mutation testing's principle (§7) applied per audit item instead of per mutant, and
the role instructions say it in those terms.

## 4. UNVERIFIED is the fourth verdict

**Needs a design pass before decomposition.** Specified here far enough that the problem cannot be
lost, not far enough to implement.

Audit rows carry `status` ∈ PASS/PARTIAL/FAIL. "I could not run anything here" has no cell, so it
lands in PARTIAL, where it is indistinguishable from "the code partly matches". These are different
facts and a driver cannot act on either while they share a bucket.

`UNVERIFIED` is not an ergonomic addition — it is the precondition for §3. Demanding an experiment
without providing an honest way to report the absence of an instrument leaves asserting as the only
way to produce a verdict, and auditors will assert.

The open question is convergence arithmetic, and both obvious answers are wrong:

- **UNVERIFIED counts as a finding** — a codebase with much that cannot be cheaply run never
  converges.
- **UNVERIFIED does not count** — it becomes the cheap exit, auditors flood it, and a round of
  unverified items reports as clean. That is the suppression failure `spec/0.36.0.md` §8 exists to
  gate, arriving through a different door.

The direction to design against: UNVERIFIED counts, and is reported separately, and a round in which
it dominates reports as **not a complete audit** — the per-item twin of `spec/0.35.0.md` §8a.3, where
a truncated audit reports as truncated instead of as a result.

## 5. The evidence mode is declared, and the mix is measured

Each audit row declares how it was settled: `ran` or `read`. The round reports the mix.

This is the release's answer to the enforcement question, and it is deliberately weaker than a rule.
tp cannot mechanically tell a good experiment from a bad one — §8 explains why every proxy considered
so far is gameable — but it can make the ratio visible and let a human judge it. A round that is 90%
`read` is not automatically wrong; it is a fact about that round that nobody can currently see.

This is the same borrowed rule §7 already runs on: *don't dictate the process; measure the outcome.*

## 6. Closure evidence

`tp done` requires one `- ` line per acceptance criterion. The field report credits the rule with
catching real deferrals several times, and it does not check the line's kind: "I checked, it looks
right" satisfies it exactly as well as a pasted command and its output.

Same treatment as §5 rather than a new fence: the closure records what kind of evidence each line
is, and nothing rejects a line for being a reading. A hard check here would be trivially satisfied by
pasting any command's output, which is §8's failure mode at the cheapest possible sink.

## 7. Mutation score as a documented gate entry

*Moved verbatim in substance from `spec/0.37.0.md` §7; the rule it instantiates is now §1's.*

**The rule being borrowed:** *don't dictate the process; measure the outcome.*

tp has an excellent ratchet on the review side and nothing on the test side. A tautological or
decorative test is invisible: coverage is high, the gate is green, and nothing measures whether the
suite would catch a regression.

Mutation score is the available instrument, and `spec/0.37.0.md` §2's gate sequence is the place to
put it. tp ships no mutation tooling and no threshold; it documents the composition, names the
trade-off, and stops there.

The trade-off is stated honestly because the source experiment measured it: mutation scores did
**not** discriminate between the runs it compared, sitting in a narrow band across every group.
Mutation score is a floor detector — it catches a suite that is decorative — not a quality gradient,
and it is slow enough that it belongs at the gate or in audit, never in `checks`, which run every
review round.

## 8. Not losing what we already catch

**The release's hazard is execution theatre.** A requirement to attach command output is satisfied by
attaching any command's output. `go test ./...` pasted under fifty-five checklist items is keyword
search with a worse token bill: more expensive, equally uninformative, and now wearing the costume of
proof. This is why §3 changes what the generator *asks for*, §5 measures the mix, and neither
rejects a row for its evidence kind.

`spec/0.37.0.md` Non-Goal 2 already records the general form of this problem — every mechanical proxy
considered for "did this repair say more than it must" was gameable or punished legitimate work. The
same holds here, and this release does not claim to have found the predicate that is not.

Nothing in §3, §4 or §5 ships until it is replayed against the recorded audit rounds in
`spec/.tp-review/` and shown not to lose a finding tp used to surface.

## 9. Non-Goals

1. **No sandbox.** tp does not execute anything on the auditor's behalf, does not manage a scratch
   copy, and takes no position on isolation beyond the existing rule that perturbation happens in a
   copy, never the repository.
2. **No verdict for the review phase.** `UNVERIFIED` is an audit-row status. Review findings are
   unchanged; prose has no experiment to run.
3. **No threshold anywhere.** Neither the mutation score nor the `ran`/`read` mix gates an exit code.
   Both are reported.
4. **No change to the finding contract's existing fields.** `role`, `location`, `class`, `severity`
   and `status` keep their meanings.

## 10. Tests

Written at decomposition. The invariant that must not be lost: every mechanism here either adds a
verdict, changes what a prompt asks for, or reports a ratio — and §8's replay is the gate on all
three.
