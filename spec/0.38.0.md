# tp v0.38.0 — The round reports its progress

> Split from the release that became `spec/0.48.0.md`, where this sat as one section of three under
> a title about sharding. It depends on none of that work, it is the smallest item in the pending
> set, and it answers a cost the operator pays on every cycle, so it ships first among the split
> pieces. The content is unchanged.

## 1. Overview

A round's length is set by its slowest single agent — `spec/0.48.0.md` §1 measures that, up to 44
minutes for one role, and shows that dropping a role does not shorten it. This release does not
attack that cost. It attacks the one sitting on top of it: **while that slowest agent runs, nothing
reports that anything is happening at all.** An operator watching a 44-minute round sees the same
thing at minute 2 and minute 40.

The information already exists and is already half-reported. Measured during v0.36.0's own audit
round 5, mid-flight:

```
tp audit <spec> --status   →  "in_flight_round": 5
round directory            →  4 prompts emitted, 0 role files written
```

So `--status` knows a round is **open** and cannot say it is **four-zeroths done**, while the two
numbers sit in the round directory it already resolves. The emitted count is the payload's
`prompts[]` length; the written count is the files satisfying `spec/0.35.0.md` §3.3's predicate —
the same predicate `engine.roundBasedUnits` already applies to decide which roles still need
spawning. Nothing new has to be computed or stored.

## 2. What must be true

When `--status` reports a non-null `in_flight_round`, it also reports that round's progress — how
many role files that round expects and how many satisfy the predicate — and names the roles still
outstanding. Both `tp review` and `tp audit`, since both have in-flight rounds.

The count is decidable from disk at read time. No state is written, no field is added to a recorded
round, and a completed round's record is untouched: this reports on the directory, not on the
history.

## 3. Why it belongs here rather than to the driver

`tp run --status` already reports units done against caps, and that is the answer *when a run is
driving*. It is silent for the interactive fallback `skills/tp/SKILL.md` sanctions — one subagent
per unit, spawned by an orchestrator — which writes no run state. v0.36.0's entire audit ran that
way, five rounds, four units each, and the operator's only signal was the orchestrator saying it had
spawned them.

The fallback is not a degraded mode to be discouraged into using the driver; SKILL.md names three
legitimate reasons for it, and human-in-the-loop repair between rounds was the one in play. A
phase-level signal that does not depend on who spawned the units is what covers both.

## 4. Non-Goals

1. **No progress bar.** No percentage, no ETA, no per-unit heartbeat. A count and a list of
   outstanding roles is decidable from disk at read time; anything finer needs the units to report,
   and a unit that reports progress is a channel this release does not build.
2. **No change to what a round is.** Sharding a role's checklist so the count means something finer
   is `spec/0.48.0.md` §2, and it is deliberately not a precondition here — a two-of-four count is
   already the difference between "something is happening" and nothing.
3. **No new state.** Nothing is written; the two numbers are read from the round directory the
   command already resolves.
4. **No convergence effect.** Progress is reporting; it enters no counting rule and no exit code.

## 5. Tests

1. With a round in flight and a strict subset of its role files written, `--status` reports the
   expected count, the written count, and the outstanding role names, for both `tp review` and
   `tp audit`. A strict subset rather than any number: zero-written and all-written are the two
   cases a wrong count still reports correctly.
2. With `in_flight_round` null, no progress fields are reported and the payload's key set is
   otherwise unchanged.
3. A round whose files are all written reports written equal to expected, and the round is still
   reported in flight until it is recorded — the two are different states and the output must not
   conflate them.
4. `--status` writes nothing: the round directory's contents and mtimes are identical before and
   after, proven by hashing the directory rather than by inspection.
5. The written count uses `spec/0.35.0.md` §3.3's predicate, proven by mutating the predicate's
   input — a partial file that fails it — and observing the count fall.
