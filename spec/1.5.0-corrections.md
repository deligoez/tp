# 1.5.0 — decisions at the review cap

The implementing tasks' acceptance for `spec/1.5.0.md`, after its review loop ended at its cap of four
rounds. Like `spec/1.3.0-corrections.md`, this file records what the reviewed text left open, so the
spec itself stays the text the rounds read. The fourth round's findings were medium and low, every one
about behaviour the release creates; each was decided under the operator's delegation, dispositioned
`wontfix` in `review-round-4.ndjson` naming its decision, and carried into the tasks. Where these and
the spec differ, these win.

| # | decision |
|---|---|
| C1 | `tp epic ready` lists the claimed epics that would otherwise be ready apart, each with its holder; that is where it names a claim's holder. `tp epic status` names the holder beside each claimed epic |
| C2 | the estimate chain is the heaviest chain by summed estimate among all chains of not-done epics ending at a not-done gate member, chosen independently of the longest chain by count |
| C3 | `tp epic import`, fenced under `TP_UNATTENDED` like every graph writer since v1.3.0, keeps the escalation decision `other`; `epic-done`, `gate-met` and `epic-binding` name only the commands the spec lists |
| C4 | `throughput` counts only epics whose status is `done` now, in the ISO week of their `done_at`; a reopened epic counts in no week until it is done again |
| C5 | row 12's critical path on "the chain with b done and A's gate on a" is `[a]`: the done b cuts the chain, and the row asserts that `[a]` and not `[a, b, c, d]` or `[c, d]` is reported |
| C6 | a claim outlives a binding but is ignored by status; `tp epic claim --release` works on a bound epic, the exit 1 for a bound epic applying to taking a claim only |
