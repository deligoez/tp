# tp v1.2.0 — tp stops lengthening work

> The release notes for the `v1.2.0` tag. Publishing is a separate, human decision.

tp's own history showed the loop making work longer instead of safer: 18 of the 20 cycles with a
round-1 snapshot grew their spec during review, none shrank, and 92% of recorded review
dispositions were `fixed`, meaning a finding's usual way out was more spec text. From 2026-09-09 to
this release's first commit, 42 commits touched only specs and one touched code, while the backlog
grew to 70 files. This release makes each loop end, lets an audit finding be accepted, fixes the defects that
were reproduced, and changes how tp develops itself. It was built through the fix track it
introduces: 34 code commits and 2 spec-only commits.

## Upgrade notes

- **Round caps now default to 3.** `review_max_rounds` and `audit_max_rounds` were uncapped by
  default. A project that relied on that now stops at round 3. An explicit `0` keeps a loop
  uncapped: `tp set --workflow --project review_max_rounds=0 audit_max_rounds=0`.
- **`file_check` item ids changed** to `file-<role>-<slug>.<16 hex>`, where the suffix is a digest of
  the file's cleaned path. Rows of a round recorded before this release name no item of the next
  round: the next prompt lists them apart, to be matched by `evidence_file`. tp's own
  `scripts/audit-round-prep.py` refuses to carry rows from such a round (exit 2).
- **Re-emitting over an unrecorded round whose spec changed exits 3** in `tp ground`, `tp review` and
  `tp audit`, naming the round and the files it would overwrite. `--force` discards the round.
  Re-emitting over an unchanged spec is still idempotent.
- **`tp ground <spec> --status --check` exits 1 while the latest round holds a `FAIL`.** It used to
  gate on coverage alone. `PARTIAL`, `QUESTION` and `UNVERIFIABLE` do not fail it.
- **`tp audit --resolve-all` no longer writes a disposition onto `PASS` rows**, and
  `--resolve <role:item_id>` disposes every finding under the key.
- **Two new escalation decisions**, `accept-finding` and `discard-emission`, for the new fences below.
- **Ejected reviewer roles keep their old text.** A project that ran `tp init --eject-roles` gets the
  new reviewer text only after re-ejecting with `--force`.

## Every loop ends

- A loop is **done** when it has converged, or when it reaches its cap with every finding of the
  latest round carrying a disposition. That one verdict (`done`, `done_by`) is read by `--status`,
  `--check`, `--record`, `next_action`, `tp resume` and `tp import`, so no two surfaces disagree
  about whether a loop is over.
- `next_action` names a disposition (`--resolve … wontfix|duplicate "<evidence>"`) as an exit equal
  to revising the spec.
- `tp import` passes at the cap without `--force` when the loop is done, and its payload names the
  verdict it passed on: `done_by`, `fixed_at_cap`, `stale_waived`.
- A blocking finding marked `fixed` at the cap keeps the loop open (`blocking_fixed_at_cap`), since
  no round re-read the repair. The exits are to accept it with evidence or to raise the cap by one.
- Under `TP_UNATTENDED`, accepting a critical or high review finding, or any audit finding, exits 2
  and escalates `accept-finding`; a `wontfix` or `duplicate` without evidence exits 2 in both phases.
  `fixed` is not fenced.

## An audit finding can leave its round

An evidenced `wontfix` or `duplicate` clears the audit round it is recorded in, live on `--status`
and `--check`. Each round is graded under the `audit_converge_on` it was recorded with, and a round
stamped clean stays clean. `tp resume`'s `unresolved_findings` counts open findings by the same
predicate the clean grading reads, so a clean round no longer reports unresolved findings, and
`duplicate` reads the same on every surface.

## An audit round records what was graded

- A `file_check` id depends on the role and the file's path only, never on the list it was emitted
  in, so two shards of one round can no longer give one id to two files. `--affected-files` is
  cleaned, made repo-relative and deduplicated.
- `tp audit --merge` collapses rows only when their verdict agrees. Rows that disagree on one item
  are all kept and reported under `conflicts`. Before, the first row won, and a second shard's
  error-severity `FAIL` could disappear behind a `PASS`.
- The conformance role reads every commit a task records (`commit_shas`, or a lone `commit_sha`),
  not only the first.
- A `--resolve` into a file no round state lists says so (`recorded_round: false`), and the
  suggestion to re-record is offered only inside a driver round, for an exact copy of that round.
- A role that writes `[]` found nothing, at merge and at record, in both phases.

## Other defects fixed

- A task-file write names the file it wrote; a write chosen by a leftover `tp use` pointer while
  another task file exists says so, and `tp init`/`tp import` of another spec warn about the pointer.
- `tp unclaim <id>` returns a `wip` task to `open`.
- `tp done --batch` accepts `commit` as a string or an array, and refuses a row that also names
  `commit_shas`.
- The floor splitter no longer ends a sentence at an ordinal before a lowercase word, or loses a
  numbered list glued to its lead-in line.
- A refused `--role` writes nothing to the state directory.
- A registered check that could not run (exit 2 or higher, 126/127, a signal, a timeout) reports
  `ran: false` and no longer suppresses its class.
- `tp init` and `tp import` warn when the quality gate's first command does not resolve; a gate that
  exits 126 or 127 names the command instead of suggesting `--skip-gate`.
- An attended `tp set --workflow quality_gate=<cmd>` writes the spec's override, and an empty value
  removes it. Under `TP_UNATTENDED` any change to the quality gate is refused.
- Both plugin hooks judge a `mcp__codedbpro__batch` op by op, so a batch of reads is no longer
  refused for naming a fenced path.

## Reviewers report what would make the implementation wrong

The reviewer roles, and the prompt around them, now ask for requirements that contradict each other
or the stated goal, cannot be satisfied, or read two ways that two correct implementations would
disagree on. Detail the code will settle is not a finding, a `high` finding carries a counterexample,
and finding nothing is a normal result. `over-specification`, the one class whose fix is a deletion,
is recorded at most medium.

## The skill triages work before starting it

`skills/tp/SKILL.md` now opens by picking a track, and the operator confirms it:

- **Fix**: a defect with a reproduction, handled by the new Workflow F. Write the failing test from
  the reproduction and watch it fail, fix, run the gate, review the diff once, commit. There's no
  spec, no ground and no review rounds. A fix that turns out to need a design choice stops and
  becomes a decision.
- **Decision**: a choice between alternatives with user-visible consequences. A note of at most two
  pages, with the change built in a clone first, then Workflow A without the ground loop, two
  reviewer roles and at most two review rounds.
- **Full**: a new capability too large to build in a clone first. Workflow A with the ground loop,
  round caps set at `tp init`, and the spec's growth checked between rounds.

On both spec tracks, a repair after the first round deletes or narrows; it doesn't add requirements.
The interview (Step 0) ends when every decision with user-visible impact is decided, not when every
behavioural claim is verified. A test row's mutant and its two counts belong in the implementing
task's acceptance, not in the spec body.

## How tp develops itself

tp's own repository now runs on these tracks. `BUGS.md` holds the reproduced defects the fix track
takes next, the backlog went from 70 files to three decision candidates (`spec/backlog/ARCHIVE.md`
says where the rest went), `CLAUDE.md` went from 589 lines to 181 with its lessons moved to
`docs/lessons.md`, and `scripts/check-spec-growth.py` is registered as the growth check.
