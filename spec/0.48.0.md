# tp v0.48.0 — The divisible round

> Split from `spec/0.41.0.md` when the pending specs were divided into independently releasable
> pieces. That file bundled three things under one title, and only two of them were about
> divisibility: a durable home for an accepted finding ships as `spec/0.41.0.md`, and in-flight round
> progress as `spec/0.38.0.md`, both of which are independent of sharding and much smaller. What
> remains here is the release the title actually names. The content is unchanged.

## 1. Overview

A round's unit of work is "one role × every affected file × every checklist item". That unit is
indivisible: `--affected-files` narrows the files but not the checklist, and nothing says "re-check
only what changed since round N" or "only what was not `PASS` last time".

Two costs follow, both measured on a field cycle running nine rounds over a PHP package:

**Round length is set by the slowest single agent.** Round 7 wall times: test-isolation 44 min,
spec-coverage 29 min, security 22 min, docs-skill-sync 10 min, maintainability 8 min. The operator
then dropped a role for round 9 — and the round did not get shorter: test-isolation 35 min,
spec-coverage 33 min. Trimming roles buys nothing because the two long poles are internal to one
prompt. `overlap_report` showed zero shared findings across all four remaining roles, so the dropped
role was not redundant either; the round simply cannot be shortened from the outside.

**Every round re-derives the whole surface.** That cycle's finding counts rise and fall across rounds
3–9 without settling; `spec/0.43.0.md` §2.1 owns the series and the reading of it, and the half that
matters here is its conclusion: rounds 6 and 7 found genuine correctness defects, so the rises are
not pure churn — but a large share of each round's growth is the *previous round's fixes* being
audited for the first time, at full depth, alongside everything already checked five times. Nothing
separates new surface from settled surface, so the trajectory cannot be read.

This release makes the round divisible. It is placed after `spec/0.43.0.md` deliberately: that
release measures where a round's cost actually goes, and sharding is the expensive answer to a
question the measurement should be allowed to ask first.

## 2. Sharding a role's checklist

The non-`spec-coverage` roles already receive one `file_check` item per file, so their cost grows
linearly with the file list and shards trivially. `spec-coverage` is the hard case: one 73-item
checklist from a 48 KB prompt, each item verified by execution.

**Mechanism, open in one respect.** A role whose checklist exceeds a threshold is emitted as several
prompts over disjoint item sets, each producing its own findings file, merged as today. What is not
decided is the split key — by item count, by prompt bytes, or by the item's own `type` (`file_check`
shards cleanly, `task_acceptance` may not) — and the answer should come from `spec/0.43.0.md`'s
measurement rather than from a guess made here.

**What must hold however it is decided.** The merged result of N shards is the same set of rows a
single unit would have produced; no item is dropped at a boundary; no item is judged twice; and the
per-role overlap report still attributes each row to one role.

## 3. Incremental rounds

`tp audit --since <round>` or `--only-open`: re-check what changed since a named round, or what was
not `PASS` last round, rather than the whole surface.

**The hazard is this release's own, and it is the v0.34.0 §7.1 shape.** Anything that narrows what a
round examines can hide a finding the full pass would have made. A settled item is settled against
the code as it was; a repair three rounds later can unsettle it silently. So an incremental round is
**uncounted for convergence** unless it can show that the surface it skipped is unchanged — which
means the skip predicate has to be derived from something tp can see (the affected-file set, a
content hash), never from the previous round's verdict alone.

## 4. Non-Goals

1. **Changing what an item asks.** Sharding splits the checklist; it does not rewrite items.
2. **Convergence arithmetic.** `spec/0.37.0.md`.
3. **A durable home for an accepted finding.** `spec/0.41.0.md`, which ships years of release
   numbers earlier because it is independent of everything here.
4. **Reporting a round's progress.** `spec/0.38.0.md`, split out for the same reason.
5. **Prompt self-sufficiency and `--out-dir`.** `spec/0.36.0.md`. A prompt that can be written to a
   file is a precondition here, which is why that ships first.
6. **Deciding the split key before the measurement exists.** §2 states the requirement and leaves
   the key to `spec/0.43.0.md`'s data. Fixing it here would be a guess wearing a specification's
   clothes.
7. **Making an incremental round count for convergence by default.** §3.

## 5. Tests

Written at decomposition. §2's split key must be decided first; §3's tests can be written today,
because its requirement — an incremental round does not advance convergence unless the skipped
surface is provably unchanged — is stated fully.

**The gate this release owes itself, and the one it may not borrow.** Sharding and incremental
rounds both narrow what reviewers see, so the release needs a gate for the same reason
`spec/0.43.0.md` §6 does. An earlier draft borrowed its form — "replayed against the recorded
rounds in `spec/.tp-review/`" — and that is withdrawn here, because the same demand was measured in
`CLAUDE.md` and found unrunnable: a quarter of the recorded review rounds carry a snapshot whose
sha256 is not the `spec_hash` that round recorded, so a replay compares against text the round never
read and reports clean. `spec/0.43.0.md` §6.1 records the second half of the same problem — no
recorded row carries a disposition — and `spec/0.49.0.md` §10 records why the borrowing failed there
too. Three files now name this; it should not be reached for a fourth time.

What replaces it is the shape `spec/0.36.0.md` §6 found when the same substitution was needed: a
gate stated as **an invariant the mechanism must satisfy**, checkable against a live tree, rather
than a comparison against history. §2 already states one — the merged result of N shards equals the
rows a single unit would have produced, on the same spec, with no item dropped and none judged twice
— and that is runnable today against any spec in the repository. §3 needs its own, and §3's own
sentence is already close to it: an incremental round does not advance convergence unless the
surface it skipped is provably unchanged by a predicate derived from the affected-file set or a
content hash. Naming those two invariants as the gate is decomposition's first job.
