# tp 1.18.0 — an audit FAIL no later round re-grades blocks convergence

What 1.18.0 changed in the audit loop and what it measured doing so. The decision is
`spec/backlog/audit-carried-fail-blocks.md`; this file holds the repro, the identity rule the
measurement chose, and what the upgrade does to tp's own shipped specs.

## Conclusions

- Empty audit rounds no longer converge past a FAIL. The audit carried set holds, per
  `(role, item_id)` since the newest epoch, the item's latest graded row; a later PASS or an
  acceptance clears it, and nothing else does.
- Every later prompt asks for the re-grade: the Prior Round block lists every carried row, a row older
  than the previous round with its `round`, so the rule never blocks on a row no prompt names, except
  a row whose role the panel no longer holds, which the surfaces say no round can re-grade.
- The identity of a positional id across a spec repair is decided from the rounds' snapshots, not from
  the spec hash alone: requiring an equal hash turned eight of the ten rows it newly carried in tp's
  own histories into false blocks.
- Two of tp's shipped specs read differently after the upgrade, 0.37.0 and 1.5.0, each over one row
  no round re-graded; they are left so, as 1.16.0 left its four.

## The repro, before and after

`TestAuditCarriedBlocking_EmptyRoundsDoNotConvergePastAFail`: round 1 records one `spec-coverage`
FAIL at `error`, rounds 2 and 3 record nothing. On v1.17.1 `tp audit spec.md --status --check` exits
0 with `converged: true`; on 1.18.0 it exits 1, `converged` and `done` false, `carried_blocking: 1`,
and the row is named by round, file, index, role, item and severity. Round 3's prompt on v1.17.1 no
longer mentioned the FAIL; on 1.18.0 it lists it with `"round":1`
(`TestAuditCarriedBlocking_EveryLaterPromptAsksForTheReGrade`). A fourth emission at the default cap
was allowed on v1.17.1, since its refusal read the stored round flags; it is refused now, its hint
naming the row's acceptance and `raise-audit-cap` (`TestAuditCarriedBlocking_TheCapRefusesAFourthRound`).

## The identity rule, measured

Audit ids `table-<t>-<r>` and `list-<l>-<n>` are positions in the spec text; the tp-smart session
pointed out that after a spec repair such an id may name another item, so a PASS under it could clear
a row it never re-graded. The first build required the PASS round's `spec_hash` to equal the row's.

Measured in a clone of this repository with the first build and v1.17.1, `tp audit <spec> --status`
over every spec with audit rounds: four specs changed their verdict, 0.31.2 and 0.35.0 from converged
to not, 0.37.0 and 1.5.0 from ended by the cap to not, over ten carried rows. Tracing each row's key
through the round files: eight of the ten were graded PASS in a later round over a repaired spec, so
the hash rule held them open falsely; two were never re-graded.

The rule shipped compares the items instead: a PASS over another text clears a table row or list item
unless the row's snapshot text for the id sits at another id of the PASS round's snapshot, which means
the item moved (a list item compared by its words, without its number); a `finding-` ordinal has no
text and still needs the same hash. With it the same measurement leaves two specs changed, over the
two rows nobody re-graded. `TestAuditCarried_APositionalIdClearsUnlessItsItemMoved` pins the three
cases: same id, item repaired in place, item moved.

## The two shipped specs

| spec | row | why it is carried |
|---|---|---|
| 0.37.0 | `spec-coverage:table-2-14`, `warning`, from round 4 | graded PARTIAL in rounds 3 and 4, absent from rounds 5 to 7 |
| 1.5.0 | a `go-safety` `file-` row, `info`, from round 4 | dispositioned `fixed`, never graded again |

1.5.0's rounds were recorded under `audit_converge_on: all`, and 0.37.0's before the policy was
stored, which is graded as `all`; under it any non-PASS row blocks. `tp resume`
over all 32 task files of the repository reads the same on v1.17.1 and 1.18.0 except these two, which
move from `release` with no blocker to `audit` with `audit-budget-exhausted` (0.37.0 also
`spec-stale`) and no unit offered. The repository's active spec, 1.8.0, and the session-start hook,
which reads only the active spec, are unchanged, so nothing proposes audit work every session.

## Calls the note left open

- **The policy a carried row is graded under** is the latest recorded round's `audit_converge_on`,
  the one the cap's grading already used.
- **Within one round** the worst row under a key counts: a FAIL beside a PASS of the same key (a
  `--merge` conflict) is not cleared by it.
- **A role the panel no longer holds** makes its rows unclearable by any round; the clause names only
  the acceptance and the epoch for them, and counts them among the rest when some rows are reachable.
- **`audit_clean_rounds: 0`** no longer lets a round's own blocking FAIL converge: the carried set
  includes the latest round. `TestAuditSignal_ConvergedGateWithholdsDivergence` now reaches its
  converged gate through a warning under `blocking`.

## After review

Two reviewer roles, correctness and agent experience, read the first build in scratch clones. Every
finding was fixed test-first except where noted.

- **An epoch past a fixed audit row (high).** `--rewritten` counted only unresolved rows, and an audit
  row marked `fixed` still blocks, so a unit could write `fixed` and start an epoch past the row, both
  unattended. The audit cut now holds every blocking row
  (`TestAuditCarriedBlocking_AFixedAuditRowIsNotCutPastUnattended`), and the unattended refusal names
  the next round's re-grade and an escalated acceptance instead of an acceptance it would refuse.
- **Positional identity.** An item whose words another item shares counted as moved; a moved item's
  row could be cleared by nothing, since the PASS lands at its new id. Both fixed: the same text at the
  same id is the same item, and a PASS where a moved item's text now sits clears its row
  (`TestAuditCarried_APositionalRowFollowsItsMovedItem`).
- **The prompt.** The earlier-round line was written for accepted rows too and told the role a row
  holds the audit open until a PASS; it now asks only for a grade, and only for rows not accepted. A
  listed item the round's checklist no longer holds gets a line asking for its row, and the schema
  accepts a Prior Round `item_id`.
- **Surfaces.** `tp resume --compact` kept only a count: the audit budget blocker's data now carries
  the rows, the acceptance command and `raise-audit-cap`. `tp run --status` read convergence without
  the carried set. Roles are read trimmed, and a row with no role or item is named by its index.
- **Docs.** `tp resume` names the rows at the cap only, since below it it offers the round that
  re-grades them; a policy switch releases rows once a round is recorded under it, so not at the cap.
- **Not changed:** a `finding-` row after a spec change, and a positional row whose snapshot is
  missing, still clear only by acceptance or an epoch; the surfaces name both exits.

The shipped-spec measurement was rerun on the final binary: the same two specs read differently, over
the same two rows, and `tp resume` differs on the same two task files only.

## Mutation

`./scripts/mutation.sh` at `cbe75403` over the Go files changed since v1.17.1; the report is
`~/.cache/tp-mut/cbe75403-20261114-021621/go-mutesting-agentic.json`, and its summary is the count.
`validate.go` carries most survivors because the whole file is mutated for a three-line `touches`
check; they sit in code this release did not change, as do those in `carried.go`'s untouched
helpers and `escalation.go`'s directory mode.

The survivors in the new audit carried code were read one by one:

- **Killed by a new test** (`internal/engine/auditcarried_mutants_test.go`, each seen red under its
  mutant): the worst row of a round (`base - rank`), the severity kept since the last clear
  (warning ranked as info), a single round's policy (`n > 1`), a latest-round row framed as earlier
  (`<=`), one carried row at the cap (`len(carried) > 1` in `AuditLoopDone`), and the plural and
  partly orphaned clause.
- **Killed by a CLI test the per-file run does not execute**: the orphaned-role count when the panel
  resolves (`err == nil`, `n := -1`), held by
  `TestAuditCarriedBlocking_ARowNoRoleCanReGradeSaysSo` in `internal/cli` (seen red under `err == nil`).
- **Equivalent**: rank and weight constants moved without changing their order, a tie between rows
  of equal weight in one round, and `latest` starting at -1 or 1 where every round number is above
  both.

## Who decided

The operator chose the rule: the same as review's in 1.16.0, an unresolved FAIL holding convergence
until a later round re-grades it PASS, and the shipped specs left as they read. The tp-smart session
gave a second opinion on the audit translation: identity by `(role, item_id)` with a guard for
positional ids, the worst row within a round, an explicit PASS rather than any later round, every
later prompt listing the row, and one `rewrite-past-blocking` decision for both phases. The agent took
the calls listed above and chose the snapshot comparison over the hash after measuring. No rule-9
decision came up while building it.
