# tp 1.25.0 — measurements

## Rolling implement slots

This section measures `spec/backlog/rolling-implement.md` §4. The expected numbers below were
written and committed before any code of the change.

### Fixture

- **The repository.** One spec and six open tasks, `t1` to `t6`, with no dependencies and a
  `touches` each (`t<i>.txt`), so no two overlap. `commit_strategy` is `builtin`.
- **The gate.** `quality_gate` is `sleep 1` with a log line before and after: real duration, almost
  no CPU. No `worktree_setup_cmd` is set, since the gate needs no ignored file.
- **The units.** A scripted unit, spawned through `TP_RUNNER_SEAM`, sleeps for the agent's time,
  commits `t<i>.txt` and closes through the real `tp done <id> --commit <sha>`. The sleeps are
  uneven: 4 s for `t1` and `t4`, 1 s for the other four.
- **The logs.** The unit and the gate append their start and end to a file outside the
  repository, so the log never dirties the tree a gate passed on.
- **Each run** starts from a fresh copy of the template with `run_max_units` 6, at caps 1, 2 and 3,
  once with the branch's binary and once with the barrier binary built from `3158f7d8`.

### What each number means

- **Wall time:** the wall clock around `tp run`.
- **Idle slot-seconds:** `cap × wall time` minus the summed `duration_seconds` of every unit
  attempt in the run state. Cap 1 has one slot, so its figure is the driver's own overhead.
- **Peak gates:** the largest number of gate runs, unit and main-branch alike, that the gate log
  shows running at one instant.
- **Gate reuse:** of the closes on the main branch, how many reused the unit's gate (the
  `gate reused from the unit's worktree` notice in the integration logs). A close reuses only when
  nothing landed on the main branch between its worktree's add and its pick. At cap 1 the unit
  gates in the main tree and there is nothing to reuse, so the rate is n/a.
- **Solo reopens:** tasks marked `solo` at the end of the run.
- **Task-audit drains:** how often a full task-audit batch drained the pool.

### Expected

The model behind the numbers: 0.3 s of overhead per `tp done` and spawn, 0.2 s per worktree add,
0.1 s per pick and per loop re-read, and the gate's 1 s. Wall times are that model's, rounded; the
other columns follow from the schedule, not from the constants.

| Cap | Schedule | Wall (s) | Idle slot-s | Peak gates | Gate reuse | Solo reopens | Task-audit drains |
|---|---|---|---|---|---|---|---|
| 1 | barrier binary | 20.4 | 0.6 | 1 | n/a | 0 | 0 |
| 1 | rolling | 20.4 | 0.6 | 1 | n/a | 0 | 0 |
| 2 | barrier | 19.8 | 19.8 | 2 | 3/6 | 0 | 0 |
| 2 | rolling | 16.7 | 13.6 | 2 | 2/6 | 0 | 0 |
| 3 | barrier | 18.4 | 35.4 | 2 | 2/6 | 0 | 0 |
| 3 | rolling | 12.3 | 17.1 | 3 | 1/6 | 0 | 0 |

- **Cap 1** is the same path on both binaries, so its two rows must agree within noise. That is
  the fixture's own check.
- **Barrier.** Cap 2 runs three batches of two, `{t1,t2}`, `{t3,t4}`, `{t5,t6}`, each waiting for
  its 4 s unit; cap 3 runs two batches of three, each holding one 4 s unit. The first close of a
  batch reuses its gate and the rest do not, so cap 2 reuses 3 and cap 3 reuses 2.
- **Rolling.** A short unit's slot is refilled as soon as it is integrated, so the 4 s units no
  longer hold the short ones back. Reuse falls, because the pool keeps landing work on the main
  branch under a running unit: at cap 2 only `t2` and `t5` find nothing landed since their add, at
  cap 3 only `t2`.
- **Peak gates** is at most the cap under the serial rule: a main gate runs only after a unit has
  exited, and its slot is not refilled until the gate ends, so at most `cap − 1` unit gates run
  beside it. A measured peak above the cap would mean a refill ran during a main gate.
- **Task-audit drains are 0 by construction:** a full task-audit batch is 10 files
  (`TaskAuditBatchFiles`), and six one-file tasks never fill one. The drain is shown by a Go test
  instead, not by this fixture.
- **Solo reopens are 0** because no two tasks touch the same file.
