# tp v0.36.0 — The rules become checks

## 1. Overview

tp's `CLAUDE.md` carries roughly fifteen hard-won rules about how to run a cycle: decompose by what
the gate sees, verify the gate with separate exit codes, keep audit repairs minimal, dogfood the
in-progress binary, mutate an implementation before trusting the test that guards it. Every one was
paid for with a failed cycle. **None of them reaches anyone who is not this repository.**

That is the same shape tp already solved once on the review side. A finding class that recurs
becomes a registered mechanical check, reviewers stop reporting it, and convergence gates on it.
v0.33.0 proved the pattern works on process rules too: "track `spec-coverage` separately" was a
CLAUDE.md instruction for one release and became `spec_coverage_clean_rounds` in the next, at which
point nobody had to remember it.

This release applies that ratchet to the rest of the list. It is also the release that turns tp back
outward: for six versions the work has been about tp's own loop, and each item here is a rule tp
learned that every user of tp should get for free.

Two items need a design pass before decomposition and are marked as such. They are specified far
enough that the problem cannot be lost, not far enough to implement.

## 2. `quality_gate` as a sequence

**The rule being mechanized:** *verify the gate with separate exit codes, never a `&&` chain.*

A gate written as `go test ./... && golangci-lint run` reports one exit code for two questions. When
it fails, the output does not say which half failed, and a red linter behind a green test suite is
easy to misread. In v0.31.2 exactly that hid a failing `golangci-lint` for four audit rounds.

`quality_gate` accepts an array of `{name, cmd}` entries alongside today's string form. tp runs each
entry in order, records each entry's exit code and duration, and stops at the first failure. The
recorded evidence names the failing entry. The string form stays valid and unchanged, so no existing
task file moves.

This also makes the gate's composition visible: an operator adding a mutation-score or race check is
adding a named entry, not extending an opaque shell string.

## 3. The test-file fence

**The rule being mechanized:** *a disagreement with a test is information, not an edit.*

"Fix the test to make it pass" is a well-known agent failure mode and it silently destroys the
oracle. tp's scope fence already covers refactor, rename, cleanup and hand-edits to `.tp-review/`
and the task file. Test files are not on it.

The fence cannot be unconditional, and this is where the field report that raised it was incomplete.
tp's own v0.31.2 lesson says a change and the test it invalidates belong to the **same** task,
because the gate runs at every close — so a unit legitimately editing a test is a normal case, not
an anomaly. The rule that holds in both directions:

> An implementation unit may not write to a test file unless its own acceptance names that file or
> the behaviour change that invalidates it. Otherwise the disagreement is reported as an
> `Out of scope:` line in the closure evidence.

`tp brief` states the fence with the unit's own permission resolved, so the unit is told which of
the two cases it is in rather than being left to judge. A `test_globs` workflow field carries the
project's test-file patterns, defaulting to the common conventions of the spec's domain.

Enforcement is the plugin's `PreToolUse` hook from v0.35.0, reading the same resolved permission.
The fence text and the hook must agree by construction — one source, two consumers.

## 4. `tp lint`: a computational section with no example table

**The rule being mechanized:** *expected values come from the spec, not from the implementation.*

v0.34.0 documented example tables as the recommended acceptance shape for behavioural tasks. A
documented recommendation decays; a lint rule does not.

A new informational rule fires when a section describes computational behaviour and contains no
table and no code block — a rule, a formula, a rounding decision, a threshold, stated in prose with
no worked example. The message asks for an example table rather than asserting a defect, and the
rule stays informational: this is a smell, not a violation, and tp's lint has earned its low
false-positive rate by being conservative.

**Design pass needed** on the detection predicate. The honest options are a keyword-and-shape
heuristic over the section text, or a narrower trigger — a section whose sibling tasks have
acceptance criteria containing numeric literals that appear nowhere in the spec. The second is
weaker but nearly false-positive-free, and it measures the thing that actually matters: an expected
value that exists only in the task.

## 5. `tp validate`: the unexecutable test-task split

**The rule being mechanized:** *a change and the test it invalidates belong to the same task.*

A dependency graph that puts a change in one task and the test it breaks in the next looks correct
and cannot be executed: the gate runs at the earlier close, and that close is already red. The graph
validates, the plan reads well, and the cycle stalls at the first close.

**Design pass needed.** tp cannot know statically which test a change invalidates. The shape worth
detecting is narrower and derivable: a task whose only work is tests, depending on exactly one task,
where both anchor to the same spec section. That is the pattern that produced the failure, it is
computable from data tp already holds, and it is a warning rather than an error because the split is
sometimes correct — a new test for a change that broke nothing.

## 6. The binary check

**The rule being mechanized:** *dogfood the in-progress binary, never the lagging release.*

During self-development the tp on `PATH` lags the repository and hides the behaviour under
development. The rule has been in `CLAUDE.md` since v0.28.0 and is violated by anyone who forgets to
rebuild.

When tp runs inside a repository that is tp itself — detected by the presence of a task file whose
spec version is newer than the running binary's version — it emits one advisory naming the mismatch
and the rebuild command. One advisory per invocation, silenced by `--quiet`, never an error.

This generalizes beyond this repo: any project developing a tool with tp hits the same trap.

## 7. Mutation score as a documented gate entry

**The rule being borrowed:** *don't dictate the process; measure the outcome.*

tp has an excellent ratchet on the review side and nothing on the test side. A tautological or
decorative test is invisible: coverage is high, the gate is green, and nothing measures whether the
suite would catch a regression.

Mutation score is the available instrument, and §2's gate sequence is the place to put it. tp ships
no mutation tooling and no threshold; it documents the composition, names the trade-off, and stops
there.

The trade-off is stated honestly because the source experiment measured it: mutation scores did
**not** discriminate between the runs it compared, sitting in a narrow band across every group.
Mutation score is a floor detector — it catches a suite that is decorative — not a quality gradient,
and it is slow enough that it belongs at the gate or in audit, never in `checks`, which run every
review round.

## 7a. The repair rule, which is the largest unmechanized one

**The rule being borrowed:** *a repair that says more than it must is the next round's finding.*

This belongs here because it is the clearest case of §1's premise: a rule paid for with a failed
cycle that reaches nobody outside this repository, and that is currently written down in **neither**
`CLAUDE.md` nor `skills/tp/SKILL.md`.

Measured over nine review rounds on an external spec, four roles per round, 502 findings. Blocking
counts by round:

```
round     1   2   3   4   5   6   7   8   9
blocking 46  35  37  34  35  14  17  11   7
```

Rounds 1–5 sat flat at 34–46 with no trend. The regime changed at round 6, and **the spec is not
what changed** — the author changed how repairs were written. Through round 5 every fix carried an
explanatory clause justifying itself; from round 6 the rule was minimum change, no rationale prose.
Average repair went from ~8 lines to ~2, and blocking fell 60% in one round.

The cause is structural rather than stylistic. Every explanatory sentence in a normative document is
itself normative surface: a new claim that can contradict another section, and a new cross-reference
that can go stale. Closing N findings by writing M lines of new prose generates roughly `k·M` new
ones, so while `M` is large the loop sits at its fixed point. Round over round, most of each round's
blocking findings were located in text written during the immediately preceding round.

v0.34.0 ran on this from its second round onward and converged. Its audit then reproduced the same
dynamic one phase later: more than half the findings after round 2 were defects introduced by an
earlier round's own repair.

**What this release owes it.** At minimum the rule moves to `SKILL.md`, where every tp user gets it,
since it is not about this repository. Better, and in the spirit of §1: `tp review --record` already
knows each round's findings and their locations, so it can measure the thing directly — report what
share of a round's findings sit in text the previous round's repairs touched. A number the loop emits
needs nobody to remember it, which is the whole ratchet.

## 8. Non-Goals

1. **The held-out example subset.** A portion of the spec's example rows withheld from the
   implementation unit and run only at close is the natural next step after §4, and it is genuinely
   attractive: a held-out failure means either the implementer special-cased the visible tests or its
   spec interpretation diverged. It needs the example-table practice to exist first, and it changes
   what a green close means. Later, on evidence.
2. **An audit-repair surface check.** "A repair that introduces a new abstraction belongs to the next
   version" is a real rule and the fourth-most expensive one tp has learned, but every mechanical
   proxy considered so far — diff size, new symbol count — is gameable and punishes legitimate
   repairs. It stays prose until someone finds a predicate that is not.
3. **`scope` on audit rows and `audit_converge_on`.** Unchanged since v0.33.0, carried in the
   candidates file.
4. **Model selection.** The `runner` map in v0.35.0 is where producer and judge are separated. tp
   takes no position on which model belongs where.
5. **Enforcing any of this.** Every item is a warning, an advisory, an informational lint rule or a
   documented composition. The one hard fence is §3, and it is scoped by the unit's own acceptance.

## 9. Tests

1. A `quality_gate` array runs entries in order, stops at the first failure, and records per-entry
   exit codes; the string form behaves exactly as before.
2. Recorded evidence names the failing gate entry.
3. `tp brief` states the test fence with the unit's permission resolved from its acceptance and
   `test_globs`, in both the permitted and forbidden cases.
4. `test_globs` resolves through the standard layered config path.
5. The lint rule fires on a computational section with no example and stays silent on prose,
   tables, code blocks and every existing spec in this repository.
6. The `tp validate` warning fires on the unexecutable split and not on a test task that adds
   coverage without invalidating anything.
7. The binary advisory fires once on a version mismatch, is silenced by `--quiet`, and never changes
   an exit code.
