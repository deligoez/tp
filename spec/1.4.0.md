# tp v1.4.0 — the epic writers and slices the field asked for

> Decision note (Decision track). The field findings it answers are recorded, in shape only, in
> `spec/1.3.0-measurements.md`; the v1.3.1 fixes already committed ship in this release too.

## Decision

The project that asked for the epic layer ran it on its own graph through four rounds of use: an
import, three review rounds over one milestone, and a topic built from zero. Every finding that
v1.3.0 did not fix and that is not the second release's binding work is answered here, in one
release:

1. **Edge writers.** `tp epic link <from> <to> "<why>"` adds the edge `from -> to` with its `why`, or
   replaces the `why` of the edge that exists; `tp epic unlink <from> <to>` removes it. Both run
   under the same lock and lint refusal as every writer, and their payload's `action` says what
   happened: `added`, `replaced` or `removed`. An absent `<from>` exits 4, as `set` does; an absent
   `<to>` and an empty `why` are lint errors (`dangling-reference`, `missing-why`) and exit 1;
   `unlink` of an edge that does not exist exits 4. An edge is the unit the field edited most —
   adding one edge or rewording one `why` — and `set <id> depends_on=<json>` made each such edit a
   read, modify and rewrite of the whole list.
2. **A revision guard.** A graph file's revision is, as a documented contract, the lowercase hex
   SHA-256 of its bytes, so a client computes it from the very bytes it read; an absent file's
   revision is the empty string. The graph writers — `add`, `set`, `remove`, `import`, `link`,
   `unlink`, `milestone add` — print the revision after their write and accept `--if-revision
   <hex>`, which exits 4 and writes nothing when the file's current revision differs: a stale read is
   a state conflict, as a lock timeout is. `tp epic lint` prints the revision it read, a convenience.
   Each writer's printed revision feeds the next `--if-revision`, so a chain of edits needs nothing
   more. Two edits made from one stale read silently reverted each other in the field.
3. **Several findings at once.** `tp epic review <slice> --resolve <i,j,...> <status> [evidence]`
   dispositions each listed index of the last round. Every index is checked before any row is
   written: one out of range or named twice exits 2, one already resolved exits 1 unless `--force`,
   and either changes no row. The payload carries `index` for one and `indices` for several.
4. **An explicit root.** An epic field `root: true` says the epic has no dependency on purpose;
   `no-dependencies` does not fire on it. `add` accepts the key, `set <id> root=true|false` sets it,
   and writers omit `root: false`. An epic marked root that has dependencies is the warning
   `root-with-dependencies`, so the mark cannot go stale silently. Some epics of a plan genuinely
   start from nothing, and a warning that cannot be answered trains its reader to skip warnings.
5. **Bulk refusals name the payload.** A refused `tp epic add --bulk` appends to each new error's
   message the 1-based payload line of every row whose epic the error names (`--bulk line 4`),
   counted as the bulk parse errors already count them; an error naming no payload row carries
   none. The hint points at the payload, not the file.
6. **A slice over a set of epics.** `tp epic review --epics <ids>` asks exactly those epics, plus the
   gate unit of each milestone whose every epic is listed, with context as for any slice. `<ids>` is
   comma-separated in CSV form, so an id holding a comma is quoted, and the flag may repeat. With
   `--name <name>` the slice's state is keyed by the kind and the name, so a set that grows between
   rounds keeps its round counter, cap and decisions, and carries every unchanged unit; without it,
   by the kind and the sorted, de-duplicated ids joined by NUL. `--epics x` and `--epic x` are
   different slices. An empty list exits 2 and an absent id 4; exactly one of `--milestone`,
   `--epic` and `--epics` is required, and `--name` without `--epics` exits 2. A topic spread over
   several milestones could only be reviewed as whole milestones — most of a round spent on epics
   nobody touched — or one epic at a time.
7. **Inserting a milestone.** `tp epic milestone add <name> --after <m> | --before <m> | --new-track`
   inserts one milestone into the track that holds `<m>`, or opens a new track with it, instead of
   rewriting every track through `set milestones`. Exactly one of the three flags is required (else
   exit 2); an absent `<m>` exits 4; a name the file already holds exits 1 by an explicit check, not
   through lint; `--new-track` on an absent file creates it. It prints the writers' payload.

## Why one release

The operator's instruction: every field finding is solved in one release rather than a release per
batch of findings. The v1.3.1 commits (earlier decisions shown to a re-asked unit, the cap hint,
the gate-only questions, Workflow E and README) ship inside it.

## Consequences

- The graph file's schema gains `root`; no other key. A file without it reads as before.
- Writer payloads gain `revision`, `link`/`unlink`'s also `action`; `tp epic lint` gains `revision`;
  `--resolve` gains `indices`. Nothing else in a payload moves.
- `--epics` is the third slice kind beside `--milestone` and `--epic`.
- SKILL.md's inventory and Workflow E, REFERENCE's epic section and exit table, and README's command
  index and Epic Graph section document each item.

## Non-goals

1. **A slice of what changed since a git ref.** The agent computes the set and passes it to
   `--epics`; with `--name` a growing topic needs it rarely.
2. **The second release's work**: binding a task file to an epic, derived status, `ready`, `claim`,
   `gate`, `status`.
3. **A revision on reads other than lint.** `tp epic export` prints Markdown for people.
4. **Renaming or removing a milestone through a new verb.** `set milestones` stays the general form.
5. **An in-place phrase swap** (`set <id> acceptance --replace <old> <new>`); `--if-revision` covers
   the lost update it would also prevent.
