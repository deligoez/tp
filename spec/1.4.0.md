# tp v1.4.0 — the epic writers and slices the field asked for

> Decision note (Decision track). The field findings it answers are recorded, in shape only, in
> `spec/1.3.0-measurements.md`; the v1.3.1 fixes already committed ship in this release too.

## Decision

The project that asked for the epic layer ran it on its own graph through four rounds of use: an
import, three review rounds over one milestone, and a topic built from zero. Every finding that
v1.3.0 did not fix and that is not the second release's binding work is answered here, in one
release:

1. **Edge writers.** `tp epic link <from> <to> "<why>"` adds the edge `from -> to` with its `why`, or
   replaces the `why` of the edge that exists; `tp epic unlink <from> <to>` removes it. Both run
   under the same lock and lint refusal as every writer. An edge is the unit the field edited most —
   adding one edge or rewording one `why` — and `set <id> depends_on=<json>` made each such edit a
   read, modify and rewrite of the whole list.
2. **A revision guard.** Every writer and `tp epic lint` print `revision`, the lowercase hex SHA-256
   of the file's bytes (after the write, for a writer). Every writer accepts `--if-revision <hex>`
   and exits 1 writing nothing when the file's current revision differs. Two edits made from one
   stale read silently reverted each other in the field; the guard turns that into a refusal.
3. **Several findings at once.** `tp epic review <slice> --resolve <i,j,...> <status> [evidence]`
   dispositions each listed index of the last round; one bad index refuses all of them.
4. **An explicit root.** An epic field `root: true` says the epic has no dependency on purpose;
   `no-dependencies` does not fire on it. Some epics of a plan genuinely start from nothing, and a
   warning that cannot be answered trains its reader to skip warnings.
5. **Bulk refusals name the payload.** A refused `tp epic add --bulk` names, for each new error, the
   payload lines whose epics it involves, and its hint points at the payload, not the file.
6. **A slice over a set of epics.** `tp epic review --epics <id,id,...>` asks exactly those epics,
   plus the gate unit of each milestone whose every epic is in the set, with context as for any
   slice. Its state directory is keyed by the kind and the sorted, de-duplicated ids, so a different
   set is a different slice. A topic spread over several milestones could only be reviewed as whole
   milestones — most of a round spent on epics nobody touched — or one epic at a time.
7. **Inserting a milestone.** `tp epic milestone add <name> --after <m> | --before <m> | --new-track`
   inserts one milestone into the track that holds `<m>`, or opens a new track with it, instead of
   rewriting every track through `set milestones`.

## Why one release

The operator's instruction: every field finding is solved in one release rather than a release per
batch of findings. The v1.3.1 commits (earlier decisions shown to a re-asked unit, the cap hint,
the gate-only questions, Workflow E and README) ship inside it.

## Consequences

- The graph file's schema gains `root`; no other key. A file without it reads as before.
- Writer payloads gain `revision`; `tp epic lint` gains `revision`. Nothing else in a payload moves.
- `--epics` is the third slice kind beside `--milestone` and `--epic`; exactly one of the three is
  required.
- SKILL.md's inventory and Workflow E, REFERENCE's epic section and README's command index and
  Epic Graph section document each item.

## Non-goals

1. **A slice of what changed since a git ref.** The agent computes the set with `git diff` and passes
   it to `--epics`; tp does not read history for this.
2. **The second release's work**: binding a task file to an epic, derived status, `ready`, `claim`,
   `gate`, `status`.
3. **A revision on reads other than lint.** `tp epic export` prints Markdown for people.
4. **Renaming or removing a milestone through a new verb.** `set milestones` stays the general form.
