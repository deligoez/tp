# tp v0.44.0 — What reading alone can decide

> Split from `spec/0.43.0.md`, whose own Non-Goal 9 named the identifier pass as one of the halves
> that should ship in a later number. It is independent of that release's measurements: nothing here
> reads a recorded round, and nothing there reads a spec's identifiers.
>
> §4 was added after the passes below were prototyped against this repository's own specs. Four of
> the five candidates did not survive that prototype, and recording which — and why — is the point
> of this file as much as the one rule that did.

## 1. Overview

Several of v0.35.0's most expensive findings needed no language model. `TP_RUN_DIR` anchored every
per-unit path in the spec and its value was never defined. `merged.ndjson` was consumed by a unit
brief and produced by nothing. A role file was written under one name and read under another. And a
single editing session on the pending specs found a withdrawn flag still required by three later
sections, and one numeric rule stated in opposite directions in two places.

Each is the same shape: **a spec contradicts itself, or references something it never introduces,
and the document alone settles it.** No corpus, no model, no execution.

This is the largest recorded finding family tp has. `spec/0.43.0.md` §2.2 already counts two of its
members — *a test disagrees with the section it pins* (24 findings, 4 slugs) and *two sections
disagree* (102 findings) — and the family is fragmented across slugs exactly as that section
predicts, with `test-contradicts-section`, `contradiction-across-sections`, `code-citation-drift`,
`recorded-fix-not-applied`, `fixed-repair-half-applied` and `invalidation-list-incomplete` all
naming it. A keyword sweep over the 3,047 recorded review findings matches contradiction phrasing in
854 of them, but **that number is a loose upper bound and must not be quoted as a measurement** —
this repository's own rule is that a keyword search is not evidence, and the phrasings it matches
(`but §`, `while §`) occur in prose that reports no contradiction at all. The slug list is the
independent corroboration; the 854 is not.

## 2. The identifier pass

`tp lint` gains an `identifiers` pass over a spec's code spans:

- An identifier is an environment-variable-shaped token matching `[A-Z][A-Z0-9_]{2,}`, or a
  path-like token containing `/` or ending in a known extension, or a `--flag`.
- **Identifiers are extracted from within code spans, not only from spans that consist of one.**
  A span such as `` `tp review <spec> --reconcile --note "<text>"` `` introduces two flags, and a
  matcher keyed on the whole span sees neither. §4 records what that mistake costs: it was the sole
  cause of every finding one refuted candidate produced.
- A span is an **introduction** when it appears in a table's first column, in a heading, or on the
  left of an `is`/`are` clause; every other appearance is a **reference**.
- A reference with no introduction anywhere in the file is reported `unintroduced-identifier`; an
  introduction with no reference is `unreferenced-identifier`.

Both are `info`, never `warning`, and neither ever gates. The pass is heuristic over prose and its
false-positive rate is unknown until it runs on tp's own corpus of shipped specs, which §6 makes a
precondition for shipping it. An `info` finding that a reviewer can ignore costs a line; a `warning`
that is wrong costs the operator's trust in the whole lint.

## 3. Contradictory comparators

**What must be true:** when a spec states one numeric rule twice with opposite comparators — *more
than three sections* in one place and *at most three sections* in another — the lint reports it.

This is the one candidate that caught the defect that motivated it. Run against the pending specs as
they stood before this cycle's repairs, it found the release whose §6 fired a recommendation above a
three-section threshold while its own test and its own gate section required the opposite, in the
same file, on the same rule — the defect took a full read of both sections to find by hand.

**The proxy is not the requirement, and the gap is measured.** The prototype grouped statements by
(number, noun) and flagged any group carrying both a greater-family and a lesser-family comparator.
Over every `spec/*.md` in the repository — 46 files at the time of measurement — that fired twice,
both in `spec/0.31.0.md`, and **both are false positives**: one pair is about `harness_stale` and the
other about `mechanize_candidates`, so they share a number and a noun while describing different
rules. A correct predicate has to establish that the two statements govern the **same subject**, and
naming that predicate is the design work this section owes. Two false positives across 46 files is a
tolerable rate for an `info` finding, so the naive proxy is a legitimate floor to ship from — but it
must be reported as the floor rather than as the rule.

## 4. What was prototyped and refuted

Five candidates were written and run over every `spec/*.md`, and against the pre-repair text of the
specs whose defects motivated them. Recording the four failures is what stops them being re-derived,
and each failed for a reason worth keeping.

| Candidate | Fired on corpus | Caught its motivating defect | Verdict |
|---|---|---|---|
| An identifier appearing only under a `Tests` heading | 3 findings, 3 files | no | refuted |
| Opposite comparators on one rule (§3) | 2 findings, 1 file | **yes** | ships |
| A stated count against the list that follows it | 4 findings, 4 files | no | refuted |
| A stated flag count against the file's flag set | 4 findings, 4 files | right line, wrong comparison | refuted |
| A claimed recorded-row field against the real key set | 53 findings, 9 files | no | refuted as a lint (§5) |

**Only-in-tests** looked like the natural catch for a withdrawn flag still required by a test
section. It is not: the withdrawn flag *was* named in a normative section, negatively, so the rule
was blind to its own motivating case. Worse, all three findings it did produce were artifacts of the
standalone-backtick bug §2 now forbids — each flag was introduced inside a longer command span the
matcher could not see. A rule whose entire yield is a parser defect is not a narrow rule.

**A stated count against the list that follows it** mechanizes this repository's most-repeated
rule — never assert a quantifier you did not count. The prototype's list counter mis-parsed
multi-line bullets and lead-ins that are not counts at all (*"One idea … arrived under 25 distinct
slugs"* is not a claim about the table beneath it), and it never caught the count that motivated it.
The idea is not refuted; this predicate is. A future attempt should be told that the corpus contains
lead-ins whose leading number quantifies something other than the list.

**A stated flag count against the file's flag set** reached the right line and is still refuted,
which is the more instructive failure. The claim in question was "four **new** flags"; the predicate
compared it against every flag the file mentions, which included flags that already shipped. It
would have reported the defect for a reason that is not the defect — and a rule that arrives at the
right answer through the wrong comparison passes a weak test and fails a real one.

## 5. The recorded-field check

The fifth candidate asked whether a spec claims a field that recorded rows do not carry — the shape
that let `spec/0.43.0.md` §6.1 build a replay baseline on a `disposition` no row has. It is not a
lint, and that is the finding rather than a technicality: **the document cannot settle it.** The
answer lives in `spec/.tp-review/`, which is exactly the phase a registered `workflow.checks` entry
runs in, so this is a check and belongs in `checks`, never in `tp lint`.

Its scope is narrower than it first appears, and the prototype measured both edges. The broad form —
any backticked identifier near any mention of a recorded row — produced 53 findings across 9 files,
of which two were true. Both true findings sat in an **enumeration** (*"those rows carry `role`,
`item_id`, `location`, …"*), and the phrasing that produced the original defect (*"read from the
recorded dispositions"*) is not an enumeration and was not caught. So the check verifies field names
inside an enumeration of row fields, it will not catch a field named in running prose, and saying so
is what keeps a later reader from trusting it further than it goes.

`CLAUDE.md`'s rule applies unchanged and is the reason this can be registered at all: a check whose
subject does not exist in the phase it runs in suppresses a finding class while verifying nothing.
The corpus exists during review, so this one is legitimate — which is precisely what the withdrawn
v0.34.0 §7.1 check was not.

## 6. The passes must not cry wolf

This gates the release rather than testing it afterwards, and it now covers two passes.

Run over every shipped spec in `spec/*.md`, neither pass may produce a finding on a spec that
shipped correct. The identifier pass must additionally produce the three v0.35.0 cases named in §1
when run against that spec at the round they were found — reconstructible from the recorded
snapshots. §3's rule must produce the pre-repair comparator contradiction, which is reachable
without any snapshot at all: it is in this repository's git history, one commit before the repair.

**One caveat on the reconstruction half, recorded so it is not discovered at decomposition.** The
snapshot corpus is not uniformly trustworthy: `CLAUDE.md` records that a quarter of the recorded
review rounds carry a snapshot whose sha256 is not the `spec_hash` that round recorded. The three
v0.35.0 cases must therefore be reconstructed from a snapshot whose hash is verified against its
round, or from the spec text at the commit the round was recorded — and if neither is available for
a given case, that case is dropped from the gate rather than assumed. §3's own gate is unaffected,
because git history is not the snapshot corpus.

## 7. Non-Goals

1. **No language model.** Both passes are regex and structure over the document.
2. **No cross-spec identifier resolution.** An identifier introduced in one spec and referenced in
   another is out of scope; each pass reads one file.
3. **Never a `warning`, never an exit code.** Every finding here is `info` and `tp lint` exits 0
   with them present.
4. **No change to the existing lint rules.** These are added passes, not a re-tuning of the rules
   whose low false-positive rate is the reason the lint is trusted.
5. **No revival of the four refuted candidates on the strength of §4 alone.** §4 records why each
   failed so a better predicate can be written, not so the same one can be retried.
6. **No general contradiction detector.** §3 is one numeric shape. *Two sections disagree* is the
   family; a rule that claimed the family would be the over-specification `spec/0.43.0.md` §2.2
   measures.

## 8. Tests

1. A spec introducing `TP_RUN_DIR` in no table, heading or `is` clause while referencing it reports
   `unintroduced-identifier`; introducing it clears the finding.
2. An identifier introduced and never referenced reports `unreferenced-identifier`.
3. An identifier that appears **only inside a longer command span** is extracted and is treated as
   introduced — the case §2 names and the case that produced every finding of a refuted candidate.
4. Both findings are `info`, and `tp lint` exits 0 with them present.
5. The comparator rule reports a file stating one rule as *more than N* and as *at most N*, and
   stays silent when the two statements govern different subjects — the `spec/0.31.0.md` pair is the
   fixture for the second half, since it is a measured false positive of the naive proxy.
6. Neither pass produces a finding on any shipped spec in `spec/*.md`.
7. Each of §1's three v0.35.0 cases is reproduced against a snapshot whose sha256 matches the
   `spec_hash` of the round it is taken from, or is recorded as dropped from the gate with the
   reason.
8. The recorded-field check reports a field named in a row-field enumeration that no recorded row
   carries, and is silent on a field named in running prose — the second half asserted so the
   check's blind spot is pinned rather than discovered.
