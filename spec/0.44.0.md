# tp v0.44.0 — `tp lint --identifiers`

> Split from `spec/0.43.0.md`, whose own Non-Goal 9 named this section as one of the two halves that
> should ship in a later number. It is independent of that release's measurements: nothing here
> reads a recorded round, and nothing there reads a spec's identifiers. The content is unchanged.

## 1. Overview

Several of v0.35.0's most expensive findings needed no language model. `TP_RUN_DIR` anchored every
per-unit path in the spec and its value was never defined. `merged.ndjson` was consumed by a unit
brief and produced by nothing. A role file was written under one name and read under another.

Each is the same shape: **a spec introduces an identifier and then references it, or references one
it never introduces.** That is decidable by reading the document, and every round spent on one is a
round a lint rule could have saved before the panel was ever emitted.

This is the cheapest item in the pending set and the only one whose whole cost is a heuristic's
false-positive rate, which is why §3 is a precondition rather than a test.

## 2. The pass

`tp lint` gains an `identifiers` pass over a spec's code spans:

- An identifier is a backticked token matching `[A-Z][A-Z0-9_]{2,}` (environment variables), or a
  path-like span containing `/` or ending in a known extension, or a `--flag`.
- A span is an **introduction** when it appears in a table's first column, in a heading, or on the
  left of an `is`/`are` clause; every other appearance is a **reference**.
- A reference with no introduction anywhere in the file is reported `unintroduced-identifier`; an
  introduction with no reference is `unreferenced-identifier`.

Both are `info`, never `warning`, and neither ever gates. The pass is heuristic over prose and its
false-positive rate is unknown until it runs on tp's own corpus of shipped specs, which §3 makes a
precondition for shipping it. An `info` finding that a reviewer can ignore costs a line; a `warning`
that is wrong costs the operator's trust in the whole lint.

## 3. The pass must not cry wolf

This gates the release rather than testing it afterwards.

Run over every shipped spec in `spec/*.md`, `tp lint --identifiers` must produce zero
`unintroduced-identifier` findings on specs that shipped without one, and must produce the three
v0.35.0 cases named in §1 when run against that spec at the round they were found —
reconstructible from the recorded snapshots. A pass that cannot find the defects that motivated it
does not ship; one that fires on shipped, correct specs does not ship either.

**One caveat on the reconstruction half, recorded so it is not discovered at decomposition.** The
snapshot corpus is not uniformly trustworthy: `CLAUDE.md` records that a quarter of the recorded
review rounds carry a snapshot whose sha256 is not the `spec_hash` that round recorded. The three
v0.35.0 cases must therefore be reconstructed from a snapshot whose hash is verified against its
round, or from the spec text at the commit the round was recorded — and if neither is available for
a given case, that case is dropped from the gate rather than assumed. The zero-false-positive half
needs no history and carries the gate on its own.

## 4. Non-Goals

1. **No language model.** The pass is regex and structure over the document.
2. **No cross-spec identifier resolution.** An identifier introduced in one spec and referenced in
   another is out of scope; the pass reads one file.
3. **Never a `warning`, never an exit code.** Both findings are `info` and `tp lint` exits 0 with
   them present.
4. **No change to the existing lint rules.** This is an added pass, not a re-tuning of the rules
   whose low false-positive rate is the reason the lint is trusted.

## 5. Tests

1. A spec introducing `TP_RUN_DIR` in no table, heading or `is` clause while referencing it reports
   `unintroduced-identifier`; introducing it clears the finding.
2. An identifier introduced and never referenced reports `unreferenced-identifier`.
3. Both are `info`, and `tp lint` exits 0 with them present.
4. `tp lint --identifiers` produces no `unintroduced-identifier` on any shipped spec in `spec/*.md`.
5. Each of §1's three v0.35.0 cases is reproduced against a snapshot whose sha256 matches the
   `spec_hash` of the round it is taken from, or is recorded as dropped from the gate with the reason.
