# tp v0.46.0 — What v0.36.0's audit handed over

> Split from the backlog release, which now ships as `spec/0.39.0.md`, when the pending specs were
> divided into independently releasable pieces. That file carries the v0.35.0 backlog; the items
> here have a different provenance — v0.36.0's own audit rounds — and a different precondition,
> since most of them are defects in code that release was still changing. Round 8 added one more
> after the split; the rest is unchanged.

## 1. Overview

One item per section below (§2–§6), each measured to a conclusion during v0.36.0's audit and each
deliberately not repaired there, because an audit repair that introduces new surface belongs to the next version rather than
to the audit. They are recorded with their derivations so this release does not re-derive them, and
so the decision to defer stays visible rather than becoming an omission.

Like `spec/0.39.0.md` this release introduces no mechanism and no new vocabulary. Unlike it, every
item here names a specific file and a specific measured behaviour, so decomposition is close to
mechanical: one task per item, each reproducing the defect before the fix.

## 2. A `--role` refusal writes state before it refuses

`tp audit <spec> --role <unknown>` exits 2 and leaves `snapshot-audit-round-N.md` behind;
`tp review` leaves both the snapshot and `state.json`, and `--status` then reports
`in_flight_round: 1` where a clean tree reports `null`. `--role ""` does the same. Both files state
the refusal-before-writes discipline in their own comments (v0.32.0 §2.5); v0.36.0's `--role` is the
one refusal placed after them.

The ordering is **not** forced, and that was proved rather than argued: `generateRoleAuditPrompts`
puts every `panel.roles` entry into either `prompts` or `skipped`, and `appendClausesAudit` adds no
role, so a name in the panel can never reach the unknown class. The exit-2 branch therefore needs
only `panel.roles` (plus `regression` on the review side), `panel.fm.Domain`, `panel.disabled` and
the spec directory — all in hand right after `resolveRolePanel`, which runs before `loadAuditSpec`
and before `loadReviewRoundState`. Moving it there also moves the hint's source from the emitted set
to the panel, a superset that still contains every emitted name, so
`TestUnknownRoleExitsTwoWithTheEmittedNames` survives unchanged.

It is a control-flow change across two commands and a hint's source — which is why it was not made
during a convergence — and it is a defect in code v0.36.0 touched but not something v0.36.0's spec
requires.

## 3. `check-suite-state.sh` cannot see an empty watched directory

BSD `xargs` runs nothing on empty input, so `spec/.tp-review/` present-but-empty hashes identically
to absent (`e3b0c442…852b855`, the sha256 of nothing). `engine.clearUnitArtifacts` does exactly that
`MkdirAll`. It is also platform-divergent: GNU `xargs` runs the command once on empty input, so the
local gate and CI disagree at this boundary — reasoned, not measured, since no GNU xargs was
available.

The blindness is to **directory-only** changes and reaches a sub-directory too — round 5 measured
`mkdir -p .tp/rounds/round-99` passing while a one-byte append to `state.json` is caught. Every file
written under either watched path is still caught, and review state lives in files, so the wrapper's
actual hazard is detected. v0.36.0 corrected the script's comment, which had claimed the opposite,
and left the mechanism.

**What this release owes is the decision, not the patch.** The mechanism is correct for the hazard
it was built for; the item is open because nobody has said whether directory-only blindness is worth
closing. Closing it means hashing the directory listing alongside the file contents, which is a
handful of lines and one more thing the gate can be wrong about. Deciding to leave it, in writing,
closes the item as legitimately as changing it.

## 4. Two CI guards are narrower than their own claims

`ci_gate_test.go` matches each gate step with `strings.Contains` over the whole `ci.yml`, so a step
named only in a YAML comment satisfies it — demonstrated with a scratch workflow, latent today
because all four steps sit on `run:` lines. `TestSuiteStateWrapperStillRunsTheRaceDetector` has the
same file-wide haystack. And `ci_pin_test.go`'s `goInstallRef` matches only `go install <mod>@<ref>`,
leaving `go-version: stable`, `checkout@v4` and `setup-go@v5` unmeasured — the compiler being the
gate's largest floating input, and the exact class the file's own comment describes. It also walks
only `*.yml`, so a `*.yaml` workflow would be skipped while its `checked > 0` guard still passed.

**The reason nobody noticed is worth more than either instance: `checked > 0` is a GLOBAL guard.** A
workflow contributing zero matches is indistinguishable from one that is fully pinned, because
`ci.yml`'s three refs satisfy the assertion alone. `release.yml` is the case that makes it matter —
it contributes zero, so the workflow that builds the **shipped binaries** is unmeasured while the
guard reports success. Round 5 proved it by floating every ref in `release.yml` and watching the
test still pass. A per-file counter, or extending the regex to `uses:` refs, is the fix.

Scope, measured rather than assumed: `release.yml` is not worse *in kind* than `ci.yml` — its
`checkout@v4`, `setup-go@v5` and `goreleaser-action@v6` are mutable major tags of the same class,
and `go-version: stable` is the identical line `ci.yml` carries. It is worse in *impact*, because
the output is what users install rather than a pass/fail signal. It has not been touched since
`84bb505`, long before that cycle.

## 5. A gate test is load-sensitive

`TestRoleWriteHookStaysCheapOnADeepMissingPath` (v0.35.0) asserts `deep < 3*shallow` on wall-clock
and failed one of four full gate runs during v0.36.0's implementation, at a measured ratio of 3.198
(deep 56.95 ms, shallow 17.82 ms). The design is right — a ratio rather than a deadline,
fastest-of-three each side — but the constant sits close to the noise floor: the test's own comment
records bounded as "within noise" and unbounded as ~6×, leaving only a 2× margin. It will randomly
redden the release gate until the constant widens or the sample grows.

## 6. A round's own findings file is written non-atomically

`WriteSnapshotAtomic` was made atomic in v0.36.0's audit round 7 because eight sibling role units
write the spec snapshot at once. The **findings** file beside it was not: `review-round-N.ndjson`
is written with a plain `os.WriteFile` at both call sites, so a reader that opens it while a writer
is mid-write sees a partial file.

Measured under the same eight-way arrangement as round 7's snapshot race: **23 torn reads in 18,093
reads**, all of them 0-byte — the window is `os.WriteFile`'s truncate-then-write, so a torn read is
an empty read rather than a half-written row. That is why it has gone unnoticed: an empty findings
file is indistinguishable from a round that recorded nothing, and `--merge` treats it as such
instead of failing.

The fix is one line at each site — `engine.writeFileAtomic`, the helper round 7 already added and
`WriteSnapshotAtomic` already uses. It is separated from that round's fix rather than folded into
it because round 7's evidence was about the snapshot's *shared temp path*, and this is a different
defect (no temp file at all) reached by the same concurrency.

Written at decomposition, one per item, each reproducing the defect before the fix — §4's two guards
