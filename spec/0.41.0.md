# tp v0.41.0 — The divisible round

## 1. Overview

A round's unit of work is "one role × every affected file × every checklist item". That unit is
indivisible: `--affected-files` narrows the files but not the checklist, and nothing says "re-check
only what changed since round N" or "only what was not `PASS` last time".

Two costs follow, both measured on a field cycle running nine rounds over a PHP package:

**Round length is set by the slowest single agent.** Round 7 wall times: test-isolation 44 min,
spec-coverage 29 min, security 22 min, docs-skill-sync 10 min, maintainability 8 min. The operator
then dropped a role for round 9 — and the round did not get shorter: test-isolation 35 min,
spec-coverage 33 min. Trimming roles buys nothing because the two long poles are internal to one
prompt. `overlap_report` showed zero shared findings across all four remaining roles, so the dropped
role was not redundant either; the round simply cannot be shortened from the outside.

**Every round re-derives the whole surface.** Finding counts across rounds 3–9 ran 31 → 20 → 15 → 17
→ 23 → 30 → 28. Rounds 6 and 7 found genuine correctness defects, so this is not pure churn — but a
large share of each round's growth is the *previous round's fixes* being audited for the first time,
at full depth, alongside everything already checked five times. Nothing separates new surface from
settled surface, so the trajectory cannot be read.

This release makes the round divisible. It is placed after `spec/0.40.0.md` deliberately: that
release measures where a round's cost actually goes, and sharding is the expensive answer to a
question the measurement should be allowed to ask first.

## 2. Sharding a role's checklist

The non-`spec-coverage` roles already receive one `file_check` item per file, so their cost grows
linearly with the file list and shards trivially. `spec-coverage` is the hard case: one 73-item
checklist from a 48 KB prompt, each item verified by execution.

**Mechanism, open in one respect.** A role whose checklist exceeds a threshold is emitted as several
prompts over disjoint item sets, each producing its own findings file, merged as today. What is not
decided is the split key — by item count, by prompt bytes, or by the item's own `type` (`file_check`
shards cleanly, `task_acceptance` may not) — and the answer should come from `spec/0.40.0.md`'s
measurement rather than from a guess made here.

**What must hold however it is decided.** The merged result of N shards is the same set of rows a
single unit would have produced; no item is dropped at a boundary; no item is judged twice; and the
per-role overlap report still attributes each row to one role.

## 3. Incremental rounds

`tp audit --since <round>` or `--only-open`: re-check what changed since a named round, or what was
not `PASS` last round, rather than the whole surface.

**The hazard is this release's own, and it is the v0.34.0 §7.1 shape.** Anything that narrows what a
round examines can hide a finding the full pass would have made. A settled item is settled against
the code as it was; a repair three rounds later can unsettle it silently. So an incremental round is
**uncounted for convergence** unless it can show that the surface it skipped is unchanged — which
means the skip predicate has to be derived from something tp can see (the affected-file set, a
content hash), never from the previous round's verdict alone.

## 4. A durable home for an accepted finding

An audit finding has three ends: fix it, reject it, accept it as backlog. tp records all three the
same way, in `.tp-review/<spec>/`, which is archived at release along with the spec. There is no
supported path from "accepted" to something a maintainer trips over later — no issue, no checklist
entry, no failing marker.

The field cycle names the symptom precisely: four of five round-6 items were answered by editing the
spec's own §12 rather than the code, and "given that the spec file is version-prefixed and archived
at release, that pattern converts findings into history rather than into maintenance pressure." A
deferral whose stated reason is self-renewing can be re-derived every round forever, and its only
record is scheduled for archival on the very release it is deferred past.

This repository has been working around it by hand for four cycles: `spec/<version>-candidates.md`
is that durable target, maintained manually, and `spec/0.38.0.md` exists because someone read one.

**Mechanism.** `tp audit` emits accepted findings to a durable target outside the archived round
directory. The target's shape is open — a checklist file, an issue template, a TODO with an owner —
and the candidates files are the worked example of what the emitted thing has to be good enough to
replace.

**Bound.** `spec/0.37.0.md` §3 already stops an accepted row from blocking convergence. That is the
counting half and it ships first because convergence needs it; this is the durability half. Neither
repeats the other.

## 4a. A round in flight reports how far along it is

§1's measurement — round length set by the slowest single agent, and dropping a role buying nothing —
has a second cost this spec has so far only implied: **while that slowest agent runs, nothing reports
that anything is happening at all.** An operator watching a 44-minute round sees the same thing at
minute 2 and minute 40.

The information already exists and is already half-reported. Measured during v0.36.0's own audit
round 5, mid-flight:

```
tp audit <spec> --status   →  "in_flight_round": 5
round directory            →  4 prompts emitted, 0 role files written
```

So `--status` knows a round is **open** and cannot say it is **four-zeroths done**, while the two
numbers sit in the round directory it already resolves. The emitted count is the payload's
`prompts[]` length; the written count is the files satisfying `spec/0.35.0.md` §3.3's predicate —
the same predicate `engine.roundBasedUnits` already applies to decide which roles still need
spawning. Nothing new has to be computed or stored.

**What must be true:** when `--status` reports a non-null `in_flight_round`, it also reports that
round's progress — how many role files that round expects and how many satisfy the predicate — and
names the roles still outstanding. Both commands, since both have in-flight rounds.

**Why it belongs to this release rather than to the driver.** `tp run --status` already reports units
done against caps, and that is the answer *when a run is driving*. It is silent for the interactive
fallback `skills/tp/SKILL.md` sanctions — one subagent per unit, spawned by an orchestrator — which
writes no run state. v0.36.0's entire audit ran that way, five rounds, four units each, and the
operator's only signal was the orchestrator saying it had spawned them. The fallback is not a
degraded mode to be discouraged into using the driver; SKILL.md names three legitimate reasons for
it, and human-in-the-loop repair between rounds was the one in play. A phase-level signal that does
not depend on who spawned the units is what covers both.

**Non-goal: a progress bar.** No percentage, no ETA, no per-unit heartbeat. A count and a list of
outstanding roles is decidable from disk at read time; anything finer needs the units to report, and
a unit that reports progress is a channel this release does not build.

## 5. Non-Goals

1. **Changing what an item asks.** Sharding splits the checklist; it does not rewrite items.
2. **Convergence arithmetic.** `spec/0.37.0.md`.
3. **Prompt self-sufficiency and `--out-dir`.** `spec/0.36.0.md`. A prompt that can be written to a
   file is a precondition here, which is why that ships first.
4. **Deciding the split key before the measurement exists.** §2 states the requirement and leaves
   the key to `spec/0.40.0.md`'s data. Fixing it here would be a guess wearing a specification's
   clothes.
5. **Making an incremental round count for convergence by default.** §3.

## 6. Tests

Written at decomposition. §2's split key and §4's target shape must be decided first; §3's tests can
be written today, because its requirement — an incremental round does not advance convergence unless
the skipped surface is provably unchanged — is stated fully.

A gate this release owes itself, borrowed in form from `spec/0.40.0.md` §8 and applicable here for
the same reason: sharding and incremental rounds are both mechanisms that narrow what reviewers see.
Neither ships until it is replayed against the recorded rounds in `spec/.tp-review/` and shown not to
lose a finding the whole-surface pass produced.
