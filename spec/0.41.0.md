# tp v0.41.0 — A durable home for an accepted finding

> Split from the release that became `spec/0.48.0.md`, where this sat under a title about sharding a
> round. It is independent of that work and depends instead on `spec/0.37.0.md` §3, which ships
> first: that release stops an accepted finding from blocking convergence, and this one gives it
> somewhere to live. The content is unchanged.

## 1. Overview

An audit finding has three ends: fix it, reject it, accept it as backlog. tp records all three the
same way, in `.tp-review/<spec>/`, which is archived at release along with the spec. There is no
supported path from "accepted" to something a maintainer trips over later — no issue, no checklist
entry, no failing marker.

The field cycle names the symptom precisely: four of five round-6 items were answered by editing the
spec's own §12 rather than the code, and "given that the spec file is version-prefixed and archived
at release, that pattern converts findings into history rather than into maintenance pressure." A
deferral whose stated reason is self-renewing can be re-derived every round forever, and its only
record is scheduled for archival on the very release it is deferred past.

This repository has been working around it by hand for four cycles: `spec/<version>-candidates.md`
is that durable target, maintained manually, and `spec/0.39.0.md` exists because someone read one.

## 2. Mechanism

`tp audit` emits accepted findings to a durable target outside the archived round directory.

**The target's shape is open,** and the candidates files are the worked example of what the emitted
thing has to be good enough to replace. Three honest options, none chosen here:

1. A checklist file at a stable path, appended to rather than rewritten.
2. An issue template written to disk for the operator to file.
3. A `TODO` entry with an owner and the finding's `item_id`.

What decides between them is a property rather than a preference: **the target must be readable by
the next cycle's decomposition without a human remembering it exists.** `spec/0.39.0.md` was written
because somebody happened to open a candidates file; that is the failure mode, not the success case.
An option that only works when read is not better than the round directory it replaces.

## 3. What this release does not decide

`spec/0.37.0.md` §3 already stops an accepted row from blocking convergence. That is the counting
half and it ships first because convergence needs it; this is the durability half. Neither repeats
the other, and this file adds no counting rule of any kind.

## 4. Non-Goals

1. **No convergence effect.** An accepted finding's blocking behaviour is `spec/0.37.0.md` §3.
2. **No `scope` field.** Deferred since v0.33.0 and not reopened here; `spec/0.37.0.md` Non-Goal 1
   carries the reasoning.
3. **No automatic filing.** tp writes a local artifact. It opens no issue, calls no API and needs no
   credentials.
4. **No migration of the existing candidates files.** They stay as they are; this release is judged
   on whether a new accepted finding lands somewhere durable, not on backfilling four cycles.

## 5. Tests

Written at decomposition, after §2's target shape is decided — a test written now would pin the
guess.

One test can be written today, because §2 states its requirement fully: an accepted finding emitted
to the durable target is still present after the round directory is archived, proven by archiving it
in a fixture and reading the target back.
