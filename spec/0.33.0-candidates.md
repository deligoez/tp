## 1. Scope-aware audit convergence — the headline

Spec review has a severity-aware predicate (`review_converge_on=blocking`). Audit has nothing:
**every non-PASS row counts against convergence, whether it concerns the spec or the codebase at
large.** The general lenses (`go-safety`, `maintainability-conventions`, `ax-contract`) always find
something in a real codebase, so under that rule there is no fixed point. In v0.32.0's own audit,
`spec-coverage` — the only role measuring conformance — was 55/55 clean from round 2 through round
11 and no round ever produced a FAIL, while rounds 3–11 were consumed by hint wording, advisory
channels, git scoping and flag hygiene the spec never mentions. Each repair round also created
fresh surface for the next round to audit.

Design:

- Audit rows gain a **`scope`** field: `spec` | `codebase`. tp owns the finding contract, so the
  auditor prompt must ask for the classification and `audit_schema.go` must carry it.
- **`audit_converge_on`** (`spec` | `all`, default `spec`) decides which rows gate. `codebase` rows
  are still recorded and surfaced as a visible backlog rather than silently dropped.
- **`tp audit --record` / `--status` must surface the divergence**: "spec-coverage clean 9 rounds;
  24 codebase-scoped findings open". In v0.32.0 that signal had to be derived by hand at round 10;
  it should have arrived at round 3. This is the part that actually prevents the failure — the rest
  is policy the driver could already have applied.

Consider the same for `tp review`: a reviewer role commenting on code style rather than the spec has
the same shape.

## 2. `output.Error` does not exit

`runAuditStatus` emits `{"error":…,"code":3}` and still returns 0 when `output.JSON` fails;
`review_status.go` and `claim.go` share the shape. `validate.go` has the correct form (Error then
`os.Exit`). Reachable only on a stdout write failure, where EPIPE usually kills the process first —
which is why it was accepted rather than fixed mid-audit. Three-file sweep.

## 3. Raw-stderr advisories outside the audit path

~25 sites still write advisories with bare `fmt.Fprintf(os.Stderr, …)`, so `--quiet` cannot silence
them while their converted siblings honour it: `review_merge.go`, `audit_merge.go`, `review_record.go`
(partially done), `set.go`, `add.go`, `commit.go`, `done.go`, `config.go`, `validate_project.go`,
`changewarn.go`, `commitstrategy.go`, `engine/configresolve.go`, `engine/discover.go`. `audit.go`,
`audit_roles.go` and both `--record` paths are already clean. Converting the rest changes six
commands' stderr contract, so it wants its own pass with its own tests.

## 4. A mistyped override *key* is silent in review/audit

`enbaled: false` (for `enabled:`) produces a lint warning that only `tp lint` consumes —
`resolveRolePanel` discards `fm.Warnings`. §2.1 calls it "a lint warning", so v0.32.0's behaviour
matches its spec, but the failure mode is the same one `output.Notice` was adopted to close for a
mistyped role *id*: the user asked for something and silently did not get it. Surfacing it in the
emission path is a new advisory, not a channel move.

## 5. A registered check does not clear its `mechanize_candidates` suggestion

Found during v0.31.x. Registering a `checks` entry for a recurring class should retire the
suggestion that told you to write it; it currently keeps recommending a check that already exists.

## 6. `tp review --resolve-all --severity <sev>`

From field feedback (the strongest item in that batch). Accepting all surviving low/medium findings
under one justification is the documented convergence move, but `--resolve-all` currently takes the
whole file; a severity filter makes it usable without hand-editing NDJSON.

## 7. Cross-repo specs

A spec whose tasks run in two repositories (backend + frontend) is how at least one team already
works: plan in one repo, run agents in both. v0.32.0 listed per-task role scoping as a non-goal
because the corpus resolves per spec. Worth a design pass — the file-selection and `commit_shas`
paths both assume one repo root.

## 8. Audit repairs should not grow the change surface

Process, not code, but it belongs here: a repair that introduces a new abstraction (v0.32.0's
`output.Notice` migration, `noticeOnce`, `rolelessRows`) is the next version's task, not an audit
repair — each one became the next round's audit surface. Recorded in `CLAUDE.md`; item 1 is what
makes it enforceable rather than advisory.
