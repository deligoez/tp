# v0.35.0 candidates

Carried from the v0.34.0 review. Items here are findings that cycle accepted with recorded
justification because its own Non-Goals fenced them out, not defects anyone judged harmless.

## 1. `next_action` recommends a registration the phase cannot honour

Found by the regression role in v0.34.0's round 17, accepted low.

`tp review <spec> --status` returns a `next_action` telling the driver to register a mechanical
check for a recurring finding class, chosen on class frequency alone (`nextaction.go`, precedence
step 3). v0.34.0 §7.1 records the case where that advice is wrong: a check registered in a phase
where the thing it measures does not yet exist suppresses the class for every reviewer while
verifying only whatever part of its subject already exists. That release corrects the rule in
`CLAUDE.md` (§8.1) but cannot correct tp's own emitter — Non-Goal 1 fences it out.

It matters for v0.35.0 specifically: the unattended driver is the consumer of `next_action`, so an
unattended run would follow the recommendation without the human who caught it here. The fix is not
obvious — tp cannot tell from the class alone whether the artifact exists in the current phase — so
the honest options are to soften the wording, to condition it on something tp can observe, or to
drop the recommendation and let the operator decide.

**Second half, found during v0.34.0's implementation.** The same unconditional advice is documented,
not just emitted: `skills/tp/SKILL.md`'s mechanize-candidate rule and its Workflow D step 3 both
tell the reader to register a check for a recurring class, with no phase qualifier. v0.34.0 §8.1
scoped its correction to `CLAUDE.md`, so the lesson now lives in the one document only this
repository reads while every tp user still gets the unqualified version. Whatever v0.35.0 does to
the emitter should carry to SKILL.md in the same task, or the tool and its manual will disagree.

## 2. `quality_gate` is settable at the project layer, and tp says it is not

Found during v0.34.0's implementation, verified end to end in a throwaway repo.

`tp set --workflow quality_gate=…` exits 2 with an error saying the field is "authored only by
tp init", and `skills/tp/REFERENCE.md` repeats that. But `tp set --workflow --project
quality_gate=…` is accepted and writes `.tp/config.json`: `runSet` routes `--project` to
`runSetProjectWorkflow`, which never consults `readOnlyWorkflowFields`.

The behaviour is defensible — the task-level value is init-authored, the project default is not —
but the message and the reference both state the narrower rule as if it were the whole one, so a
reader looking for a supported route concludes there is none. v0.34.0's `gate-overrides` task spent
its time on that conclusion before measuring otherwise. Non-Goal 3 fenced the fix out of that
release: it is a message and a document, not a behaviour change.

## 3. Wrong argument counts exit 1, while unknown commands now exit 2

v0.34.0 §9.1 made an unrecognised command name a usage error at exit 2. It scoped itself to the
name, so the neighbouring case stayed as it was: `tp show` with too few arguments, or any command
whose `ExactArgs`/`RangeArgs` is violated, still exits 1 — the code tp uses for "ran and failed".
`tp completion bash extra` is the same shape from cobra's own built-in.

An arity violation is a usage error by every definition §9 gives, so the contract now splits a
single idea across two exit codes and an agent cannot tell "you typed it wrong" from "it ran and
failed" without reading the message. Fixing it is a behaviour change across every command's `Args`
validator, which is why v0.34.0 fenced it out rather than widening its own section mid-release.

## 4. `tp init`'s already-exists hint recommends `tp init`

When a task file already exists, `tp init` exits 3 and hints `run 'tp use <file>' … or 'tp init
<spec>' to create one` — the second half names the command that just failed for that exact reason.
An agent following the hint loops.

v0.34.0's §9 sections each named their own command, and none of them named `init`, so the unit that
found this reported it rather than widening its task. The fix is one string, but it belongs with a
pass over hints that recommend an action the caller has already taken — worth checking whether
`init` is the only one.
