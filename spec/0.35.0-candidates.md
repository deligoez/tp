## 1. `next_action` recommends a registration the phase cannot honour

Found by the regression role in v0.34.0's round 17, accepted low.

`tp review <spec> --status` returns a `next_action` telling the driver to register a mechanical
check for a recurring finding class, chosen on class frequency alone (`nextaction.go`, precedence
step 3). v0.34.0 §7.1 records the case where that advice is wrong: a check registered in a phase
where the thing it measures does not yet exist suppresses the class for every reviewer while
verifying only whatever part of its subject already exists. That release corrects the rule in
`CLAUDE.md` (§8.1) but cannot correct tp's own emitter — Non-Goal 1 fences it out.

It matters for v0.35.0 specifically: the unattended driver is the consumer of `next_action`, so an
unattended run would follow the recommendation without the human who caught it here. The fix is not
obvious — tp cannot tell from the class alone whether the artifact exists in the current phase — so
the honest options are to soften the wording, to condition it on something tp can observe, or to
drop the recommendation and let the operator decide.

**Second half, found during v0.34.0's implementation.** The same unconditional advice is documented,
not just emitted: `skills/tp/SKILL.md`'s mechanize-candidate rule and its Workflow D step 3 both
tell the reader to register a check for a recurring class, with no phase qualifier. v0.34.0 §8.1
scoped its correction to `CLAUDE.md`, so the lesson now lives in the one document only this
repository reads while every tp user still gets the unqualified version. Whatever v0.35.0 does to
the emitter should carry to SKILL.md in the same task, or the tool and its manual will disagree.

## 2. `quality_gate` is settable at the project layer, and tp says it is not

Found during v0.34.0's implementation, verified end to end in a throwaway repo.

`tp set --workflow quality_gate=…` exits 2 with an error saying the field is "authored only by
tp init", and `skills/tp/REFERENCE.md` repeats that. But `tp set --workflow --project
quality_gate=…` is accepted and writes `.tp/config.json`: `runSet` routes `--project` to
`runSetProjectWorkflow`, which never consults `readOnlyWorkflowFields`.

The behaviour is defensible — the task-level value is init-authored, the project default is not —
but the message and the reference both state the narrower rule as if it were the whole one, so a
reader looking for a supported route concludes there is none. v0.34.0's `gate-overrides` task spent
its time on that conclusion before measuring otherwise. Non-Goal 3 fenced the fix out of that
release: it is a message and a document, not a behaviour change.

## 3. Wrong argument counts exit 1, while unknown commands now exit 2

v0.34.0 §9.1 made an unrecognised command name a usage error at exit 2. It scoped itself to the
name, so the neighbouring case stayed as it was: `tp show` with too few arguments, or any command
whose `ExactArgs`/`RangeArgs` is violated, still exits 1 — the code tp uses for "ran and failed".
`tp completion bash extra` is the same shape from cobra's own built-in.

An arity violation is a usage error by every definition §9 gives, so the contract now splits a
single idea across two exit codes and an agent cannot tell "you typed it wrong" from "it ran and
failed" without reading the message. Fixing it is a behaviour change across every command's `Args`
validator, which is why v0.34.0 fenced it out rather than widening its own section mid-release.

## 4. `tp init`'s already-exists hint recommends `tp init`

When a task file already exists, `tp init` exits 3 and hints `run 'tp use <file>' … or 'tp init
<spec>' to create one` — the second half names the command that just failed for that exact reason.
An agent following the hint loops.

v0.34.0's §9 sections each named their own command, and none of them named `init`, so the unit that
found this reported it rather than widening its task. The fix is one string, but it belongs with a
pass over hints that recommend an action the caller has already taken — worth checking whether
`init` is the only one.

## 5. Three gaps v0.34.0's sweeps measured but were not scoped to close

All three came out of mutation testing during v0.34.0 and were reported rather than fixed, because
closing them means adding tests or merging code that no section of that release mandates.

**Two values no test discriminates.** Mutating `readFilesContent`'s per-file 5000-byte cap, and the
5-second lock-timeout fallback, leaves the whole suite green. Both were literals before v0.34.0
inlined them, so this is a pre-existing gap, not something the inlining introduced — but a sweep
that measures a value and finds nothing guarding it has produced exactly the evidence a guard test
should be written from.

**A duplication below the detector's threshold.** `runReviewDocPlan` and `runReviewTestPlan` in
`internal/cli/review.go` are near-identical prompt builders differing mainly in one cap. `dupl` at
its configured threshold does not flag them, so §6.1's sweep never saw them. Worth deciding
deliberately: either they merge, or the threshold is the wrong instrument for this pair.

Two smaller drifts from the same file, recorded so they are not rediscovered: the `§3.x` and test

## 7. `tp audit` reports a truncated file set as a complete one

The strongest finding of v0.34.0's audit round 1, measured on the shipped binary.

Auto-detect caps the audited file set at 50 and says so in one stderr line. On this release that
dropped 63 of 113 changed files, including **all four documentation files** — the exact surface §8.2
and §8.3 changed — and `internal/engine/lock.go` with both lock tests, the subject of §3. Four
things make it a contract defect rather than a cosmetic one:

- The payload carries no truncation flag, and `file_summary.total_files` reports **50** — the cap,
  not the 113 that changed. An agent parsing stdout alone reads a complete-looking result.
- `--quiet` erases the only signal while the exit code stays 0. `output.Notice` returns early on
  quiet, which is the failure the Notice-vs-Info comment in `audit.go` was written to prevent,
  reintroduced through the other suppression path.
- "more than 50 files changed" reads identically at 51 and at 113, so the agent cannot size the
  damage or the `--affected-files` workaround.
- Selection is lexicographic, so which files survive is an alphabetical accident.

Worth recording precisely because the obvious fix is the wrong one: excluding tp's own
`spec/.tp-review/` records does not help. Those sort after `internal/` and were dropped too;
removing them still leaves 75 candidates over a 50 cap. The fix that generalizes is a `truncated`
and `total_changed` field in the payload plus a count in the notice — a feature change, which is
why v0.34.0 fenced it out and worked around it with an explicit `--affected-files` list.

## 8. Smaller audit findings v0.34.0 measured and deferred

Each was verified, each is a behaviour or message change that §11 keeps out of a maintenance
release.

- `internal/engine/lock.go` swallows `EnsureTPGitignore`'s error with `_ =`, on the very mechanism
  its own comment says keeps `.tp/locks/*.lock` out of the working tree — so a failure silently
  reproduces the symptom the call was added to prevent. `errcheck` cannot see it (`check-blank` is
  off). Aborting would be wrong; a stderr warning is the honest minimum.
- `internal/cli/validate_project.go` drops `ScanProjectTaskFiles`' walk error, so a partial walk
  reports a partial deviation list and exits 0 — a silently partial "clean". Pre-existing, not
  introduced by v0.34.0.
- §9.2's exemption list is shared across both hint channels, so `config.go`, `config_extract.go`,
  `set_local.go` and `set_project.go` still offer task-file advice for a `.tp/config.json` object.
  Closing it means repairing 13 hintless exit-3 sites in the same files.
- The hint enumeration is blind to a bare `os.Exit(ExitValidation)` that never goes through
  `output.Error` — `validate.go` and `validate_project.go` both do this deliberately, as a
  report-exit convention where the payload is the message. Not a defect, but the guard should say
  it, since it is the second blind spot after the hint-variable one v0.34.0 fixed.

## 9. Two spellings of one path take two different locks

Found in v0.34.0's audit round 2 and demonstrated on the shipped binary, not argued from source.

`LockFilePath` hashes `filepath.Abs(target)`, which is purely lexical, so a symlinked spelling of
the same directory hashes to a different lock file. With a holder on the `/private/tmp/…` lock, the
same `tp add`, from the same working directory, against the same physical `spec.tasks.json`:

```
PWD=/private/tmp/tp-ax2   exit 4, timed out waiting for lock
PWD=/tmp/tp-ax2           exit 0, wrote the file
```

Afterwards `.tp/locks/` holds two lock files for one target. On macOS this is the ordinary case, not
an exotic one: `/tmp` → `/private/tmp` and `/var` → `/private/var`.

The reason it is worth a section of its own is what it says about the tests. v0.34.0's new lock
guards call `filepath.EvalSymlinks` in their setup, with a comment stating the two processes "must
agree on the absolute task-file path or they hash to different lock files" — the fixture works
around the hole, so no test can fail on it. That is the fixture-blindness pattern this repository
has hit before, and it is why the defect survived a release whose §3 headline is that atomicity is
not mutual exclusion.

v0.34.0 left it alone because `LockFilePath` is untouched by that release and canonicalising the
key changes lock-file naming — a behaviour change to the locking mechanism at the end of a
maintenance release. §3's own claim, that both writers now take the lock, is unaffected and true.

## 10. Four smaller things v0.34.0's audit measured and left

- **`tp validate --project` omits `skipped` entirely when empty**, and documents it nowhere, so an
  agent cannot tell an absent key from a zero count. Separately, `--strict` promotes deviations
  only, so exit 0 can also mean a malformed task file was never examined — two different states
  behind one code.
- **The write-lock reachability guard cannot see a method on a constructor-returned receiver**
  (`h := newX(); h.write()`), nor one bound as a function parameter. Both were proved by mutation
  and both are vacuous today — no method in `internal/cli` writes a task file — and the file's own
  comment discloses the general rule. Worth closing if a method ever becomes a writer.
- **A write inside the argument expression of the `WithFileLock` call itself is treated as locked.**
  `walkLockAware` marks everything under the call node, and its comment says "sits lexically
  inside", which literally covers the argument list. Every real call site passes a plain identifier
  or a `filepath.Join`, so there is no live instance.
- **The two-homes count is much coarser than the work it scores.** v0.34.0's last repair cut twelve
  duplicated statements and moved the figure from 7 to 6, because the collection instrument reads
  headings while the duplications lived in bullets inside sections both documents legitimately keep.
  The number is a floor and a weak one; a sentence-level comparison is what actually found the
  duplicates, and it is what a future check should run.

## 11. Three things v0.34.0's later audit rounds measured and left

- **The gate structurally cannot see dead exported code.** `unused` (U1000) skips exported
  identifiers, so `GetFileFlag`, `IsNoColor` and `IsQuiet` in `internal/cli/root.go` have zero
  callers and pass. `git log -S` puts their last change in the v0.24.0 cycle, so this release did
  not leave them — but §6.3's dead-branch sweep could never have found them either, because the
  instrument that would report them is off by design for exported names.
- **The two new lock test files share an 18-line block below `dupl`'s threshold**, including a
  `runResult` type declared twice. The fix is a shared helper, which is the abstraction an audit
  repair is not allowed to introduce.
- **`tp show` with no arguments exits 1 with a hint that does not apply.** The hint says "the error
  message names the object that failed", but the message is `accepts 1 arg(s), received 0`, which
  names no object. So the arity path is not only split from the exit-2 usage channel (§3 above) —
  its hint is inapplicable to the errors it lands on.

**One boundary worth keeping when any of this is worked.** The duplication instrument these rounds
converged on clears verbatim repetition at 55 characters, not semantic restatement: `README` and
`REFERENCE` both state `empty-section`'s container-heading exemption in different words, and no
substring measure sees it. Below the threshold the four documents still share about thirty
phrase-level fragments, which two roles independently judged to be field-name vocabulary rather
than facts with two homes. That judgement, not a measurement, is what the final §8.1 pass rests on.

## 12. tp catches a duplicated paragraph in markdown and cannot see one in Go

`internal/model/io.go:76-77` carries the same doc-comment line twice. That is exactly the shape
tp's own `duplicate-paragraph` lint rule reports in a spec, and nothing in the toolchain sees it
here: `dupl` reads tokens, not comments, and no other enabled linter looks at comment text.

It predates v0.34.0 (introduced in `a4c1807`, shipped since v0.29.0) and no acceptance covers it,
so round 7 recorded it rather than fixing it. The interesting half is not the two lines — it is
that tp already knows this defect class well enough to lint for it in one language and has no
instrument for it in the language it is written in.

## 13. `category` means two different things, and only one of them is checked

Found by running `deadcode` after v0.34.0 shipped, and half-fixed on the spot.

The audit side has an enum — `security | concurrency | error-handling | correctness | contract` —
declared as typed constants with a validator, and the record sink now rejects anything else.

The review side has a different enum — `completeness | ambiguity | consistency | feasibility |
redundancy | regression` — declared as a **string literal inside the prompt template** at
`internal/cli/review.go`, with no constants, no validator, and nothing checking what comes back. A
review finding can carry any category at all and be recorded.

So one field name carries two disjoint vocabularies through two parsers, and the two halves are
held to different standards. Worth deciding deliberately: give the review side the same treatment,
or rename one of them so a reader stops having to know which phase a row came from to know what
`category` may say.

Evidence that the unchecked half drifts: 107 rows across 21 test fixtures carried a category outside
either enum, including `cat-a`, `c`, `x` and `style`. The audit ones were corrected when the sink
check landed; the review ones are still there, because nothing rejects them.

## 15. What v0.35.0's audit found and deliberately did not fix

Four rounds, four roles, ~200 rows a round. Every FAIL was repaired in the round after it was found;
what follows is the residue — findings the audit surfaced, verified by running, and left, each with
the reason and the version that should take it. None is a spec-conformance gap: `spec-coverage`
reached 169/170 PASS with zero FAIL.

**`output.Notice` is not yet the only warning channel (v0.36.0).** v0.35.0 converted the four sites it
either added or repaired — `runlock.go`, `lock.go`'s byte-identical twin, and `validate_project.go`'s
two — plus `surfaceConfigWarnings`, which was leaking one line above a repair and made
`tp validate --project --quiet` not quiet. Roughly twenty raw `fmt.Fprintf(os.Stderr, "warning: …")`
sites remain elsewhere. The bulk migration is a channel move, which CLAUDE.md assigns to the next
version; the principle applied here was narrower and worth keeping: **a release does not add to a
class it knows about, and closes any instance inside the surface it just repaired.** A mechanical
check for the class is the natural v0.37.0 item.

**`tp graph` and `tp stats` (v0.36.0).** Surfaced by the QA regression pass, both pre-existing —
each reproduces identically on `v0.34.2`, which is how they were told apart from this release's
changes. `graph` emits `nodes: null, edges: null` on an empty result, violating the nil-slice rule
this repo states about itself, and both commands iterate a map so identical input yields different
bytes run to run. Neither is in v0.35.0's surface, and determinism is worth its own change rather
than a rider on an audit repair.

**`done --batch` drops a row's `commit_sha` silently (v0.36.0).** The batch schema wants
`commit_shas` (array); the singular is both the `Task` field name and what `--commit` stores, so it
is the natural mistake, and the task closes green with its provenance gone. Unknown keys are ignored
without warning in `tp add` and `tp import` too, so this is one instance of a class. Warning on
unknown keys changes three commands' input contracts — a deliberate change, not an audit repair.
Related: a `done --batch` whose rows all fail still leaves the tasks `wip`, while `tp done --help`
promises "Task unchanged".

**`tp run --status` and `--dry-run` together apply a silent precedence (v0.36.0).** `--status` wins
with no diagnostic, while `tp audit`'s two sub-modes reject the same shape with exit 2 and
"mutually exclusive". Same shape, two contracts: a driver that learns the rule from `audit` gets
silence from `run`.

**The duplicated run-lock test helper (v0.36.0, low).** Fourteen lines repeated across four
`cli_test` files while `internal/engine/runlock_test.go` factors the idiom into `holdRunLock`.
Settled by measurement rather than taste: `dupl` reports zero for those files at the configured
threshold of 150 **and still zero at 40**, and `holdRunLock` is unexported in package `engine` while
the copies are `package cli_test`, so "reuse the existing helper" is not an available fix — a fresh
`cli_test`-local helper would have to be written.

**A symlinked directory defeats the write fence, and that is in scope for the fence's stated job.**
With a pre-existing `cfg -> .tp` symlink, `cfg/config.json` is allowed and does clobber the real
file; the hook's lexical `..` resolution likewise disagrees with the kernel. Not raised as a finding
because §6.2 scopes the fence to stopping hand-editing rather than sandboxing, shell tools are
deliberately outside the matcher, and an agent that can create a symlink can already write the file
through Bash. It buys no access it did not have.

**Two tooling hazards worth carrying forward.** codedbpro's `edit` and `patch` both clear a shell
file's executable bit on every write — four hook tests now assert mode 100755 for exactly this
reason. And `faster_search` with `mode: "regex"` over a *directory* path returned zero matches twice
in this cycle for patterns that demonstrably exist; an auditor treating a regex zero as a fact is at
risk of reporting an absence that is a tool artifact.

**`tp config --extract` does not hoist `commit_strategy`, while `tp validate --project` now reports
its deviation (v0.36.0).** v0.31.1's Non-Goal 1 fenced both halves; v0.35.0 re-opened the validate
half on the ground that reporting a deviation only reports, and left the extract half closed because
`--extract` writes. So the two field sets differ on purpose, and the asymmetry is now the thing to
decide rather than an oversight to fix. Note for whoever takes it: being read-only at the task level
(`readOnlyWorkflowFields`) is **not** a reason against hoisting — `quality_gate` is in that same set
and is hoisted today, because after a hoist the field lands at the project layer where the project
setter can author it. An audit round recorded that wrong reason and a later round refuted it by
running `--extract`; the corrected reason is scheduling.

## 16. What the pre-release mutation run said, and what is deliberately left

`gremlins unleash ./internal/engine` at the release decision point, on an `rsync` copy, machine
otherwise idle: **1540 mutants, 1033 killed, 253 lived, 227 not covered, 27 timed out, 80.33%
efficacy, 85% mutator coverage, 53 minutes**. Classified rather than scored, per the standing rule.

**The number that answers the release question.** Split by whether the file is v0.35.0's own new
surface: the new engine files kill **169 of 180** tested mutants (**93.9%**), against **78.1%** for
everything pre-existing. `driver.go`, the largest thing this version adds, is at 90.2%, and
`recordround.go` came back with every mutant killed. The version's own code is tested; the survivors
are almost entirely older.

**Deliberately left, with the reason:**

1. **`validate.go` — 46 survivors, 24.6% efficacy.** Unchanged from the figure CLAUDE.md already
   carries as the standing backlog. It is not v0.35.0 surface and this release did not touch it.
2. **`vague.go` (37), `structured.go` (17), `brief.go` (16), `resolve_section.go` (14).**
   Pre-existing lint and prompt heuristics. Each survivor is a boundary or negation inside a
   scoring rule whose exact threshold is not a documented contract, so a test pinning it would
   pin an implementation choice rather than a promise.
3. **27 timeouts, concentrated in `structured.go` and `linecoverage.go`.** These are
   `INCREMENT_DECREMENT` applied to loop counters, which produces a genuine non-terminating loop —
   a correct timeout, not the load artifact that invalidates a run. At 1.8% of mutants they do not
   put this run in the "a run full of TIMED OUT is not a result" category.

**One new item, routed rather than fixed (v0.36.0 or later).** `internal/engine/bookkeeping.go`
scored 0 killed / 4 lived / 17 not covered. It is **v0.29.0 surface**, not this release's — but the
gap is real and larger than mutation alone shows: measured against the *whole* suite with
`-coverpkg`, `roundRefFromName`, `closureEntries`, `managedFieldsChanged`, `ptrTimeEqual` and
`ptrStrEqual` are all at **0.0%**, with `DeriveBookkeeping` itself at 52.4%. `tp resume` prints a
`bookkeeping` array in production — this repo's own state has one — so these are reachable paths no
test reaches. Out of scope for a v0.35.0 audit repair under the spec-conformance rule; worth a task
of its own.

**A correction to CLAUDE.md's own estimate.** That file says gremlins takes "about five minutes for
~1000 mutants". This run took **53 minutes for 1540**. The engine package has roughly doubled since
the estimate was written, and the two decision points should be budgeted at an hour, not five
minutes — which is also why it must not be started while task gates or role agents are running.

## 17. The two degraded-scan repairs disagree with each other (v0.36.0)

v0.35.0's audit produced two repairs of one defect class — a scan that could not be performed
reporting as one that came back clean — and they chose different channels.

`tp validate --project` puts it in **both**: an unreadable or unparseable config emits an
`output.Notice` on stderr *and* a `skipped` key in the payload. The comment there argues the payload
half explicitly: stderr "is erased by `--quiet`; this is the same fact in the payload a driver
actually branches on."

`tp run --status` puts it on **stderr only**. An unprobeable run lock reports
`run_state: "in_flight"` with an `output.Notice`, and under `--quiet` that notice is gone — leaving
a payload indistinguishable from a genuinely live run. Round 7's `ax-contract` demonstrated it by
making `.tp/locks` a regular file and running `tp run --status --quiet`: `in_flight` on stdout,
nothing on stderr. `run_status_unreadable_lock_test.go` asserts the stderr warning and has no
`--quiet` case, so the suite does not see the gap either.

**Deliberately not repaired in v0.35.0.** §3.5 defines `run_state` as three values and requires no
payload field for a probe that could not be run, so closing this means inventing vocabulary the spec
does not carry — the "a repair that introduces a new abstraction belongs to the next version" rule.
The dangerous direction is already fixed: a live run is never reported as `crashed`. What remains is
that a consumer cannot tell a verified `in_flight` from an assumed one.

**For whoever takes it:** decide the channel rule once for both sinks rather than per-command, and
add the missing `--quiet` case to the run-status test. This is also a concrete instance of the
`spec/0.38.0.md` §5 problem — a verdict with no way to say "I could not verify" — reached from the
run-state side rather than the audit-row side.
