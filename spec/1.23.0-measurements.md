# 1.23.0 measurements: an epic's owner

What the release measured. The decision is `spec/backlog/epic-owner.md` (archived; read it at
`edeebda0`); `spec/backlog/ARCHIVE.md` carries its row.

## What shipped

- **Graph.** A top-level `owners` set (`{handle, name}`) and `epics[].owner`, a list of handles in
  the order written. Two lint errors: `unknown-owner` (an epic names an undeclared handle) and
  `owner-handle` (blank, spaced, repeated, or equal to an earlier handle under Unicode case folding;
  an epic naming one twice). Every writer refuses a write adding either, so a handle still named
  cannot be dropped from the set; `tp epic apply` lints once after its last row, so a rename is one
  apply file.
- **Reads.** `tp epic ready` and `tp epic status` entries carry `owner` when the graph declares
  owners; both take `--owner <h>` (repeatable) and `--unowned`, a union when combined, an
  undeclared handle exiting 2. An epic naming only undeclared handles reads as unowned. `--md` gains
  an owner column after tags when owners are declared.
- **Not scope.** An owner is not in an epic's review block or the `tp epic scope` fingerprint.
- **Dashboard.** Drawer owner row; map owner selector (kept by handle across pushes) and a
  colour-by-owner switch (fill by owner from eight slots per theme, "other" past the eighth, an
  unowned slot, border kept for state, `+N` on multi-owner epics, legend counts by membership);
  operator conditions grouped under their owners, unowned last, other decisions under their own
  heading.

## A graph without owners

On a synthetic graph with two tracks, a gate with a threshold, a tag check, a claim, a condition, an
any-of group and a done epic, the released v1.22.3 and the branch binary printed byte-identical
output for `tp epic ready`, `ready --all`, `status`, `status --compact`, `export --md`, `lint`, and
`export` with `generated_at` removed: 7 of 7. A test keeps the word `owner` out of every read of a
graph without owners.

## Prototype and process

Decision track. The note was read once in depth by the planning session, whose eight objections
(output with no owners, multi-owner counts, palette bounds, handle equality, escaping, the rename
claim, import, flag semantics) were folded in before any code. A clone prototype of the schema,
setters and lint measured the three behaviours the note rests on: dropping a handle in use is
refused at exit 1, apply lints once (a rename in one file passes), and import carries the set with
the graph and reports undeclared handles as findings, as it reports every lint error.

The dashboard was built by a second agent in a worktree and checked in a browser, in both themes,
against counts written down before the page was opened (synthetic fixtures: three owners, one
named with markup, a two-owner condition, an unowned condition; ten owners for "other"; a graph
without owners): every count matched.

## Review

Two roles, two rounds, on `main...epic-owner`, each finding probed in a clone before it was
reported.

- **Round 1, ten findings, four medium.** An epic naming only undeclared handles was hidden by every
  filter; the map's owner selection was kept by position and broke after a push that dropped or
  reordered owners; colour-by-owner hid state at far zoom; operator rows outside the owner groups
  fell under the last owner's heading. Low: Unicode case-fold twins (`ς`/`σ`, `ſ`/`s`) passed
  `owner-handle`, a selected epic outside the chosen owner was dimmed, the empty-set refusal printed
  an empty list, two stacked doc comments, a Turkish heading. All fixed test-first.
- **Round 2, four low, every round-1 fix confirmed.** A byte-for-byte repeat after a case twin was
  reported with the twin's message; SKILL.md said `--unowned` keeps entries that name no one; the
  light theme's "other" and "unowned" fills were ΔE76 3.3 apart and two slots were both blue; the
  legend drew an "other owners" row with a count of 0. All fixed; a test now holds every pair of
  owner fills at ΔE76 12 or more in each theme (smallest measured: 13.4 light, 15.6 dark).

## Mutation run

`TP_MUT_PKGS=internal/engine ./scripts/mutation.sh v1.22.3`, five engine files: 34 mutants, 25
killed, 0 escaped, 9 not covered; covered-code score 100%. The nine not covered sit in code the
engine tests do not reach and the `internal/cli` tests do, as a subprocess the per-test selection
cannot see (the trap recorded in `spec/1.22.3-measurements.md`). Those paths were checked by hand
mutants during the build, each turning its CLI test red: the owners setter ignoring its value, the
owner rules unwired, the `owners` JSON tag dropped, owner entries filled without a declared set,
and the empty-set refusal hint.
